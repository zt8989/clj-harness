# 0002 —— 会话归服务端：内存是权威、记录异步落后、浏览器只发动作

- **日期**：2026-09-20
- **状态**：**已采纳**
- **推翻**：`docs/architecture/overview.md` 三条铁律的**第 1 条与第 3 条**，以及同一份文件「状态存在哪」
  那张表的若干行；`.scratch/job-output/spec.md` 决策 3（「帧就是客户端的会话」）；
  `.scratch/skills-and-instructions/spec.md` 里由「服务端不存会话」派生的那条推论。
- **不推翻** `.scratch/session-after-refresh`：它的 01–03 已落地（本决定就建立在它们之上），04–10 未落地、
  仍然算数，其中票 05「拒绝同一会话的第二条 run」是**本特征的前置**。

## 背景

**读侧已经是副本了，写侧还是客户端。** 这是本决定的全部由来。

1. `session-after-refresh` 的 01–03 已落地：页面把「我在哪一场」记在 `localStorage`
   （`ui/src/lib/session-memory.ts`，键 `clj-harness.session`），关掉标签页、重启浏览器都回到那一场；
   挂载时历史**从服务端读**（`sessionHistory.load` 走 `rebuildThread` / `readSofar`，`app.tsx:207`），
   而 adapter 的 `append` / `update` 是 **no-op**——注释自己写着「the harness owns the log」。
2. 但**写侧**还是客户端：每一轮把累积的整份 `messages` 送回去（服务端只读 `(:messages input)`，
   `ag/inbound` 只是转换它）。于是：
   - **两个标签页是常态**——同一个 id 共享 localStorage，`session-memory.ts` 自己写着
     「TWO TABS LANDING IN ONE SESSION is the ordinary case, so the client can never be assumed to be
     the only one talking」——而**服务端今天不拒绝第二条 run**：那条门是
     `.scratch/session-after-refresh/issues/05`，还没落地（`http.clj:513` 的注释就指着它）。
   - **注入每轮重算、每轮一张卡**：注入不在任何一方**持有**的历史里（客户端不回发它），所以每次模型调用
     都要现算、现送、现画。
   - **两份「真相」并存**：客户端手里那份 vs 记录那份，谁对谁错没有裁决处。

## 决策

1. **会话归服务端。** 一个 thread-id 的会话在服务端**内存**里：`thread-id → 会话`，进程寿命。
   run 的输入**不再**是浏览器递上来的消息列表——`RunAgentInput.messages` 退役。
2. **历史初次从记录（jsonl）重建，之后在内存里操作。** 读文件是**一次**的，不是每轮的。
3. **记录异步写，落后是允许的。** 帧进一条队列，单个消费者逐行 append。落后 = 记录是一份**更短的**
   会话，不是一份错的：它永远是**有序的前缀**（一行一个 JSON、一个写者、按发生顺序）。而「一段会话在
   记录里停在 run 中间」这个状态**仓里早就有名字与处置**：重建先 `close-off-open-run!`（`http.clj:1827`）
   补上收尾帧，那就是客户端看见的结局。**落后的记录不会假装自己完整。**
4. **浏览器是只读副本，只发动作。** 发送消息、换模型、审批回答、停止、归档都是动作；副本画什么由服务端
   给的帧决定，它不撰写历史。
5. **会话的寿命：按需出生 + 空闲 30 秒放掉，两个钉子把它按住。** 出生在**点进界面**（或对它发起一次动作）
   时，从记录重建一次；此后空闲 30 秒放掉。两个钉子：**正在跑**（run 没结束不放）、**还有没落盘的东西**
   （run 跑完也要等记录写完才放）。后一个钉子正对着决策 3：有「已经落盘」这个事实，放掉才不等于丢东西。
   **内存的上界不靠放掉兜**，靠**限制同时运行的会话数量**。
6. **写失败不许静默。** 落盘节奏是**每帧**：一帧入队就写，单消费者逐行 append。异步换的是「IO 不在
   响应路径上」，**不是「少写」**——落后的窗口 = 队列积压。写失败（盘满、权限）⇒ 那个会话进**降级态**，
   并在界面上说出来。落后允许，**失败不许静默**。
7. **一个 thread 归一个进程。** 认领（锁文件／库里一行 owner）；后到的只读或拒绝。理由：记录异步且落后，
   两份权威交错写进同一个 append-only 文件之后**没有任何东西能把它们分开**。
8. **副本自播，只在动作与刷新时对账**，配一个单调序号。**刷新走内存**（不是记录）：否则落后时刷新会看到
   比屏幕上**更早**的会话，像是丢了东西。
9. **输入面：动作只携带「做什么」和「对谁做」。**

   | 字段 | 归类 | 决定 |
   |---|---|---|
   | `messages` | — | **退役**（服务端持有） |
   | `threadId` | 目标 | 留；**铸 id 收进「新建会话」这个动作，服务端铸**（客户端不再能凭空开一场） |
   | `runId` | — | **服务端铸**，动作里不带（客户端从帧里的 `messageId` 读） |
   | `provider` | 状态→动作 | **动作化**（= `POST /api/model`，composer 的选档器），请求里退役；客户端显示服务端报的当前档 |
   | `context` | 状态 | **归会话状态**：出生时构造一次、进历史，此后不在输入面里 |
   | `resume` | 动作 | 留（`interruptId` 也留，认不出就拒——今天已是如此） |

    **2026-09-21 修正（只改 `threadId` 这一行）**：合并 `brand-header` 时这一条与主人的另一句规矩
    「点击新增不立刻会话，发送才新建」正面撞上，改的是**谁铸、何时铸**，不是「客户端可以凭空开一场」
    ——那件事仍然不行，而且挡在原来的地方：库里在发送之前一行都没有，而这枚 id 必须在那一场的第一次
    run 请求**之前**登记一次（项目会话走 `POST /api/project`，任务走 `POST /api/sessions`；两条路由
    都认调用方给的 id、都幂等），因为 run 那条边对陌生 id 仍然是 404。于是页面在点击时铸一枚自己的 id、
    只在本地打开一场空会话，服务端在这次登记之前对这枚 id 一无所知——登记的**时刻**从「点击时」挪到了
    「第一句发送前」。见 `docs/architecture/client.md` 的侧栏那条流。

    统一由后端创建」，问清之后是「不使用uuid的意思是**不引入 uuid 库**，之前手机端报错了，所以不要有
    这个依赖」。上一次修正改的是**何时**铸（登记挪到第一句发送前），这一次改回**谁**铸：页面不铸了。
    根因是 `crypto.randomUUID` 只在**安全上下文**存在 —— 手机走 `http://192.168.x.x` 读 dev server
    时它根本没有，页面在画出来之前就抛 `TypeError: crypto.randomUUID is not a function`，而 127.0.0.1
    **是**安全上下文，所以机器门全绿。于是新增 `GET /api/ids/new`：**铸一枚名、什么都不写**；页面在
    首次绘制之前（`ui/src/main.tsx`）与每次「新建」时向它要（`app.tsx` 的 `spareName` 把下一枚先要到手，
    所以点击没有往返）。**「点击新增不立刻会话，发送才新建」一个字没动**：名字不再由页面编，而登记的
    **时刻**仍然在第一句发送之前 —— 上一次修正与这一条并不冲突，冲突的只是「谁铸」。
    见 `.scratch/server-named-sessions/`。

10. **铁律 1 的新措辞**：**「run 中不读自己的日志（内存里就有）。日志只 append、异步写、允许落后，
    且永远是会话的有序前缀。日志是恢复源；运行时的真相在内存。」**

## 代价

- **进程成了会话的寿命。** 内存随进程死，**唯一的恢复源是记录**，而记录允许落后 ⇒ 崩溃丢掉的是「还没
  落盘的那一段」，**恢复不回来**。这是本决策买的单，不是副作用。
- **多进程是两份权威**（决策 7 认领之前）：`running?`（`http.clj:517`）是**进程内**的注册表，
  它答不了另一个进程里有没有人在跑同一场。
- **同一场的第二条 run** 今天**不被拒绝**——那是别人票上的事（`session-after-refresh` 票 05），
  而本决策把「一个会话只有一份权威」抬成了前提，所以那一票从「补一个洞」变成「补一根柱子」。
- **两条铁律与它们的推导要重写**：散在 `overview.md`、`kernel.md`、`edge.md`、`client.md`、
  `skills-and-instructions.md`，以及「状态存在哪」那张表。

## 落地

`.scratch/sessions-live-on-the-server/spec.md` + 六张票（01 → 06）。

## 边界（不做的事）

- 不改记录的格式：一行一个 JSON，只 append，不迁移。
- 不改记录里 `message` 行的形状：它今天就是「那次真送出去的那份」，是忠实度的凭据。
- 不改 AG-UI 那几帧的形状。
- 不做鉴权、账号、多人协作。
