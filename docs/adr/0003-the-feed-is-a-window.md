# 0003 —— 会话是一条带窗口的 feed：尾页 + 增量推送 + 按需补页

- **日期**：2026-09-20
- **状态**：**已采纳**
- **修正**：`docs/adr/0002-sessions-live-on-the-server.md` 的 **决策 8**（「副本自播，只在**动作**与
  **刷新**时对账，配一个单调序号」）。0002 的决策 1–7、9、10 **不变**。
- **参照**：DeepSeek Harness 的实际形状——`@deepseek-ai/dsh-api-session-controller` 的
  `open()` / `loadOlder()` / `loadThrough()`，`@deepseek-ai/dsh-client-connection` 的 journal 流，
  `@deepseek-ai/dsh-client-ui-trajectory` 的 `hasEarlierRecords` / `onLoadEarlier`。

## 背景

**0002 决策 8 只给了两个对账触发，于是读者被分成了两种。** 发起 run 的标签页拿到 `POST /api/agent`
的 SSE；**只是看着**的标签页每 1.2 秒轮询一次 `sofar`（`app.tsx:110` 的 `WATCH_INTERVAL_MS = 1200`），
而那条轮询读的是**记录**——落后那份。`app.tsx:336` 的注释自己写着「never a second streaming path」：
它是**刻意**不做第二条路的妥协，不是没想到。

**而读侧还是全量。** 票 01 把会话表立起来之后，读路由答的仍是整份 `:messages`（`http.clj:1948`）；
一场 300 条消息的会话，每次打开、每次刷新都把那 300 条搬一遍。长会话的 wire 成本随会话长度线性涨。

**参考实现在这里走的是第三条路：推 + 窗口 + 补页。**

- 首次打开拉的是**尾页**，不是全史：`events.open({ maxMessages: 50 })`。
- 窗口自带 `baseSeq` / `hasMore` / `revision`（`windowSnapshot(node, hasMore, revision, change)`），
  每次变更 `revision + 1`。
- 更早的历史是**拉**：`loadOlder()` 一页 50（`prepend({ beforeSeq, maxMessages: 50 })`），
  跳转是 `loadThrough(seq)` 一页 200、循环拉到窗口覆盖目标。
- 断档只重建**已加载窗口**：「replace window 或 revision 断档从完整已加载窗口重建」，重连的 seq 缺口
  「通过 tail page 修复」——不重读全史。
- 那条 feed 是推的：`dsh-client-connection` 写着「**带重连的事件流投递**」，走 WebSocket。

**「全量推送」是错的那一半。** 把「推」和「全量」绑在一起，等于把一个有界的读变成长会话的线性成本，
而且它和 0002 决策 3（记录异步、允许落后）不在同一个坐标系里：落后只影响**尾巴**，窗口让这件事
变得可操作——更早那部分已经落盘了，不会变。

## 决策

1. **一场会话一条 feed**，服务端是它唯一的写者；条目按发生顺序，每条带一个**单调序号**。
2. **存量是尾页，不是全量。** 打开一场会话拿到的是**尾部一页**（条数是一个写下来的数字），外加
   `baseSeq`（窗口第一条的序号）与 `hasMore`（更早的还在不在）。
3. **增量是推送。** 窗口内的新条目由服务端推给连着的副本。推送与补页是**同一条 source 的两个方向**
   （向前 `append` / 向后 `prepend`），不是两个接口。
4. **更早的历史是拉，不是推。** 副本按需向前补页（一次一页，条数写下来）；「显示更早」是一颗按钮，
   不是自动加载全史。
5. **断档只重建「已加载窗口」。** 序号缺口 / 重连拉一页尾巴把窗口对齐（`since` 语义），再继续增量。
6. **窗口有一个 generation。** 会话被放掉（空闲 30 秒）、进程不再是它的 owner（票 04）、地址被替换 ⇒
   窗口作废，重开尾页。副本拿着作废的 `baseSeq` 继续补页要被**拒绝并说出** generation——不静默从头
   （那会重复），也不静默断（那会让副本以为到齐了）。
7. **「服务端不做订阅」的准确说法是「服务端不记谁在订阅」。** 0002 决策 8 真正想保的那件事
   ——不做**按客户端**的推送状态——仍然成立：游标随连接走（`since=N`），服务端从会话里取 N 之后发；
   除了活着的连接，进程不持有任何「谁订了什么」。票 07 改措辞时按这一条改。
8. **刷新走内存**（0002 决策 8 的后半，不变），窗口化之后更自然：刷新拉尾页，落在最新那一版，
   不必先算「内存比记录新多少」。
9. **不改记录格式。** 序号必须**能从记录重放出来**（记录 append-only、一个写者），否则刷新之后序号
   会变，对账就没有凭据。

## 代价

- **窗口是一个新概念**（`baseSeq` / `hasMore` / `revision` / `generation`），客户端要维护它；读路由从
  「答一份消息列表」变成「答一页 + 三个标量」。
- **推送是一条有寿命的连接**：会话被放掉、认领易主时它必须收干净并**说出结局**，不许静默断。它落在
  http-kit 的线程池上，所以 `docs/rules/concurrency.md` 那套纪律照旧适用。
- **副本「超前」**（客户端有服务端不知道的东西）在窗口下依然是必须处理的诚实测试，见票 06。
- **`app.tsx` 那条「never a second streaming path」的妥协要还回来**：第二个观察者从轮询升级成一等读者，
  代价是当时省下的那些代码要重新写——换来的是同一条路服务两种读者。

## 边界（不做的事）

- **不推全史，也不做「订阅注册表」。**
- **不改 AG-UI 帧的形状**：序号是**新增字段**，不引入 `STATE_SNAPSHOT` / `STATE_DELTA`——本仓的「会话」
  是消息 + 卡，不是 agent 的一个 JSON state。
- **不改记录的格式**与 `message` 行的形状。
