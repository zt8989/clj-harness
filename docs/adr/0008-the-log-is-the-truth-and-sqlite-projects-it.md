# 0008 —— 日志是真相，库投影内容：SQLite 从 JSONL 追加消费

- **日期**：2026-09-25
- **状态**：**已采纳**
- **修正** `.scratch/project-sidebar` 的**决策 2** 与 `docs/architecture/home-and-storage.md` 的
  「**库不是日志索引**：jsonl 里的任何内容都不进库」。那一条的**另一半**——「库装可改写的状态」
  ——**一个字不动**：项目、会话归属、归档、认领、锚点、待办照旧住在库里。
- **参照**：主人 2026-09-25 拍的（「连内容一起投影（messages / tool_calls 表）」）。

## 背景

**原来的裁定有一条清楚的理由**：库装**能被改写**的东西，文件装**只追加**的东西；判据是「能不能被
改写」而不是「改得勤不勤」——而「一条消息永远不会被改写，所以它永远不进库」。

**主人换掉了这个取舍**：查询与状态恢复交给库（按 `seq` 取一段、按关键词找、按工具名统计），
而这些查询今天要么靠读整份记录（一场 68 MB 的会话，一次 `read-records` ≈ 1.8 s），要么根本没有。
代价是**内容从此有两份**——所以这一条必须把「可重建」从口号变成**动作与判据**。

## 决策

1. **JSONL 仍是唯一真相。** 投影**只读**：任何写路径都不碰它；任何读都必须能从记录**整份重算**。
2. **一层独立的投影消费者**：读每个活跃 JSONL 的**新增字节**（按 `byte_offset` 记进度），解析成行，
   投影进库，然后推进 offset。它**不在写路径上**。
3. **表**：`messages` / `tool_calls` 这类内容表 + `sessions` / `projection_offsets` 这类进度表；
   主键带 `(session_id, seq)`，写入用 `INSERT OR REPLACE`（**幂等**：重复消费不产生重复行）。
4. **库的配置**：`journal_mode = WAL`、`synchronous = NORMAL`（投影可重建，不必 FULL）、
   `busy_timeout`。**这一条与 `harness.infra.db` 今天的连接纪律要合起来看**（它是 per-call 打开、
   不缓存句柄的——投影消费者要是长期持有的第二个连接，得单独说清）。
5. **落后要说得出来**：JSONL 的字节数 − 投影的 offset = 投影延迟；它是**读侧的一个数**，不是沉默。
6. **整份重建是一个动作**：删掉投影、从记录重放一遍，结果是**逐行相同**——这是这一族的验收标准，
   也是「可重建」这句话的唯一凭据。

## 代价

- **内容有两份**，所以「库和记录不一致」从此是一种可能的故障，而以前不是。判据（决策 6）与
  延迟（决策 5）是这一条的护栏。
- **库会跟着记录长**：投影是记录的字节级副本（去掉封装后略小）。今天 `harness.db` 已经 174 MB
  （那是锚点树），而一场会话的记录可以到 68 MB——**投影不是免费的**，要能按会话丢弃与重建。
- **多一个长期跑的东西**：消费者线程/协程要有生命周期、要有停法、要在测试里能换成同步实现。
- **今天读内容的那几处**（`stats` / `context` / `trajectory` / `sidebar` / `rebuild`）**先一个都不动**：
  投影是**新加的一层**，谁改用它是之后逐处的事，且每一处都要能退回「读记录」那条路。

## 边界（不做的事）

- **投影不进写路径**，也**不做第二真相**：任何读都能从记录重算。
- **不改记录格式**，不改行号语义。
- **不动库里那半「可改写状态」**。
- **不在投影里存记录没有的东西**（不做摘要、不做全文索引之外的派生内容）。

## 落地

`.scratch/event-persistence/spec.md`：内容投影是它最后一张票（票 06 之后的那张），
而票 01（记录同步写，ADR 0007）是它的前置——**同步写让 offset 与 `seq` 当场可得，投影消费者
才不必猜「哪一行是第几行」**。
