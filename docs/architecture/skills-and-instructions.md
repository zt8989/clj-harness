# 技能与指令（一场会话开场拿到什么）

会话开场时，模型除了 system 消息（冻结的开头 + hook 追加的文本，见
[hooks](hooks.md#systempromptstdout-是内容的那一格)），还会拿到**两块约定内容**：约定位置的**指令文件**，
以及约定位置的**技能清单**；技能被**加载**后，正文再补进对话——而加载有两条路：模型的 `skill` 工具，
与人在输入框里打的 `/name`。三件事由两个命名空间分管——
`harness.cap.skills` 管技能（根、目录名即身份、frontmatter、坏技能诊断、正文的派生注入），
`harness.cap.preamble` 管**user 侧开场块**那几条消息的**顺序**与读指令文件的失败语义。

**这一页讲的是现状**：默认位置是哪几个、注入的形态与顺序、失败怎么分、以及各自为什么这样定。
它不创作技能——不写、不装、不做授权。

## 一场会话开场拿到什么

一条 run 交给 provider 的消息向量，形状是固定的——**先问题，再为它准备好的料**：

```
[system  组装的 system 文本：prompt.md 的冻结开头 + 各 SystemPrompt 声明追加的文本]
[...客户端带来的会话消息...]
[user    <instructions path="<os-home>/AGENTS.md">…</instructions>]        全局，先
[user    <instructions path="<project>/AGENTS.md">…</instructions>]        项目，后（更具体、离提问更近）
[user    <skills>…清单…</skills>]                                          能力菜单，最后一块 context
[user    context（既有：每轮请求携带的 context）]
[user    <skill name="…">…正文…</skill>]                                    skill context，缺省没有（见「技能正文是派生的」）
```

**2026-09-18 起这个顺序是「system → 提问 → context → skill context」**：注入物从 system 之后、客户端消息
之前挪到了**提问之后**——模型先读人问的那一句，再读为它准备的料，而最近的一段（技能正文）贴着问题。
常驻规则排在能力菜单之前，这条没变：模型先知道「必须先怎样」，然后才拿到「还能拿什么」。

**挪动不花 prefill 一个字节**：prompt cache 钉的是**稳定的前缀**，那个前缀是 system 加客户端每轮重发的
历史，而注入物本来就在它之外——从前夹在两者之间，现在排在两者之后，前缀长度一模一样。

**顺序是语义，不是排版，所以它只有一个地方决定**：`harness.cap.preamble/messages` 定几块之间的先后，
`harness.edge.ag_ui/inbound` 的 `tail-blocks` 把它们拼在**尾部**，技能正文由
`harness.cap.skills/derived-injections` 追加在最后。散落在调用点就是把这个决定藏进两行 `into`，所以不许。

**system 消息只有一条，这一页说的那些块一律 `role=user`。** 两条理由：
`ag_ui/inbound` 关于 system 的规则只有「客户端带了就换成冻结的那条、没带就前置一条」——多加一条
system 会把那条规则变成「关于一族 system 消息的规则」；而 role 本身就是给模型的框架（这是被放进来的
东西，不是人刚打的字），`<instructions>` / `<skills>` / `<skill>` 三个标签再补一层明确的边界。
（system 那一条里**追加**的部分属于另一半，由 `harness.cap.system-prompt` 组装、`SystemPrompt` 点上的
hook 决定——两半不可能交错，因为 role 不同。）

**位置解析是纯函数**：`skills/roots` 与 `preamble/instruction-files` 都是 `(配置值, 项目目录)` 入参，
**不查绑定、不读 harness.edn**。这不是洁癖，是断环——围栏必须知道技能根（见「与围栏的关系」），
所以 `harness.cap.project` require 它们，反过来 require 就是环（Clojure 在 `require` 时就报）。
调用方手里本来就有这两样：围栏有绑定，`skill` 工具体有 thread-id，于是 `harness.cap.project/skill-roots`
与 `preamble-files` 做那一次配对——只有它同时看得见配置读取、绑定、以及两个纯函数消费方。

## 技能：目录名即身份

- **默认根**：`<OS 家目录>/.agents/skills`（**系统级**），绑定项目时再加 `<项目>/.agents/skills`（**项目级**）。
  **前面的根赢同名**，所以按这个默认顺序**机器上的那份赢**：项目里放一份与机器上同名的技能，
  它在模型的清单与人的技能列表里**都不出现**（它加载不动，所以不该在表里）。顺序本身就是机制，两处各钉一半：
  `harness.cap.skills-test/the-two-defaults-are-the-host-conventions`（默认顺序 = 项目那份排在后面、输）
  与 `harness.cap.skills-test/layer-precedence-the-project-wins-a-name-conflict`（把顺序倒过来，赢家就换人）。
- **一个技能 = 一个目录里有一个 `SKILL.md`**。文件名**精确匹配**，不做大小写猜测：这个仓的纪律是
  「没人写过的名字是命名失败」，而替人猜哪个文件是「把一次手滑变成一次静默 no-op」。
  没有 `SKILL.md` 的目录（`_shared/`、`references/`）**静默跳过**——它根本不是技能。
- **身份是目录名，不是 frontmatter 里的 `name`。** frontmatter 的 `name` 只用来**核对**它与目录名是否
  一致，不一致就是坏技能（`:name-mismatch`）。这条是安全性的来源：`scan` 只会产出它从目录列举里读到的
  名字，所以 `skill-for` 是一次**查表**而不是路径拼接——`../../etc/passwd` 不是被拒绝，是根本不在表里。
- **frontmatter 只读三个键**：`name` / `description` / `disable-model-invocation`。其余
  （`allowed-tools` / `license` / `metadata` / `argument-hint` / `hidden` …）**属于宿主，读到了也不报错**——
  一个文件多写了字段不是错误。解析是手写的窄解析器（扁平的 `key: value`、引号值、`|` 与 `>` 两种块标量），
  不是 YAML 依赖：那会为了五个键买一个库，而它多接受的那些形状没人写过。
- **坏技能是诊断，不是失败。** 读不动、没有 frontmatter、`name` 与目录名不符、没有 `description` ——
  该技能 `:available? false` 且带 `:reason`，**仍在 `scan` 里**，只是不进清单、被调用时得到同一句话。
  它留在表里是刻意的：**一个静默消失的技能，与一个从没装过的技能，从外部看没有区别**，而后者难查得多。
- **清单只发目录，不发正文。** 五十个技能付五十行的代价，不付五十份文档。每条技能的 description
  **原样不截断**：触发词（"Use when…"）大多落在 80 字符之后，而它正是模型据以选择的依据，
  裁长度省下的恰恰是选择需要的那一截。代价如实写：一份超大的 description 会原样进上下文，
  所以自省面报出每块的字符数（见「自省」），但**绝不静默裁剪**。
- **`disable-model-invocation: true` 的技能不进清单**：文件自己说这条不该由模型决定去用——所以清单里
  没有它、`skill` 工具也拒绝它（人有一条 `skill` 以外的路：`/name`，见「人也能加载」）。它仍在 `scan`
  里可见并注明原因，因为「文件在、能力没了、没人说得清为什么」是最坏的形态。
- **`allowed-tools` 刻意不信**：工具表由会话与编辑模式决定，不让一个技能文件给自己扩权。

## 指令：在但读不出来是命名失败

- **默认位置**：`<OS 家目录>/AGENTS.md`，绑定项目时再加 `<项目>/AGENTS.md`。同一次会话里两份都在时，
  全局的在先、项目的在后。
- **两种失败，两种政策，分开是刻意的**：
  - **不在**、**是目录**、**只有空白** → 跳过（`:missing` / `:not-a-file` / `:empty`）。三者都是日常
    ——多数项目没有 AGENTS.md，占位文件什么都没说——都不值得为它停一次 run。
  - **在但读不出来**（权限、非 UTF-8）→ **指名失败**，带上绝对路径，run 不开始。它是这场会话自己的
    配置，与 `config.edn` / `harness.edn` 同一族；静默跳过等于让会话按一套**没人写过的规矩**在跑，
    而这是一场会话唯一绝不能默认做的事。
- 解码是**严格 UTF-8**，畸形字节是失败而不是替换字符：`slurp` 的默认解码器会把 U+FFFD 塞进一个二进制
  文件，然后把一套没人写过的指令交给模型——那比不启动更坏。
- `instruction-files` 回答的是**该看哪里**，不是**那里有什么**：它不过滤不存在的文件，因为「读」是
  `gather` 的事。这条拆分正是「缺文件安静、读不动大声」得以成立的原因。

## 技能正文是派生的，不是累积的

一条纯函数：provider 形状的消息向量 → 同样的向量（`harness.cap.skills/derived-injections`）。它扫出
assistant 消息里名为 `skill` 的 `tool_calls`，按 `tool_call_id` 配对它的工具结果，**结果是那句加载确认**
时，在**历史末尾**追加 `<skill name="X">…</skill>` 的 user 消息。

**为什么是派生的。** 参考实现（applepi）的服务端自己持有会话，所以它的工具能把注入物 `push` 进历史；
本仓反过来——**对话归客户端所有，服务端每轮现收现算**。存服务端内存则刷新即失，发给客户端则前端会
把它画出来。于是只剩一条路：每轮从会话自身重算。两条性质因此免费：

- **幂等**：把它施加在自己的输出上不改变任何东西（正文已在原位），所以**每轮施加不需要任何簿记**。
- **同名只注一次**：一个技能加载两次只贡献一份正文——加载它是为了拿到指令，拿两份只花上下文。

**同一句话，「加载」有两个来源，而这是刻意的：**

| 谁在加载 | 怎么看出来 | 正文插在哪 |
|---|---|---|
| 模型 | assistant 消息里名为 `skill` 的 `tool_calls`，配上那句**加载确认** | 历史末尾（追加） |
| 人 | 一条 user 消息**以 `/name ` 开头**（见「人也能加载」） | 历史末尾（追加，与上一条同一个位置） |

两条都不是「被记住的」：`/name` 是人打出来的字，tool call 与它的结果在客户端手里，所以两条**下一次施加
时都还在**——这正是「派生而非累积」在这里的用处。而**只认一个来源的地方只有一处**：`load-confirmations`
的判据是 `loaded-prefix` 那句前缀，工具写、它读，共用一份常量。被否决、被禁用、缺参数的调用根本到不了
工具体，也就从不写下这句话——而在别处重建那个事实，等于用第二个地方、从日志里重新推导「到底发生了什么」。

**施加点在 `harness.kernel.loop/drive!`：每次 `llm/stream!` 之前对 history 施加一次。** 不放在 `ag_ui/inbound`
——模型调用 `skill` 就是为了**现在**照着做，人打 `/name` 更是为了**这条消息**，等下一轮等于白调；
幂等让「每轮施加」不需要任何簿记。**施加之后新加的那几条会说出去**：内核在一个 `swap-vals!` 里拿到前后
两份历史，尾巴上多出来的每条发一个 `:context/injected` 事件，边把它转成 `CUSTOM` 帧——「模型被交给了什么、
它自己没要」这件事从此不再沉默（见下）。

**正文从根现读**（每轮现解析），与 config.edn / harness.edn 同一条纪律：改一份技能，
下一轮就生效。代价写清楚：**正文因此不冻结在会话里**——技能在会话中途从根里消失时，注入位换成一句
点名说明（「没有叫 X 的技能在任何根里……它读不到，也不该被假定」），**绝不静默少一段指令**。
一个**打错的**名字拿到同一句话：什么都没加载，和加载到一个「无话可说」的技能，不能长得一样。

## 人也能加载：`/name`

模型有 `skill` 工具，人有**输入框**：一条消息以 `/name `（名字后面跟空白，或消息到此为止）开头，
harness 就把那份正文加载进来——**同一个派生、同一个 `<skill name="…">` 的 user 消息**，
追加在**历史末尾**。两条路唯一的差别写在下面（`disable-model-invocation`）。

- **触发形状是严的**：`/` 在**消息开头**，名字后**必须有分隔**。所以 `/alpha/beta` 是路径、
  `see /alpha` 是一句关于技能的话、`/alphax` 是另一个（大概不存在的）名字，而不是 `alpha` 的前缀匹配。
  名字的字符集与 frontmatter 的键一样——那是目录列举能产出的字符集。
- **人打的字一个字不改，`/name` 留在原地。** 这是选择不是疏忽：模型读到的「这个人说的话」就是他打的字，
  而正文作为**另一条消息**跟在后面。代价是一行上下文；换来的是**可重复读**——一个必须被剥掉才能识别的
  触发词，需要一个地方记住「它已经被剥掉了」，而这里没有那个地方（对话归客户端）。
- **打错了不是失败**：名字不在任何根里、或那份技能坏了，注入位换成一句**点名说明**——说出收到的名字、
  为什么、以及**本会话能加载哪些**。run 照常继续。这和「AGENTS.md 在但读不出来就停 run」是两条纪律：
  一个名字打错是日常，一份指令读不出来是配置坏了。
- **图片不挡路**：消息可以既带图又带 `/name`（content 是 parts），触发词从**文本部分**里读，
  所以那条消息照旧算数。
- **前端零改动**：人打的字本来就在客户端手里、本来就在 wire 上；harness 加的是服务端那一侧的正文。
  （唯一的例外是**技能列表**——那份菜单是前端画的，见下面一节；它画的也只是这份清单的呈现，
  协议侧仍然一个字节没动。）

## 技能列表：`/` 在输入框里弹出的那份菜单

`/name` 一直是人的加载路径，而**名字只能靠背**——页面上没有任何一份目录。技能列表补的就是这一截：
输入框里打 `/`，弹出一张**平铺的表**：每行是名字、它所在的**层**（`System` / `Project`）与一句描述；
选中一行，输入框里就是 `/名字 `，后面照旧由人接着写。

- **数据只有服务端有，所以由服务端回答**：`GET /api/skills?threadId=…`（只读，**不留痕**——
  与 `/api/model`、`/api/choices` 同一条纪律）。答的是 `{:groups [{:layer :system :root "…" :skills […]}]}`：
  每组是**一个根**，按先后顺序（系统级在前），**空的组不出现**；每行是 `:name` / `:description` /
  `:available?` / `:reason`。哪几个根、同名谁赢、坏技能为什么坏——这些答案只在 `harness.cap.skills` 有一份，
  前端复刻一遍就是第二份会漂移的答案。
- **层跟着根走**：`harness.cap.skills/root-layers` 在**造出默认根的那一处**给它们贴上 `:system` / `:project`，
  `harness.cap.project/skill-layers` 做配置与绑定的配对（`skill-roots` 就是它丢掉层的结果，默认只写一次）。
  **配置里 `:skills {:roots …}` 写的根没有层**——配置表里没有「系统 / 项目」这回事，从列表位置猜一个
  就是把猜测写成事实，所以那些行不画徽标，只把根路径放在 `title` 里。**插件级将来是这里多加一项**，
  不是前端多一个分支。
- **列表是「人能加载的」，不是「模型能用的」**，两处与清单**故意不同**：
  `disable-model-invocation: true` 的**在**（文件说的是模型不该自己决定去用，人打 `/name` 就是人在决定，
  服务端放行），**坏技能也在**——带原因、但**不可选**（它不在可选条目里，所以方向键与 Enter 都够不到它）。
  这一条是既有纪律在界面上的样子：一个静默消失的技能，与一个从没装过的技能，从外部看没有区别。
- **同名被盖住的那份不在表里**：它加载不动，而 `scan` 已经回答了那个名字归谁——列出输家是对一个
  已经有答案的问题再答一次。
- **选中不发送**：写进输入框的逐字是 `/名字 `（尾随空格是服务端触发形状要求的那个分隔），
  后面那句话由人写。触发形状与 `slash-pattern` **同一形状**：只在**消息开头**，且名字后面还没有空白——
  所以 `see /alpha` 不弹（服务端不会加载它，菜单不该提供一个做不到的动作）。
- **它站在上游的触发面板上**（`ComposerPrimitive.Unstable_TriggerPopover*`，见
  [client](client.md#技能列表输入框里打--弹出的那份菜单)）：弹层、键盘、combobox 的 ARIA 全归上游，
  本仓写的是「名字从哪来」「哪些能选」「一行画什么」。抄进来的 12 份元素**一行未改**。
- **它只做技能**：命令与子智能体在本仓**不存在**（没有可列的东西）；插件级是上面那条多加一项的事。

## `skill` 工具

一个参数 `{"name"}`，成功时答一句**关于会话**的话（不是关于这次调用）：

```
[skill-loaded] <name> is now in this conversation and stays available for the rest of
the session (<N> chars). Follow it unless a later instruction supersedes it.
```

- 定位**只按清单里的名字查表，从不拼路径**。
- 未知名字 → **指名拒绝**，说出收到的名字与本会话能用的名字（沿用
  `harness.cap.providers` 那句 "no provider named X; the registry defines …" 的形状）。
- 坏技能 → 指名拒绝，带 `:reason` 与它的 `:path`。
- **`disable-model-invocation: true` 的技能被拒绝**——这条是两条加载路径**唯一**的不同：
  文件自己说这条不该由模型决定去用，所以模型侧拒绝、人侧放行（人打 `/name` 就是人在决定）。
  在 `/name` 出现之前，这个标志只做到「清单里不列」，而那**是藏不是拒**——猜中名字照样加载得动；
  现在猜测会被指名拒绝，拒绝的话还说出人可以用哪条路拿到它。
- **不标 `:requires-approval`**：读一份指令不是副作用，而正文里让人做的事，各自过各自那道缝
  （围栏、工具自己的 `:requires-approval`）。给读指令加门，比它描述的动作还难拿到，是反的。
- 清单**不在工具的 schema 里重复**：schema 是每次调用的请求的一部分，把一份会话级的清单塞进去，
  会让它因为一个与工具形状无关的原因在会话之间不同。

## `InstructionsLoaded` 接线

27 个 hook 点里**已接线的第六个**（第七个是 `SystemPrompt`，它管另一半）。每折叠**一个**指令文件触发一次，
观察者（`:gate? false`），verdict 丢弃；**被跳过的文件不触发**——什么都没被折叠，为一个没发生的事
宣告一次 hook 比没有更坏。

这个点自 hook 引擎落地起就声明着（`payload #{:path}`，"an instruction file is folded into the run's
context"），一直没有触发源；**本特征就是它的子系统**。

**实现上有一条不改就会静默失效的约束**：run 作用域的 sink 由 http 边 binding，而折叠发生在第一条消息
组装**之前**，所以那个 `binding` 必须**包住 set-up**，不能只包住 run。否则 `hook/emit` 拿到 nil sink，
这个点永远静默——而「一个声明了却永不触发的点」比没有这个点更难查。

## 配置：`:skills` 与 `:instructions`

两个键都在 `harness.edn`（用户级 `~/.clj-harness/harness.edn`，项目级 `<项目>/.harness/harness.edn`）：

```edn
{:skills       {:roots ["/abs/path/to/skills" "relative/to/project"]}
 :instructions {:files ["/abs/AGENTS.md" "docs/AGENTS.md"]}}
```

- **整表替换该半边的默认值**（不是追加），所以「只要项目那一份」写 `["AGENTS.md"]` 就够，
  用户级那两处整个退出画面。空向量 `[]` 被接受且意思就是「什么都不读」——否则「我都不要」只能靠指向一个
  不存在的路径来表达。
- **相对路径按工具路径的规矩解析**（绑定项目时相对项目根，绝对路径直通），因为写它的人期望的是同一条规则。
- **段本身必须是 map**：`{:skills 42}` 在问它要 `:roots` **之前**就指名失败。`contains?` 撞上非 map 会抛
  一句既不说键也不说文件的 JVM 错误，而一个读者定位不到的配置错误正是这套纪律要消灭的东西；
  失败信息说出收到的值、该写成什么、以及去哪个文件改。
- 顶层仍是**整键替换**（与 `:approval` 同一条纪律），键**内部**才按键合并——`{:skills {:auto-read false}}`
  这种半份写法在 `:skills` 里合法，在顶层则不是。
- **用户级那两处取 OS 家目录，不跟随 `CLJ_HARNESS_HOME`**：它们与 ZCode / Claude 读的是同一份文件，
  是**宿主的**约定位置，不是 harness 的配置家目录；把配置家目录挪到别处不该让另一批技能凭空消失。
  `harness.infra.home/user-home` 因此是**第二层 floor**，与 `root` 互为兄弟而非嵌套，且各自一条测试缝
  （`*user-home-override*`）。嵌套会让 OS 家目录落进围栏的允许集——那恰好是围栏测试要问的问题，
  安排本身就会替它回答。

## 与围栏的关系

**技能根在允许集里，指令文件的内容不在。** 技能正文常写「读 `references/x.md`」，那个路径就落在技能
目录里、项目目录之外——不放行的话每读一份参考文件都要人点一次批准，技能等于白装。技能根因此与配置家
同级，`:approval {:strict true}` 也**收不走**（strict 收的是项目目录那条）。

**反过来，一份 AGENTS.md 里提到的路径照常停泊。** 允许的是「配置里说过的根」，不是「某份文档说可以读
的东西」——文档能给自己扩权是另一套安全故事，不是这次的范围。指令文件本身也**不经过围栏**：
它们是服务端读的，不是 `read` 工具调的。

## 看得见，但仍然不是会话的一部分

**2026-09-18 起注入物会以 AG-UI 帧出去**——这一页原先写的是「从不产生任何 AG-UI 帧」，那天起不再成立。
一条注入 = 内核的 `:context/injected` 事件 = 一条 **`CUSTOM` 帧**（`name` 是 `injected-context`，值里是那条消息，
`messageId` 是我们给的确定性 id），客户端把它画成**会话栏里一张可折叠的卡**
（见 [client](client.md#注入物在会话栏里的一张卡)）。**但客户端不回发它**：适配器把 `CUSTOM` 落成一个 `data` part，
而它的回发转换只带 text / reasoning / tool-call ——所以**它仍然不是会话的一部分**，模型下一轮收到的历史与
从前逐字节相同。这条契约由用例钉住（`ui/test/suites/injections.ts` 第三条；适配器升级时第一个要看的就是它）。

**立场没被推翻，只是被说准了**：注入物不在对话里——改的是「因此人也看不见它」这半句。

**那几块拼在哪**：`ag_ui/inbound` 的 4-arity 把开场块拼在**客户端消息之后**（空块时返回原向量本身，不是
等价的一个新向量——那是「什么都没配的会话与从前逐字节相同」这条回归保证的形状）。发帧的是**边**：块在它
手里组装、走的也是它的 sink，内核从没见过它们是「它加的」。这个函数仍是个转换器：块是递进来的，它自己
不读任何东西。

`InstructionsLoaded` 走既有的 `hook/<Point>` 审计行；**不新增 jsonl 行种类、不改 AG-UI 帧形状、不动 CORS**。

**注入物本身照旧写进 jsonl 的 `message` 行**——包括指令文件与技能清单。这一条按字面执行
「模型看到了什么，日志就有什么」：`log-messages!` 记的是整个入站向量，清单是它的一部分，
所以清单也在日志里。（`.scratch/skills-and-instructions/spec.md` 决策 14 里「清单不进日志」那句
与它同一条决策的前半句自相矛盾，以这里为准——那是历史文档，不改。）

## 自省

`harness.cap.preamble/report` 回答「这次 run 开场拿到了什么」：每块的来源与**字符数**、以及被跳过的东西和
原因。字符数记的是**真正注入的文本的长度**，不是文件的字节数——模型付的是交给它的文本，被 trim 掉的
空白没交给它。什么都不截断，正是这个数字值得报出来的原因。

**它今天没有端点**：`GET /api/settings`（只读的生效配置）覆盖的是 provider/家目录那一片，技能与指令
这一片只有 `scan` / `report` 两个函数——用 `eval` 就能问，界面与 HTTP 边都还没有接。
