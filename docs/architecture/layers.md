# 四层

`src/harness/` 分四层。这一篇回答三个问题：**怎么判**（一个命名空间该在哪一层）、
**边界在哪**（谁可以 require 谁）、**能力怎么进核心**（核心层不认识能力，那它们怎么接上）。
归属表按层列在 [模块地图](../architecture.md#模块地图) 里，这里只讲规则与理由。

这套分层不是目录美化：2026-09-16 之前它是扁平的 33 个命名空间，而**依赖方向是乱的**——
核心层的 `tools` / `loop` / `editing` 反过来 require 能力层。分层把那些反边**一条不剩地**断掉了，
13 条变 0 条，而且有一位守卫测试（`harness.layers-test`）看着它们。

## 判据

| 层 | 前缀 | 是什么 | 一句话判据 |
|---|---|---|---|
| 基建 | `harness.infra` | 东西落在哪、错了写哪、进程怎么起来 | 与「这个 harness 会做什么」无关，换个产品也照样需要 |
| 核心 | `harness.kernel` | **只提供机制，不提供能力** | 说得清「怎么做」，说不清「做什么」 |
| 能力 | `harness.cap` | 这个 harness 具体会做的事 | 说得出「它会做什么」，去掉它 harness 就少一样能力 |
| 适配 | `harness.edge` | 对接前后端：AG-UI 帧、HTTP 边、日志记录 | 把内核翻译成别人的协议 |

判据要能用一次，不是每次凭感觉：**删掉它，内核还转不转？** 删掉一个能力，内核照转，只是少做一件事
——删光 `cap.tools` 的内建表，循环仍然流式、仍然调 provider，只是工具表空了。
删掉一个机制，内核自己的部件就散了。

## 允许的边

```
infra    → infra
kernel   → infra, kernel
cap      → infra, kernel, cap
edge     → infra, kernel, cap, edge
test/dev → 任意
```

**核心层不 require 能力层。** `harness.layers-test` 的三条断言就是这张表加上两条格式规则：

1. **每个命名空间都在一层里**。`src/harness/` 下新建一个平铺文件会立刻失败，而不是等谁想起来。
   唯一的例外是 `harness.user`：它在进程里被 `create-ns` 出来，没有文件。
2. **没有一条向上的 require**。失败信息里带着「谁 require 了谁」和那一层为什么不能要求上面。
3. **路径与命名空间名一致**，`src/` 与 `test/` 都查。这是 Clojure 的硬规矩，而它坏起来很安静：
   一次改名会顺手把**名字开头恰好是某个被搬走的命名空间**的另一个命名空间也改了名
   （这次搬 hook 引擎时就发生过一次），于是文件和名字对不上，而**没人 require 它之前什么都看不出来**。

**守卫测试看不见什么，也要写下来**：它查 **require**，不查**内容**。
一个不 require 任何能力、却在字符串里写死某个能力名的命名空间，它能绿。
这不是假设——这次分层里真发生过（核心层里残留过 `"anchor_grep"` 这样的工具名），
抓住它的是人眼 grep，不是测试。所以这条规则靠人守着，测试只钉住能机械钉住的那一半。

## 能力怎么进核心

核心层不认识能力，那它们怎么接上？两样手段，**按优先级**，不许颠倒：

1. **参数（首选）**——能力把事实算出来交给核心。
   例：每轮 LLM 前的技能注入是 `run-chan` 的 `:before-llm`，由边传进去；
   工具按编辑模式换脸、批的算术，都发生在能力层自己内部，连核心都不过。
2. **安装（install）**——参数到不了的地方才用它：缝在并发里被叫（`specs` / `run!` /
   `declarations-at`），没有参数位可传。由**组合根在 setup 时**把能力装进核心层留的一道门。

### 安装门的形状

```
(install! {...贡献表...})  →  teardown    ; 一个无参函数，撤掉自己装的那一层
```

`harness.kernel.tools/install!` 与 `harness.kernel.hooks/install!` 是同一道门，四条约束也一样：

1. **同名后者覆盖前者**。要换一个实现不必先卸载。
2. **禁用不是删除**。指名禁用一个名字，它**仍在表里**、仍被模型看见，只是执行被拒、
   并说明是被谁禁的（层自带 `:name`，拒绝语里说得出）。`CONTEXT.md` 的 `工具表` 那条已经写死了
   这条规矩，安装机制必须服从它。
3. **`teardown` 撤自己那一层，并还原下面那层**。注册表按层记账，卸载弹出自己写过的那一层，
   而不是「把这个名字删掉」。否则「A 装了 X，B 覆盖了 X，A 先卸载」会把 B 的 X 一起带走——
   卸载顺序于是变成 load-bearing。`harness.kernel.install-test` 与
   `harness.kernel.hooks.install-test` 各有一条测试钉着它。
4. **`teardown` 的真正消费者是测试**，不是生产：生产路径上它只在进程收尾时用得到
   （`edge.http/start!` 返回的 stop 里就带着它），而测试靠它拿回一个干净的缝。

**不采用「require 即注册」**（加载一个命名空间就产生副作用）。它把「装了什么」变成隐式的：
一个测试凭什么有内建工具，答案会是「因为别的某个命名空间 require 过它」。setup 时显式装上，
答案就在 setup 那一行。这次分层把最后两处这样的副作用也清掉了：内核自己那两条 `SystemPrompt` 行
过去是 `cap.system-prompt` 被**加载**时顺手注册的，现在由它的 `install!` 装上。

### 装完之后的三条后果

都是实测踩出来的，写下来省得下一个人重新踩：

- **缝在没装东西时是空的**，而且答案是「unknown tool」而不是「disabled」——前者叫模型去别处找，
  后者叫它以为这个能力存在但被关了。这两句话对模型是不同的指令。
- **会话开关只对表里已经有的名字生效**，所以**测试里改开关一律放在安装之后**：
  `session-disable!` 的守卫是「这个名字我看得见才记这笔」（它保证「禁用不会凭空造出一个工具」），
  在能力装上之前禁用等于什么也没禁，而且不报错。
- **组合根的 `stop` 必须带回 teardown**，否则测试套件里每起一次服务就叠一层
  （http_test 起上百个），而「缝是空的」那条断言就会看到别人留下的表。

## 几处边界判断，连着反面意见

写在这里是因为守卫测试抓不到它们，将来翻案只能靠这张纸。

- **`llm` 里的 `prompt.md` 载体留核心层**：冻结是机制（provider 前缀缓存的前提：一条逐字节稳定的
  首消息），读哪个文件不是能力。
- **`cap.tools` 与 `kernel.tools` 的分界线是「定义」与「缝」**：十六个工具的描述、参数与 `:run`
  在能力层，注册表、overlay、审批、三相执行、声明的词汇在核心层。缝曾经两者都装
  （一份 1320 行的文件），分开之后它的 docstring 才能说一句真话：它不认识任何一个具体工具。
- **`cap.editing` 是能力，核心层没有 `editing`**：`:hashline` / `:str-replace` 是两套具体编辑实现的
  **名字**，名字就是能力。核心层只要「一张表可以被一条装进来的策略**收窄**，收窄的表现是
  **拒绝**而不是消失」这个机制。**第一版曾把模式表留在核心层**，理由是「工具表这个机制在核心层」
  ——那条理由把**一张表**与**这张表的账**混为一谈。
- **hook 引擎留核心层，只有来源是能力**：`cap.hooks` 负责读哪两个文件、怎么两级浅合并；
  点表、声明契约、来源档位与排序、引擎本身都在核心层。
  **反面意见**：引擎能「无声明即不可见」地缺席，那正是**槽**的样子；而内核控制流真正被 hook
  **改道**的地方只有 `tools/run!` 一处（`loop` 的 `:stop` 是观察者，判决被丢掉）。
  **留下的理由**：`tools/run!` 三个出口里「阻断」的命名来源之一就是 `PreToolUse` 的退出 2，
  「悬置」的应答者之一是 `PermissionRequest`，而 [overview](overview.md#三条铁律) 的**铁律 2**
  （「system 消息只有一条，它的开头冻结，hook 追加其后」）把 hook 写进了内核的定义里——
  铁律是「每一处设计都能追到它们之一」的那种东西。**翻案路径**：整个 `hooks` 进 `cap`，
  核心层收两个装进来的 handler；代价是上面那两条。
- **`replay` 在适配层，不是独立一层**：它是边的日志的**读侧**，与写侧是同一份契约的两半。
- **`providers` 在能力层而不是基建层**：它是「能跟哪个厂商说话」；基建层只有「东西落在哪、
  错了写哪、进程怎么起来」。
