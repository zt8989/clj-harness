# 06 — 命令与技能同名：拒绝而不是猜

**What to build:** `/foo` 只有一个意思。当同一个会话里 `foo` 既是一条命令又是一个技能的名字，
这一处**不猜**：那一条不进可选行、带原因、选不动；打 `/foo` 得到一句点名说明——说出这个名字下
有两种东西、以及各自的根。

理由是既有的那条：从外部看，一个静默挑了一个的解释，与一个从没装过的解释没有区别，
而后者难查得多。

**这一票是「一个接口答两样」的直接产物**：冲突只在两样东西**同时**被读出来时才看得见，
所以它只能长在 `GET /api/picks` 这一份合并答案上（见 01）——两条各自独立的只读路由
永远发现不了对方占了同一个名字。

**Blocked by:** 01、02

**Status:** ready-for-agent

- [ ] 同名冲突报成一条**诊断**（带名字、两种来源的根、各自的可用性），不是静默取一个。
- [ ] 冲突时 `/foo` 不加载任何东西，run 照常继续——与「名字打错」同一档，不与
      「AGENTS.md 读不出来」同档。
- [ ] 冲突只在**生效的名字**之间判定：被前面的根盖住的那份本来就不参与，所以它不制造冲突。
- [ ] 四种可用性组合（命令好/坏 × 技能好/坏）都有确定行为，且各有测试。两个都坏也仍是一句话，
      不是两句。
- [ ] 这一条**只在「两种东西抢一个名字」时成立**：技能之间、命令之间的同名，仍旧是
      「前面的根赢」那一条既有纪律，不是诊断。
- [ ] **`/api/picks` 的每一行因此多一个「它是哪一样」的字段**（技能还是命令）——菜单要按它画，
      而冲突行两样都不是，它的 `:available? false` 与 `:reason` 说清这一点。
