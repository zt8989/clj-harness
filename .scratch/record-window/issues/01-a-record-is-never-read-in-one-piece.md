# 01 — 一份记录永远不要一次读完

**Status:** ready-for-agent
**Blocked by:** None

**要做的**：把"从某个字节偏移读到文件尾"改成**按有界块循环读**，两处各一份：
`harness.edge.replay/rows-after`（窗口的冷游标与投影都用它）与
`harness.edge.projection/new-rows`。每轮最多读 **4 MB**，块边界取到该块内**最后一个换行**，
剩下的留给下一轮；读到文件尾为止。

**为什么（2026-09-30 实测，pid 6116）**：

| 情形 | 代价 |
|---|---|
| COLD：从 0 读到 15.0 MB / 46754 行的记录尾 | **432–772 ms，一次性 15MB `byte[]` + 一份同尺寸 `String` + 46754 行**（瞬时约 45 MB） |
| WARM：没有新字节 | 0.07 ms |
| 一次真实 tick（现场那场会话） | 0.06 ms / 0 新字节 |

触发时机是**每次 run 一次**（窗口的冷游标）与**每条记录到被投影为止一次**（投影），
不是每 tick——所以这不是热路径问题，而是**峰值**问题：清掉那批归档会话之前，本机最大的记录是
**124 MB**，那样一次冷读就是 124 MB 的 `byte[]` 加 124 MB 的 `String`（约 370 MB 瞬时）。
记录只增不减，所以这个形状会随记录长大而变糟。

**为什么分块是安全的**：entries 的折本来就是增量的（`replay/entries-fold` /
`entries-of-fold`），而块边界只落在换行上——所以"分块读"与"整份读"给出的是**同一批行、
同一个行号**，逐条相同。这一点不需要新的论证，只需要一条用例。

**要守的既有规矩**（`rows-after` 的 docstring 里写着，别弄丢）：

- 偏移只越过换行；半个尾行不是行，留给下一轮，**不丢**；
- 一个完整的行解析不了就**停在它前面**（偏移停在它开头），下一轮重试；中间的行按名字硬失败；
- 行号要同时维护"行数"与"行序号"两个计数（旧契约的 `input` 行会产生多行）。

**验收**：

- `harness.edge.replay-test` 加一条：同一份文件"按小块的阈值读"与"一次读完"得到**逐条相同**的行
  与偏移。阈值要能被测试绑小（别在实现里写死 4 MB，否则这条用例只能跑真货）；
- 现有两条（分两段折 == 整份折；半行不算一行）保持绿；`harness.edge.projection-test` 保持绿；
- 在活进程里量一次 COLD：峰值不再随文件大小线性增长（`byte[]` 封顶在块大小）。
