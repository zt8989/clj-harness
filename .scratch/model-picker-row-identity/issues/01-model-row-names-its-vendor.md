# 01 — 模型选择器的一行由「厂商 + model」共同命名

**What to build:** composer 的模型选择器里，一行不再只由 model id 代表 —— 它由**厂商 + id**这一对命名。于是：

- 同一个 model id 被两家厂商声明时，菜单里就是**两行**，各自骑在自己厂商的标题下，彼此不是同一行；
- 点哪一行，发给服务端的 `provider` 就是那一行标题写的厂商、`model` 是那个 id；
- 本会话此刻被服务的那一对（厂商 + id）高亮在**它自己**那一行上，而不是目录里第一个声明这个 id 的厂商那一行。

**为什么是这个形状。** 今天的选择器把一行的身份交给 model id，厂商只活在分组标题里，点选时再靠
「目录里第一个声明这个 id 的厂商」反推厂商。可 id 撞车是配置里一种真实存在的状态 —— 例如
`qwen` 与 `workbuddy` 都声明 `deepseek-v4.1-flash`，于是点 workbuddy 标题下那行，发出去的却是
`qwen`（目录按名字排序，`q` 在 `w` 前）。同一个身份假设还让两行共用同一个身份：它们会被画成
**同时选中**，键盘高亮也串在一起。厂商标题下的一行本来就是「这家厂商的这个 id」，把它当
「id」用是把已经在手里的另一半丢了。

**Non-goals（都是已经决定不做的）：**

- **触发按钮的文本不变**：仍然只写 model id，厂商仍旧只在 hover 的 title 里（`厂商 / model`）；
  「id 不撞车也把厂商画上去」不在这一票里。
- **`/api/choices`（以及 `POST /api/model`）的形状不动**：厂商与它声明的 model 表已经在答案里，
  缺的只是客户端把它当成一行的身份。服务端不该为这个改动。
- 不动「有密钥的厂商才被展示」那条规则，也不动搜索同时匹配标题与 id 的既有行为。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

      身份（不会互相冒充「当前选中」，键盘高亮/移动也不串行）。

      不是目录里第一个声明这个 id 的厂商。撞车时点另一家的同名行，送出的就是另一家。
