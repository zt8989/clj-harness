# 03 — 窗口的相等判断先比便宜指纹，只在看起来相同时才 `JSON.stringify`

**做什么**

`ui/src/lib/window.ts:91` 的 `sameEntry` 是 `a.seq === b.seq && JSON.stringify(a.message) === JSON.stringify(b.message)`，
而它是在**每一条已持有的条目**上被调的（`merged` 里按 id 命中就比一次）。半写状态每帧把整条答复重发
一次（`replay/entries` 的折叠就是这么写明在 `merged` 的注释里的），两边各一次全量序列化 ⇒ 跟着答复长度
平方增长。改成两级比较。

**做法**

1. 先比**便宜指纹**：`role`、parts 数、每个 part 的 `type` 与 `text.length`（缺字段、非对象一律给 `null`
   —— wire 上的 message 是 `unknown`，防御是必须的，不是客气）。
2. 指纹不同 ⇒ 直接判「是新版本」；**相同**才落回今天的 `JSON.stringify` 逐字节比较（这条是罕见路径，
   不在热路上）。
3. 指纹是一个**纯函数**、单独一个模块（照 `reasoning-preview.ts` 的形状），这样它能被套件直接测；
   比较这个动作本身要**可数**（序列化器注入或包一层），否则「有没有真的省掉序列化」只能靠读代码。

**Blocked by:** None

**Status:** ready-for-agent

- [ ] 纯函数用例：只有文本变长的一对判「不同」；逐字节相同的一对判「相同」；`null` / 少字段 / 非对象的
      message 不抛（并且不能被误判成「相同」——误判成相同会让正在写的答复**冻住**，这是这个函数唯一
      真正危险的方向，用例要专门钉它）。
- [ ] `ui/test/suites/window.tsx` 现有用例全绿，尤其「一条在写的答复按 id 就地替换、光标不前进」那条。
- [ ] 一条按**字符数**判的判据：一帧重发 N 条条目时，被完整序列化的字符数只与「真的变了的条目」成正比，
      不与整场的字节成正比（靠第 3 点那个可数的序列化器断言，不靠耗时）。
- [ ] 现场数字进 `evidence/`：一场长答复在跑的会话（观看另一进程），一帧 `applied` 前后的耗时 before/after 同表。
