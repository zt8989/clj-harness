# 02 — 原位的送达：能力位与那条 `developer` 消息

**What to build:** 模型条目新增 `:instruction-updates`（`:in-place` / `:replace`，缺省 `:replace`）。
标成 `:in-place` 的端点上，01 说「变了」时：请求体里 `message[0]` **保持上一轮那份的字节**，把新的
指令全文作为**一条 `developer` 消息**插在**新提问之前**。变化累积成链，后说的覆盖先说的。

「自动获取模型列表时按内置前缀预填」是票 04 的事（决策 8）：那是**写文件前**的一次建议，不参与这里
的解析——别把那张家表接到 `selection` 或送达那一处。

**Blocked by:** 01

**Status:** ready-for-agent

## 要落地的判断

1. **能力位是模型条目的键**，不是 provider 条目的：同一家 vendor 的不同模型可以两边都有。加进
   `cap/providers.clj:114` 的 `model-keys`（**闭集**——加了才行，写别的键仍然按名字拒绝），并让
   `resolved-fields`（`:127`）带上它，这样「这个会话是怎么被送出去的」是一句答得出来的话。
   取值两个，缺省 `:replace`；**保守的方向是有理由的**：不声明 ⇒ 一次冷前缀（可接受的坏结果）；
   错发一条 vendor 不认的消息 ⇒ **整个 run 起不来**（`llm.clj:296` 只有 `:openai-completions`
   一种实现）。
2. **role 用 `developer`**：Chat Completions 那一族里它就是「对话中途仍然带着指令分量」的写法。
   写成一个**具名常量**、在一处拼出来——不要把这个字符串散落在请求构造里（散开就没有一处能回答
   「我们到底发没发过这种消息」）。
3. **位置**：`system → 历史 → developer 更新 → 新提问 → context → skill_context`。拼接点是
   `edge/ag_ui.clj` 的 `inbound`（`:369`）——它今天已经有两个位置：`after-system`（`:355`，开场块）
   与尾随的 context 消息。新位置是**第三个**，插在客户端消息里**最后一条 user 消息之前**。
   - 客户端消息里最后一条**不是** user（病态历史）⇒ **不插**，退回 `:replace` 那一档并记一行。
     不猜。
   - 位置的理由：更新是**提问的前提**，所以在新提问之前；context 与技能正文是**为提问准备的料**，
     在之后（`.scratch/context-frames/issues/05`，在飞）。
4. **送全文，不送差量**：厂商的指令槽是**覆盖**语义。一条只带差量的消息把「合并」丢给读的人，还要
   为「差量」再造一套算法——那是第二个真相源。一条消息一个事实。
5. **链要每轮重送**：客户端**不持有**它（它不在客户端的历史里，也不会被回发），所以每一轮都要把
   当前整条链插回去，按发生顺序排列。
6. **重送的代价说清楚**：链落在尾部，而尾部每轮本来就要重算。**共享前缀 = system + 客户端每轮重述
   的历史**，它整段留在缓存里——这正是与 `:replace` 的差别：`:replace` 让整场对话从 token 0 重算。
   这句话要写在拼装处的 docstring 里，别让它只活在这张票上。
7. **在记录该看到它的那一次拼好**：新拼出来的消息向量就是 `message` 行 submitted 侧的来源
   （`edge/http.clj:841` 前后那一段注释说明两半按什么分），所以链要在**那一次**拼完，不是在
   `llm/stream!` 里临时加——后者会让记录与实际送出的东西不一致。
8. **报告与解析各说各的那半句话**（设置页靠这个分档，票 04）：`registry-report` 的 `model-row`
   （`providers.clj:1531`）**只在该模型自己写过这个键时带上它**——与那两个计数「有才带」同一条写法。
   而 `selection` 出来的那份选择**一定**带值，缺省补 `:replace`。报告填了缺省，设置页就再也分不出
   「没说」与「说了 `replace`」，一次无关的保存会把每一行都改一遍；解析不补缺省，送达那一处就得自己
   认缺省，那是第二个主人。
9. **值也是闭集，别的按名字拒**：`:in-place` / `:replace` 之外的值在 `check-model` 里失败并点名
   （`unknown-keys!` 管的是**键**，值另有一条）。静默退化成 `:replace` 的代价不是错误，是**一次没人
   注意的冷前缀**——写错一个名字的人会以为它生效了。

## 验收

- [ ] 目录里一个端点标成 `:in-place` → 加/删一个工具（或加/删一条 hook）：`message[0]` 与上一轮**逐字节相同**（用例断言
      字符串相等，不是断言「非空」）
- [ ] 多出**恰好一条** `developer` 消息，内容是**新的指令全文**，位置在最后一条 user 消息之前
- [ ] 连改两次 → 两条，顺序就是发生的顺序，后一条是当时的全文
- [ ] 什么都没改 → **一条都不多**（与 01 的「没有变化」对上）
- [ ] 最后一条不是 user 的病态历史 → 不插、不猜，走 `:replace` 并记一行（有用例）
- [ ] `:instruction-updates` 写在模型条目上不报错；写别的键仍然按名字拒绝（既有那条用例照旧绿）
- [ ] 写一个不认识的值（比如 `:inplace`）→ 按名字拒绝（有用例）
- [ ] 报告里未声明的模型那一行**不带**这个键；解析出来的选择**一定**带（缺省 `:replace`）（有用例）
- [ ] 不声明这个键的模型**永远**收不到 `developer` 消息（有用例）
