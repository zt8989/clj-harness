# 09 — spill：单条巨型输出挪走，只留一张取货单

**What to build:** 单条**刚产生**的巨型工具结果，在产生的那一刻就挪到别处，只给模型一个**不透明定位
符** + 一句**取回指引**，模型能主动把它取回来（用已有的读工具）；存不下时**保留内联原样**，不把成功
的调用变成错误。定位符**不透明**：消费方只按取回指引渲染，不假定「读文件」始终是正确的取回方式
（后端可能返回 URI 或键）。

第 12 章明确把它与压缩**分开**：它解决的是「**单次输出**就巨大」（一次抓回一个网页、一次匹配几万
行），不是「历史累积得太多」。它也是四档手段里最省事的一档——把「什么时候需要这段内容」的决定权
**还给模型**，而不是替它做决定。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 巨型工具结果在**产生时**被换成一条预览 + 定位符 + 取回指引；模型视图从这一步起就不带那坨大文本
- [ ] 定位符**不透明**：消费方只按取回指引渲染，不假定它一定是文件路径
- [ ] 模型能按指引**取回原文**（走已有的读工具）
- [ ] 本地后端写入是**排他**的（防止有人预先埋一个符号链接把写入重定向走）
- [ ] 保存是**尽力而为**：失败时保留原始内联结果，**不把成功的调用变成 `isError`**
- [ ] 三档分工写清楚：spill 管**单条刚产生的**工具结果，剪枝管**已有的大**工具结果，摘要管**一整段**
      历史；**信封**（system prompt + 工具 schema）三者都不管
- [ ] 端到端：一次巨大的 web 抓取被 spill，压力**从一开始就没上去**
- [ ] 命名不与既有的后台作业 spill（把前台命令整份输出落成一份记记录）混淆，两处在文档里说清各是哪
      一种「spill」
- [ ] 离线全量 `harness.test-runner` 全绿
