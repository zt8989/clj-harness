# 07 — 锁：`end` 一定写在最后，崩了要看得见

**What to build:** 压缩到一半崩掉留下的痕迹必须**看得见**。`start` 在任何异步工作之前同步落盘，
`end` 在所有实际工作之后落盘，于是中途崩溃表现为**「有 `start` 无 `end`」的可检测遗留锁**，而不是
一个虚假声称成功的 `end`。有活动的未配对 `start` 时下一次入口**拒绝**（报 `busy`）；比最近一次
**`session/end-seed`** 还老的 `start` 是陈旧证据、**忽略**；失败的尝试也写 `end`，带错误闭合。

这是可靠性工程里那个反复出现的选择：只能在两种错误里挑一种时，**挑会被发现的那种**——宁可误报
「还在忙」（假阳性，吵、能修），也不要误报「已完成」（假阴性，哑、会烂在那里）。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] `start` 在**任何异步工作之前**同步追加；`end` 在**所有实际工作之后**追加
- [ ] 压缩中途进程死掉，记录里留下「有 `start` 无 `end`」；下一次启动能查出来并**说成「有一次压缩
      没完成」**，而不是无从判断
- [ ] 活动未配对 `start` **阻塞所有压缩入口**（自动与手动都拒，报 `busy`）
- [ ] 比最近一次 `session/end-seed` 还老的未配对 `start` 被当作**陈旧证据忽略**（种子历史里那个开
      括号属于一个已结束的生命周期，边界之后的才是真的还在跑）
- [ ] 失败的尝试也写 `end`，带 `error`：会话内容不变，但这次尝试**在记录里留痕**（失败不是不留痕，
      是留成另一种痕）
- [ ] `end` 都写不进去（持久化坏了）时，锁**卡住**——宁可卡住，也不继续猜自己处在什么状态
- [ ] 端到端：压到一半 kill，重启后下一次压缩**被拒**；再构造一个「陈旧 start」，下一次压缩**照常
      进行**——两种都演示
- [ ] 离线全量 `harness.test-runner` 全绿
