# 05 — 溢出恢复：已经炸了，压得更狠

**What to build:** 厂商**明确以「上下文超限」拒绝**时，认出**这一种**拒绝（与别的失败分开），
绕开常规压力与保留预算做一次更激进的头缩减（只留最近一个不可分单元），然后重试；但**只有模型视图
真的变短了才重试**——这是「进步」的可判定形式，也是防止无限重试循环的那道门。重试有次数上限，
否则把原始错误原样报出去。

这条路径**不需要知道模型容量**：既然厂商已经拒绝，就不需要任何容量元数据来论证该压缩了。
它同时是 01 那张票承认「估算会失准」的兜底——失准是被承认的常态，不是异常。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 提供方以超窗拒绝时被识别为**这一种**（不是所有 400 都算）；别的失败照旧走原来的错误路径，
      错误里厂商的原始说法不被吞掉
- [ ] 这条补救路径不依赖容量元数据（不给 `:context-window` 也能走）
- [ ] 重试判据是「模型视图**真的前进了**」：压缩没能减少任何东西时**不重试**，把原始错误原样交出
- [ ] 重试次数封顶（默认 1，可配 `0` 完全禁用）
- [ ] 剪枝已落地、后续摘要失败时，只要模型视图前进过，仍算有资格重试；**取消优先**
- [ ] 恢复发生在**失败步骤结束之后、失败轮次结束之前**：重试接在同一个轮里，用户不会看到一个
      中断又冒出来的新轮
- [ ] 端到端：构造一次超窗拒绝，看它压一次并成功重试；再构造「压不动」，看它**不重试**、报原始错
- [ ] 离线全量 `harness.test-runner` 全绿
