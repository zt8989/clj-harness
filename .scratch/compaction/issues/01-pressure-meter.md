# 01 — 压力表：这一刻的请求有多满

**What to build:** 每个**轮**开始、派生请求之前，能答出「这一刻要发出去的请求离满还有多远」，
并且每次**模型调用**把答案记进**记录**。数从一个真实锚点出发：只要**信封没变**（system prompt、
工具表、路由），就拿厂商上次报回来的 `prompt_tokens` 当基线，启发式只负责算「从那一刻到现在
新增了多少」（4 字符 ≈ 1 token，每条消息的角色字段、每个内容块再各加一点结构开销）。窗口是
目录为这个 model 声明的 `:context-window`。一并报出**阈值比例 0.7** 与**保留比例 0.16** 算出的
两个界，好让读者看出还剩多少余量。管理边答得出它，圈上画得出它。

这是**只报告**的一张票：请求照旧发出去，一个字都不拦。它给后面所有票提供那个「要不要动手」的数。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 给定一份记录与当前**模型视图**，得到一个答案：当前压力 token、窗口、百分比、阈值 token、保留预算
- [ ] 有可复用锚点时，**只有增量是估算的**；锚点被采用的条件（厂商报的总量不低于本次完整启发式估算）
      写下来并用测试钉住——估算偏低时这个条件反而更容易满足，正是它在挡误差
- [ ] 没有可复用锚点（首次请求、信封变更）时退回纯启发式，并**说出来**：所采用的基线种类是
      「估算」而不是「厂商用量」，两者在读法上分得开
- [ ] 中文文本与 JSON schema 会被系统性低估这件事，有一条测试把它**量出来**（断言它偏，不是断言它准）；
      另一条断言锚点机制把误差挡在增量之外
- [ ] 每次模型调用把这次的压力记进记录（一条只写日志的事实行），含窗口、阈值、保留预算、基线种类
- [ ] 管理边（会话统计那一路的 `context` 一节）答得出这个数；目录没声明 `:context-window` 的 model 上，
      窗口与百分比**缺席**而不是 0
- [ ] 只报告：不改变任何行为，没有任何拦截
- [ ] 离线全量 `harness.test-runner` 全绿
