# 任务清单提醒（todo reminder）

**状态**：已实现（本票的改动就在 worktree 里）。

## 要解决什么

`todo_write` 的清单活在库里，但**只有模型写它的那一刻它在模型眼前**。一轮结束时清单还剩三项没做完，
模型就停了——没有任何机制把它拉回来。人不得不手动打一句「接着做」。

**目标**补的是另一格（一整场会话去哪儿），而这一步的清单没人管。本票补这一格：
**清单没做完时，把 `<system-reminder>` 提醒注入对话，并让这一轮接着走**。

## 参考

`goal` 的整套机制（`.scratch/goal/spec.md`）——注入 + 驱动器。本票是它在任务清单上的**轻量翻版**：
两种触发（人手动 / 事件自动）、一种注入（`<system-reminder>` 块）、一个驱动器（run 收尾后自动开下一轮）。
两处**故意不同**，理由各写在各条决定里：

- 目标有相位和 `{id, revision}` 栅栏（两只手并发写、要回答「改过几次」）；清单**整体替换、没有历史**，
  所以它还是纯状态，**不进记录**。
- 目标的续跑许可（armed）为人保留「人没说话就不自动续钱」；清单的自动开关**是人自己按下的开关**，
  重启即失、会话重建即失（进程内存），但**不会**被人无关的一句话重新打开。

## 决定

### 1. 两种提醒，一种形状：都是一条真的 user 消息

“手动提醒”和“自动提醒”都产出**同一条消息**——由 `harness.cap.todos/reminder-turn` 一处产出，
`role = "user"`，内容是 `<system-reminder>` 块（`harness.cap.reminder/wrap` 的唯一写手），
所以它进对话、进记录、在客户端画成一张注入卡，和 goal 的 round 开场同形。

```
<system-reminder>
Task list reminder:
- [ ] 读一遍代码
- [~] 写测试
2 items are not done yet (1 in progress, 1 pending).
接着把任务清单做完：做完一项就把它的状态改成 completed；清单有变化就用 todo_write 重新提交完整清单。
</system-reminder>
```

- **为什么会话里是两条路。** 目标提醒是**派生注入**（每轮 pre-LLM 缝现算，幂等）。清单提醒是**一次性事件**：
  手动是「现在催一下」，自动是「一轮收了、活没干完」——两者都必须**重新开一轮**（或插进正在跑的那一轮），
  派生注入做不到这件事，`start-run` 才做得到。
- **`Task list reminder:` 进两处标签表**（`harness.cap.reminder/labels` 与 `ui/src/lib/injections.ts` 的
  `LABEL_PREFIXES`），记录里它归 `injection`，是「这个 harness 在说话」那块卡。

### 2. 手动提醒 = 一条命令；有 run 时插进那一轮，没有时开一轮

`{"type": "todo", "action": "remind"}` 走会话命令队列（`.scratch/run-commands`，与 goal 同一条），
`:no-run :execute`：没有 run 在跑时由路由就地执行，有 run 时入队、在那个 run 的下一个 pre-LLM 边界执行。

- **有 run 在跑** → 提醒**注入正在跑的这一轮**（下一次模型调用就看得到），**不开第二轮**。
  两个 run 写一条对话是这套里唯一的真危险（`refuse-second-run!` 就是拦它的），手动提醒没有理由去撞。
- **没有 run 在跑** → `start-run` 开一轮，把 `reminder-turn` 当 `append`。这就是「重新开始一轮」。
- **清单里没有未完成项时手动提醒被拒绝**，按名字（`:nothing-to-remind`）：提醒一句「都做完了」是噪音。

### 3. 自动提醒 = 本进程里按会话开的一个开关

`{"type": "todo", "action": "auto", "on": true|false}`。它是**进程内存**里一张 `thread-id` 的表
（与 goal 的 `armed`、作业注册表、命令队列同族）：

- **只对当前会话生效、当前这份清单生效**：表按 `thread-id` 存，提醒的内容永远是**当下那一份**清单
  （决定 4 的指纹门决定「同一份只催一次」）。一份写完之后**全 completed 的新清单会把开关关掉**
  （`write!` 顺手 `disarm!`）：开关就是为「没做完的活」开的，活做完了它自己灭。
- **重启即失、会话重建即失**（`harness.edge.sessions` 的 `:build` 缝里 `todos/disarm!` 一句，
  和 `goal/disarm!` 并排）：一个人不在场的进程不该继续替他开轮。
- **人无关的一句话不会把它打开**——这是与 goal 的 `arm-if-active!` 的**故意不同**：goal 的许可本来就是
  「人说话我就接着推」，而这是一个**开关**；被一句「你好」悄悄打开、然后开始自动烧钱，是这套里最糟的意外。
  打开它只有一扇门：那个命令。

### 4. 驱动器：run 正常收尾之后，最多开一轮

挂在 `harness.edge.http` 已有的 `:run/done` 尾部、**goal 的驱动器旁边**（同一块受保护的 try 里）。
`turn/end` 行也是在这里写下的，所以「turn/end 或 run/end 之后」就是这一处。

**四道门，任何一道不成立就静默停（什么都不写、什么都不开）：**

1. **开关开着**（决定 3）。
2. **清单有未完成项**——全 `completed` 或清空了就没有提醒的对象。
3. **这一轮的清单与上一次自动提醒时不同**（指纹，`todos/fingerprint`）。
   **这就是刹车**，而且它是清单版唯一的刹车：模型被提醒一次却一个字没改清单，再提醒它是原地打转。
   清单推进了（哪怕只是标完一项），下一次才可能再提醒。
4. **这一轮是正常收尾**（`ended-normally?`：`RUN_FINISHED` 且不是 interrupt）——错误、被停、等在
   人手里的 run 都不是「该接着做」的信号。

再加一道**跨机制**的：**goal 刚开了下一轮就不再开**（`drive-next-round!` 先跑，答 `true` 时跳过）。
两个驱动器都开一轮 = 两条 run 写一条对话，这是不能发生的。

**上限**是保险丝不是目标值：`config.edn` 的 `:session :todo {:max-rounds N}`，默认 **25**（与 goal 同）。
到顶就停、**不写任何相位**（清单没有相位），下一次清单推进或人再按都还能走。

### 5. 手动提醒的“插进正在跑的那一轮”怎么落地

`harness.cap.todos` 里一张进程内存的 `pending` 表（`thread-id -> true`）：命令执行器记下它，
`before-llm-with-commands` 在这轮的下一次模型调用前取走、把 `reminder-turn` 追加进历史
（**取走**，所以只注入一次）。没有 run 时路由不记 pending，直接开一轮带这条消息。

- **不落盘**：pending 是一次性的意图，进程重启就没了——这正是它该有的寿命。
- **取走不是幂等**：它和 goal 的派生注入是两种东西，一次性的事件不该留在历史里被反复看见。

### 6. 不去动的东西（以及一处改了主意）

- **`prompt.md` 一个字不动**：清单会中途变，冻进 system 前缀就是一句会过期的话。
- **`pre-LLM` 派生注入里不加清单**：清单已经在对话里（`todo_write` 的调用与 receipt），
  每一轮再贴一份是替模型重复它自己刚说的话。清单提醒是**事件**，不是常驻。
- **开关有一条帧家族（`todos`，第六族）**。`docs/rules/panel-data.md` 那条规矩问的是「这个可推对象凭
  什么没有写点」——它有：一条 `todo` 命令。所以 `harness.edge.http/todos-send!` 在命令之后推一帧
  `{threadId, todos, auto?}` 整份（另一页画的开关会跟着动），`onDownlinkOpen` 再补一次存量（这一族帧
  没有游标）。**清单本身不走这一帧**：`todo_write` 走工具表、没有面板写点，它的变化照旧由 `model/start` /
  `turn/end` 两个 fact 重读。

### 7. 工具与命令是同一个开关的两扇门

**模型不加新工具**：清单的提醒是 harness 对模型说的话，不是模型要求的东西（goal 相反，模型能自己立目标）。
**人**只有那一条 `todo` 命令，和 `GET …/todos` 的存量。两个动作（`remind` / `auto`）都在
`harness.edge.http/run-todo-command!` 一处解释，`:no-run :execute`、优先级与 goal 同档。

## 代价（写清楚，不藏）

- **自动提醒会花掉整轮的钱**：一道提醒 = 一轮 run = 一次（或多次）模型调用。它的刹车是「清单必须动过」
  （决定 4 的第 3 道门）和 `max-rounds`；一个人打开开关后不再看，最多烧掉上限那么多轮。
- **多一族帧名**：`todos` 要进 `ui/src/lib/mux.ts` 的 `familyOf`、`wantedThreads`、`stillWanted`、
  `subscribeTodos` 与那条读 wire 的客户端测试，以及 `docs/rules/panel-data.md` 的家族清单——漏一处，那一帧
  要么到不了页面、要么被 AG-UI 的 schema 拒掉、把正在看的 run 一起带走。
- **指纹判据的口径**：同一份清单，模型只改了 `pending` 项的文字但状态没动，也算「变过」——指纹是内容级的。
  代价是模型可以靠改文字骗过刹车；换来的是「标完一项 = 推进」，那是这份清单上真正的进展。
- **`GET …/todos` 的答案多一个字段**：`{"auto?" bool}`。UI 客户端与它的类型要跟着，两处任一漏了就画不出开关。
- **手动提醒在有 run 时不开新一轮**：与「重新开始一轮」的口径有一处偏差，理由在决定 2——
  两个 run 写一条对话比少开一轮危险得多。
