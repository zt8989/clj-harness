# 02 — `job_list`：把本会话的作业与记录列出来

**What to build:** 一条命令答出「本会话有哪些后台作业、哪些记录」：本进程里活着的每一条（id、命令原文、
状态），**以及盘上本会话留下的每一份记录**——包括前面几次运行跑过的（id 相同、进程戳不同）与前台 `bash`
溢出落下的 `c*` 那份。状态仍是记录末行那一个约定（`[exit N]` / `[stopped]` / 没有那一行即还在跑），
**不新立枚举**。一个作业都没有时，答句与 `unknown-job` 拒绝句里那句**同一处出处**。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

## 形状

- 工具名 `job_list`，**没有参数**（本会话的作业与记录，没有第二个问法）。
- **一行一份记录，不是一行一个 id。** 同一个 `j1` 在两棵进程戳下是两行——文件名里那截戳说的就是
  「哪一次运行」（`process-tag` 的全部理由）。
- 每行至少：id（`j1` / `c3`）、哪一次运行（本次运行 / 进程戳）、状态、路径。活着的作业那几行还有
  **命令原文**（**压成一行**：内部换行折成空格，过长截断并说明省略了多少字）；旧记录那几行没有命令，
  一行里写明这件事（记录里装的只有命令说过的输出与末行——不猜、不留白让人以为是空的）。
- 前台记录与作业**分段标出来**（`spill!` 的原话是「一个前台记录**不是作业**」：没有进程可停、没有 id
  有人会去寻址）。留这份记录的全部动机就是「回头读一条命令说了什么」，所以它也列。
- 最新在前；超过一个**具名上限**（`def`，好让用例绑小它）时，按 `job_output` 省略句的先例加一句
  「还有 N 行没列」以及怎么自己看（那份记录就在说的那个目录里）。
- 本会话一份都没有 → 与 `unknown-job` 那句「This session has no background jobs.」**同源**
  （一处写、两处用），别各写一句。

## 决策

- **读的是两样东西，读在 `harness.cap.jobs`**（与 `output` / `stop!` 同处，私有件与注册表都在那里，
  不必导出）：注册表给出**活着**的那几条与它们的 `:command`；`<配置家>/jobs/<会话>/` 目录给出盘上的
  每一份（`record-files` 已经在走这棵树，按 mtime 排序）。名单 `<id>-<进程戳>.log` 就是这两样的接缝。
- **只读，不动树。** 不复活注册表、不删记录、不建索引、不加元数据文件——要 `ls` 的答案本来就是 `ls`，
  缺的只是模型不知道 `ls` 哪里（`unknown-job` 的拒绝句今天已经在替它列 id，理由同源）。记录的回收仍只有
  `prune-records!` 那一条字节封顶的路。
- **不改 `unknown-job` 的语义**：它答的是「这个 id 我没有」，不是「有什么」。只让「本会话没有后台作业」
  这一句有同一处出处。
- **翻掉旧非目标**：`.scratch/bash-record-persistence/spec.md` 的「不引入任何「列出/找旧记录」的动词
  （`job_list` 之类）」——**划线 + 日期注**，写明当初的判据（「要 `ls` 的答案就是 `ls`」）仍然成立、
  **记录仍不会被这个动词删或救**，缺的只是入口。
