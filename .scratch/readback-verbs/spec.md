# spec: 两只读回来的手，与状态行归位

**一句话**：工具面加两只**读**的手——`todo_read` 把本会话的任务清单读回来，`job_list` 把本会话的作业
**连同盘上跨运行留下的记录**列出来；`job_output` 的答案把状态行从**头一行**挪到**最后一行**，与那份记录
自己的末行、与 `bash` 答案的末行同一处。

2026-09-24 立。四张票：`01 → 02 → 03 → 04`（01/02/03 互不阻塞）。

## 问题

1. **任务清单只有写没有读。** `todo_write` 整份替换、答案只报个数（回执，不回放），库里那行今天只有
   `harness.cap.todos/items-for` 读得到——而清单**跨 run、跨进程活着**，这是它进库的全部理由。于是
   压缩过一轮、换过一轮上下文、或者另一个调用写过之后，模型再也拿不回自己那份清单：它记得「有一份」，
   读不回来。`.scratch/tool-parity/issues/03-todo-write.md:20` 当初写着「**不设「读」工具**」，
   理由是「清单就在上一次调用的答案里」——那句话只在一个上下文窗口内成立。
2. **作业只有「指名问」，没有「有什么」。** 注册表里有 `:id` / `:command` / `:path`，`unknown-job` 的
   拒绝句今天就在替它列 id；记录还**活过写它的那个进程**。而模型重启之后既不知道有哪几个 id，也不知道
   盘上躺着哪几份记录——`job_output` 要一个 id，它连一个 id 都想不起来。`.scratch/bash-record-persistence/spec.md`
   的非目标原文是「**不引入任何「列出/找旧记录」的动词**（`job_list` 之类）」，理由是「要 `ls` 的答案就是
   `ls`」；`ls` 那条路今天仍然通（`bash` / `glob` 读得了配置家），但**模型没有 `ls` 的动机**：它不知道
   那个目录叫什么，也不知道里面按什么命名。
3. **`job_output` 的答案把状态摆在最前面**，与它所读的那份记录正好相反：记录的**末行**才是状态
   （`.scratch/job-output/spec.md` 决策 6），`bash` 的答案也是末尾一行说它怎么结束的，只有这一只手把
   同一件事实摆到了开头。`cap.jobs` 的模块注释与 `CONTEXT.md` 的词条都照着这个错位写了下来。

## 决策

1. **两个新动词都是「读」，答案按读法交付。** `CONTEXT.md` 的「回执」那条讲的是**写**类调用：不回放模型
   刚送进去的东西。这两只手交付的正是模型手里没有的东西，所以**不是回执**，也不套回执的措辞。
2. **`todo_read` 没有参数。** 清单属于本会话，没有第二个问法。答案：**一项一行、带状态标记**，末尾一句
   总数与状态分布。空清单与「本会话从没写过」**同一种答法**——`items-for` 已经把这两种事实并成一答，
   照着它说，不另造第二句。没有会话在作用域里 → **指名拒绝**，与 `todo_write` 的 `:no-session` 同一家族。
   渲染落在 `harness.cap.todos`（与 `items-for` 同处），工具体只做「取 thread-id → 渲染」。
3. **`job_list` 列两样东西**：本进程注册表里活着的作业（id、命令原文、状态），以及盘上本会话留下的
   每一份记录（跨运行那几份——文件名里的**进程戳**说的就是「哪一次运行」）。**一行一份记录，不是一行一个
   id**：同一个 `j1` 在两棵进程戳下是两行。
   - 状态仍取自**记录的末行**（`[exit N]` / `[stopped]`，没有那一行即还在跑），**不新立枚举**。
   - 命令原文只有**活着**的作业有（`spill!` 与注册表都说明了：记录里装的是命令说过的输出与末行，
     命令本身只在注册表条目的 `:command` 里）。旧记录那几行**没有命令**，一行里写明这件事，不猜。
   - 前台记录（`c1` 那种，`spill!` 的原话是「一个前台记录**不是作业**」）与作业同名同目录：**也列**，
     分行分段标出来。留这份记录的全部动机就是「回头读一条命令说了什么」，前台那份同样在。
   - 最新在前；超过一个具名上限时按 `job_output` 的省略句先例说「还有多少行没列」以及怎么自己看。
   - **只读，不动树**：不复活注册表、不删记录、不建索引。记录的回收仍只有字节封顶那一条路。
4. **`job_output` 的状态行挪到最后一句话**：`正文 → （装不下时的范围/路径行） → 状态行`。顺序与记录
   一致（记录的末行就是它），与 `bash` 一致（末尾一行说它怎么结束）。状态行的**字**一个不改；改的只是
   它排在哪。`jobs/output` 的返回形状不动（`:status` 仍是一个字段），动的是「脸」怎么摆。
   通知（`<job-ended>`）、`job_kill` 的答句、「告知」的规矩：**一个字不改**。
5. **工具数 18 → 20。** 三处硬编码名单（`tools_test` 两处、`editing_mode_tools_test` 三处）与四份讲工具的
   文档（`docs/architecture.md` 的模块地图、`CONTEXT.md` 的闭清单、`docs/system-prompt.md` 的名单、README
   那一节）跟着加名。**顺手核一件事**：`CONTEXT.md` 的闭清单今天比真实工具表少一个 `skill`（17 比 18），
   这次核到逐名相等。
6. **`ui/` 不阻塞这件事。** 页面本来对没见过的工具就有兜底（`WrenchIcon` + 第一个字符串参数），所以两个
   新动词不加 UI 也能用；但 `todo_read` 是 `todo_write` 的另一半，图标给同一族，`job_list` 也给一个——
   一行卡认得出来才叫落地。

## 非目标

- **不给任务清单做 UI 面板 / HTTP 端点**（`.scratch/tool-parity` 决策 14 照旧）。读侧仍是函数 + 工具。
- **不提供「删记录 / 清树」的动词。** 记录的回收只有字节封顶那一条，`job_list` 只读。
- **不改 `job_output` 的 `offset` / `limit` / `wait` / `timeout`**，不改 `job_kill` 的幂等，不改记录末行的
  约定（`[exit N]` / `[stopped]` / 缺席即还在跑），不改「告知」与通知的三样事实。
- **不给记录建索引、不加元数据文件。** 文件名就是索引。
- **不动 MCP、不动审批、不动子代理的只读基线**（两个新动词都不声明 `:read-only`）。

## 验收主线

1. **清单读得回来**：写一份三项（三种状态各一）→ 另起一个 JVM 打开同一个 home → `todo_read` 逐条读回，
   顺序与状态一致。
2. **作业列得出来**：起一条跑完的、一条挂着的 → `job_list` 两行都在，跑完那行的状态就是记录的末行。
3. **跨运行那几份也在**：绑 `*tag-override*` 再起一条 `j1` → 上一次运行那份 `j1` 记录也在列表里
   （进程戳认得出是哪一次），且**一行都没被删**。
4. **状态行归位**：一条作业打了几行输出 → `job_output` 的答案**最后一行**是状态；装不下整份记录时，
   范围/路径行在它上面。
5. **工具表二十个**：三处硬编码名单 + `CONTEXT.md` 闭清单 + `docs/architecture.md` 逐个名字对得上。

## 跨特征对照

- **`.scratch/tool-parity/issues/03-todo-write.md:20`**「不设「读」工具」——本特征翻掉它（划线 + 日期注），
  并写明为什么：清单跨 run、跨进程活着。
- **`.scratch/bash-record-persistence/spec.md` 非目标第一条**「不引入任何「列出/找旧记录」的动词」——
  本特征翻掉（划线 + 日期注）。当初的判据「要 `ls` 的答案就是 `ls`」仍然成立，缺的是模型知道该 `ls` 哪里；
  记录的**寿命与封顶一个字不改**。
- **`.scratch/job-output/spec.md` 决策 6**（记录末行即状态）：一个字不改，本特征让答案跟上它。
- **`.scratch/job-receipt-no-path`**（回执不报路径、读的那一个报）：一个字不改，只是「读的那一个」现在
  多了一个「先列出来」的入口。
- **`.scratch/bash-record-persistence/spec.md` 决策 4**（跨进程只有「读」，没有「问」）：本特征给它一个
  「读」的动词——**不是**把注册表复活，而是把盘上已经在那儿的事实列出来。
