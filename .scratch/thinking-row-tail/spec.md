# 思考行：不自己展开，流式那段在行上滚，停下来回到首行

**由谁提的**：2026-09-22，主人一句话——*「不要默认展开思考，思考中那一行文字滚动显示，思考完成再回到第一行」*。
三句话是三条判据，本文件把每一条落到一处实现、一次实测上。**当天被推翻一次**：第一版用「裁左边缘」的布局做出了
滚动的**结果**，但每一批字都是**跳**的；主人一句话纠正——*「从左边字退出，右边字插入」*——现在是拖（`transform`）
出来的连续滑动。第一版做了什么、错在哪，见文末复议。

**推翻的是哪一条**：`.scratch/flat-step-rows/spec.md` 与 `.scratch/assistant-ui/issues/04-message-parts.md`
第 14 节（2026-09-17）写下的「**正在到达的那段思考自己展开**，用上游那扇跟随最新 token 的窗口滚动显示，
最后一个 token 落下再折回行上留首行」。那扇窗**还在**，但它只给**点它的人**开；两处按仓库规矩就地划掉
并在文末各追加一段复议。

## 三条判据，各自落在哪

| 主人说的 | 判据 | 落在哪 |
| --- | --- | --- |
| 不要默认展开思考 | 行仍是 disclosure，但 `open` 由行自己持有、初值 `false`；上游那条 `userOpen ?? (streaming \|\| defaultOpen)` 再没有机会替人点开 | `message-parts.tsx` 的 `ReasoningBlock`（`open` / `onOpenChange` 交给 `<ReasoningRoot>`） |
| 思考中那一行文字滚动显示 | 行上的摘要换成**已经到达的那一段**（压成一行），装在一只 `overflow: hidden` 的窗里；整行被**往左拖**到它的**末尾**停在窗的右边缘——字于是从**左边出去**、新字从**右边进来**，而拖动是 `transform`（能被插值），所以是滑不是跳 | `message-parts.tsx` 的 `ReasoningTail` ＋ `styles.css` 的 `.aui-reasoning-trigger-tail` |
| 思考完成再回到第一行 | 不流式时回到原来那条规矩：第一个有字的 part 的首行、截 120 字、末尾 `…` | `lib/reasoning-preview.ts` 的 `firstLine` / `clip` / `previewOf(…, running=false)` |

## 决策与代价

1. **「不展开」不是「把 `streaming` 拿掉」。** `streaming` 照旧传给 `ReasoningRoot`：它还决定**打开着的**那扇窗
   跟不跟最新 token、长不长底部渐隐。真正拿掉的是**上游替人点头的那一下**——所以 `open` 收到 `ReasoningBlock`
   自己手里（初值 `false`），整套上游动画、scroll lock、`max-h-64` 全都不动。
   **代价**：接管了 open 状态之后，上游那条「流式开始/结束时自己播一次动画」的分支不再走（它本来就只在
   `!isControlled && userOpen === null && !defaultOpen` 时才走）——而那正是这次要停掉的东西。
   手动点开的人在流式期间拿到的仍是原来那扇实时窗（`streaming && open` 才长出底部渐隐与跟随）。

2. **滚动必须是 `transform`，这是整件事的技术核心。** 窗只能装下一行里的一段，所以一定要有东西在动；
   问题是**什么在动**。
   * 让**布局**去动（把行裁在左边缘，字依次被挤出去）：一个 token 一次重排，浏览器画出位置 A 再画出位置 B，
     中间**没有帧**——读到的就是**跳**。
   * 让**变换**去动（整行先按左对齐排好，再 `translateX` 拖到末尾对齐窗的右边缘）：`transform` 是 CSS 里
     唯一能被**插值**的运动，`ReasoningTail` 每次布局完、绘制前量一次（`useLayoutEffect`），
     `styles.css` 给它一条 transition——同一段位移，被摊成一帧一帧的滑。
   **代价**：这一手要一次测量、一次写样式，每个 token 都做；换来的是「滚动」这个词真的成立。

3. **拖动给的是速度，不是一个固定的时长。** 固定时长会让滞后正比于模型写得有多快：拖动永远落后那么多毫秒，
   字越快、屏幕上的字越旧，而且「最新到达的字」恰好是被右边缘切掉的那几个。所以每一步的时长按
   **`TAIL_SPEED`（像素/毫秒）**算出来，并封顶 `TAIL_SETTLE_MAX`：一个字宽的量几毫秒走完，一整句砸下来也还是滑。
   `TAIL_SPEED = 4`（这个字号下约 300 字/秒）取的是**厂商最快也就这么快**——真实会话里拖动能跟上，
   只有甩开它的爆发才允许落后。实测（脚本流限速到约 250 字/秒）：滞后的中位数 190px、99 个采样里 32 个完全跟上、
   流末尾 0px。

4. **行上拿到的是「已经到达的那一段」，不是切出来的 120 字窗。** 拖动要能把已经划过去的部分一起移动，
   而**丢掉左边的字就会把运动交还给布局**——每丢一个字跳一次，正是第一版的毛病。
   **代价**：那一段字留在 DOM 里（一个文本节点，宽度随思考增长）。原来的 120 字封顶就是为了不这样，
   现在它是「停下来之后贴给行的首行」那一条的常量（`PREVIEW_LIMIT`），不再管流式那一半。

5. **三条文字规则在 `lib/reasoning-preview.ts`，不在 `message-parts.tsx`。** 那个文件进不了 UI 套件
   （它摸 assistant-ui runtime），而这三条规则恰好是**纯字符串规则**，搬出去就能被
   `test/suites/reasoning-row.ts` 当数测（三条用例）；剩下只有浏览器能看的四条判据去了走查。
   `firstLine` 同时被 `subjectOf` 给 `bash` / `eval` 的摘要在用，所以它是导出、不是私有。

## 实测（2026-09-22，真 Chromium，`--scripted`）

`node .scratch/thinking-row-tail/walkthrough.mjs http://localhost:5393/` → **GREEN，21 条**（全表见
`evidence/README.md`）。几个数：

* **字不动的时候，行还在走**：99 个采样里有 81 对相邻采样的**字完全相同**，其中 **67 对位置仍在变**——
  这就是「插值，不是跳」的判据。（**字为什么会成批地变**：AG-UI 客户端与 React 把一串 SSE 帧并成一次渲染，
  实测 4 秒里只换了 18 次行文，也就是每批 ~60 字 ≈ 780px。第一版正是每批跳 780px。）
* 行一直被往左拖：`trackLeft` `507px → -10487px`，窗宽 478px；行的起点最多跑到窗左边 **-63px** 之外
  ——**左边出去**成立。
* 右边缘**始终有字**（滞后 ≥ -1px），并且会**追平**：99 个采样里 32 个滞后 ≤ 2px、中位数 190px、末尾 0px
  ——**右边进来**成立。
* 行高全程 **28px**（一行 13px 字 + `py-1.5`）：没有换行，下面的步骤不会被推走。
* 停下来之后行上回到首行 ` · 先读 deps.edn，确认依赖有没有变。`；手动点开是整段（1058 字），再点收起；
  刷新之后仍是折着的一行首行。

## 没有做的事

* **不动抄来的 `reasoning.tsx` / `reasoning.aui.tsx`**：这次只用了它们的 `open` / `onOpenChange` 与
  `streaming` 三个已有的口子，一份抄来的文件都没改（`LOCAL:` 标注数不变）。
* **不动那一轮的折叠**（`.scratch/assistant-ui/issues/04` 第 15 节）：本轮结束时步骤仍会收起来，
  收起来的是**已经想完**的东西。
* **没给 `harness.fake` 加节奏开关**：走查用 CDP 限速把同一段字节摊开（见 `walkthrough.mjs` 头注释），
  夹具因此一行没改——代价是这条证据依赖限速，换台机器跑要重新读一遍那几个数。
* **恢复出来的会话**永远是折的一行首行（不流式 ⇒ 首行），这条与改动前一致。

## 复议（同日）：第一版是「裁左边缘」，被主人一句话推翻

**第一版做了什么**：`direction: rtl` 的盒子把行裁在**左**边缘（rtl 里溢出的是起始那一侧），内层
`direction: ltr` 把文字掰回来；行上贴的是**最后 120 字**。位置是对的——左边出去、右边进来，四个几何判据
`GREEN`——但**运动**不对：窗里的字靠**布局**往前走，一次重排一步，读到的是一跳一跳。

**为什么当时量不出来**：那版走查量的是「每个采样都是全文里连续的一段、整窗的位置逐次前移」——它全都成立，
因为**位置**确实在动。**当时没有任何一条判据在问「两帧之间有没有中间态」**，而「跳」与「滑」的差别只在那里。

**主人怎么说的**：*「不是我想要的效果，我要的是，从左边字退出，右边字插入」*——说的正是**动词**：
`退出`/`插入` 是运动，不是位置。于是这一版把运动本身做成判据（「字不动而位置动」，见上），
把使运动的机制从布局换成 `transform`。**几何判据一条没丢**，只是不再是全部。

**代价如实记下**：`direction: rtl` 那一手很轻（三行 CSS、无测量、无 JS），换来的是不可能插值的布局位移；
现在多了一次每 token 的测量与一次样式写入——这就是这条复议的全部交换。
