# 01 — 帧总线：子agent 的帧有人能收

**What to build:** 一条**进程内**的帧总线：按 thread-id 发布 / 订阅 AG-UI 帧。`run-subagent!`
现在是「转好帧、只写进子agent 自己的 jsonl、一个字节都不发」——这一票在它旁边加一句 publish，
于是「有谁在看」成为一个可以问的问题。**没有订阅者时什么都不做**（不是发到一个空集合，是压根
不构造要发的东西）。

要点：

- **进程内，不是文件。** 与 `subagents/live`、parked 表同一条规矩：一张按 thread-id 分家的表，
  随进程退出消失。`http.clj` 头注释那条「记录不是事实来源、服务器从不读回文件」是这一票的由来，
  别绕开它去 tail 日志。
- **表要按键分家，读的那一侧也带 key。** 进程级的容器不许有一个全局单槽（AGENTS.md）。
  `nil` 那个键留给「进程级」这一档时要有意为之并写清。
- **订阅者的生命周期归订阅者自己。** 客户端的连接断了，它的 channel 必须走掉——否则总线会把帧
  灌进一个没人读的 channel，填满后把发布方**阻塞**在工具线程上。这是本票唯一的真陷阱：
  publish 必须是**非阻塞**的（满了就丢这一帧，或者只发到还活着的订阅者），因为发布方是子agent
  跑轮的那条线程，它被卡住等于整个委派被卡住。
- 订阅 / 退订是一对原子操作，不许在两个原子操作之间夹副作用（AGENTS.md），正例见
  `harness.cap.providers/take-provider-changes!`。

**Blocked by:** 无

**Status:** ready-for-agent
