# 02 — 只读跟随通道 `GET /api/threads/<stem>/follow`

**What to build:** 一条 **SSE、只读** 的路由：subscribe 一个线程的帧。连上以后先**补发**它已经落在
记录里的帧，然后跟着 01 那条总线走，直到终态（`RUN_FINISHED` / `RUN_ERROR`）收尾关闭。

这是本组的 tracer bullet，也是唯一能证明「边跑边长」的一票。

要点：

- **不许被误认成「起一次 run」。** 这是 `GET`，它**不**回答 `POST /api/agent` 那个形状，也不
  接受任何输入：它没有要跑的东西。这一点要写在路由的 docstring 里，否则下一个读者会以为它是
  另一条 run 通道。
- **`POST /api/agent` 一个字都不改。** 父会话那条流仍然只属于它自己那次 run；跟随是**另一条**流。
  父子不同路，是因为把子agent 的帧混进父会话那条流会让客户端的运行时把它们当成父会话的消息
  （`app.tsx` 里一个 host 一个 core 的设计正是为了不串台）。
- **补发那一次读不是「把记录当事实来源」。** 它与 `rebuild` 是同一条读法，读的是**已经写完**的
  部分。要区分清楚：补发是历史，总线是当下；`http.clj` 头注释那条禁令针对的是「让服务端一边写
  一边读自己的文件去分发」，那件事这一票不做。
- **补发与订阅之间有一个竞态，必须有显式的答案。** 「先订阅、再补发」会重复（补发里的最后一帧
  可能同时也从总线来了），「先补发、再订阅」会漏（补发读完到订阅之间落地的那一帧没人要）。
  不许留给运气：要么给帧一个每线程单调的序号（记录里与总线上是同一个数，补发读到第 N 就丢掉
  ≤ N 的），要么写清另一种等价的去重。上一轮那条「两个原子操作之间不许夹副作用」是同一个道理。
- **容忍正在写的最后一行。** 记录是边跑边追加的，所以读到的主文件末尾可能是一个**没写完的
  半行**。那不是损坏，是「现在就读到这里」；`rebuild` 对**完整**日志的严格判定不适用于这一条路，
  不可以把半行当 corrupt 拒掉整条流。半行丢掉即可，下一次读取它会以完整的样子回来。
- **只读，不拿写锁。** 这条路由只读日志与内存表，**不碰** `harness.infra.db` 的写侧、不写
  `~/.clj-harness`。AGENTS.md 那条「库只有一把锁：写会把正在跑的应用一起带走」在这里尤其相关——
  这是一条会在子agent 正在跑的时候被连上来的路由。
- **没人跑就直说。** 线程不在跑、记录也已经收尾，那就立刻答一句话（哪个线程、它不在跑）并关闭，
  让客户端回落到 `rebuild`。**不要**挂着一条永不产出、也不结束的流——那种连接在客户端的运行时
  看来和「还在跑」完全一样。
- 客户端断开要退订（01 的那个陷阱在这一侧收口）。
