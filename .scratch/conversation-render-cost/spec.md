# spec: 画出来的那场会话 —— 实测读数，与四刀

**一句话**：成本全在「画」不在「收」。一场 4,285 帧的流，主线程 JS 只花 19–132 ms/秒、样式与布局
≈0–5 ms/秒；而把一场已有会话**冷画一次**（50 条窗口里含一条 18k 字回答）是 **176 ms**，其中
**138 ms 是 JS**。所以优化要落在 markdown 解析 + React 重建上，不要去做 CSS/合成层；「收帧」本身
封顶几十 KB，不是问题。

2026-09-30 在真浏览器里实测（owner 的 Chrome 153，`kimi-webbridge` 借一个 tab），流由
`node scripts/dev.mjs --scripted <script.json>` 的脚本 provider 推。方法是差值读数，不是推算。

## 怎么量的（可复现）

1. 脚本（照 `scripts/example.json` 的形状）：`{"pace-ms": 8, "turns": [{"reasoning": …, "content": …}]}`
   ——5 字一块、8ms 一块，18,000 字回答 + 1,200 字思考 ⇒ **4,285 帧 / 45 秒（≈95 帧/秒）**。
   对照一场真实 run（`62f30024` 上那场）：23,461 帧 / ~450 秒（≈52 帧/秒）——这条流更密、只是短。
2. `node scripts/dev.mjs --scripted <script>` 起隔离服务（临时 home、OS 分端口），把打印的地址
   用真浏览器打开（**本仓库没有 Playwright**，页面的事就是浏览器的事）。
3. 仪器是 CDP（借来的 tab 上）：
   - `Performance.getMetrics` 的**差值**：`TaskDuration` / `ScriptDuration` /
     `RecalcStyleDuration` / `LayoutDuration` / `Nodes` / `JSEventListeners`；
   - `Runtime.getHeapUsage`：`usedSize` / `embedderHeapUsedSize` / `backingStorageSize`；
   - 页面里裹一层 `WebSocket` 数收了多少帧、都是什么类型。
4. 三档场景：① 边流边画；② 画好之后空闲；③ 把会话从 DOM 里拿掉再冷画一次（对话 ↔ 轨迹 切两次）。

## 读数

| 场景 | 主线程 task | 其中 JS | 样式 / 布局 | DOM 节点 | JS 堆 |
|---|---|---|---|---|---|
| 流式 45 秒 / 4,285 帧 | 80–350 ms/秒 | **19–132 ms/秒** | ≈0–5 ms/秒 | 432 → 468 | 32 → 58 MB 锯齿 |
| 冷画一场会话（50 条窗口，含一条 18k 字回答） | **176 ms 一次** | **138.5 ms** | 13.5 / 11.8 ms | 510 → 657 | +1.6 MB |
| 画好之后空闲 | 0.6 ms/秒 | 0 | 0 | 不变 | 不变 |

同一场流的内存那一半（上一轮另测，`mux-run-replay-dupes` 的同一套仪器）：**4,275 帧只换来
+~100 个 DOM 节点**（一条回答一个段落）；跑完强制 GC 后留下的是**那场对话本身**（几 MB，18 KB 的
回答加它的 message / markdown / React 对象）；隐藏（不画）时合批上限 `HOLD_LIMIT = 200` 帧
≈ 几十 KB。整机 Chrome RSS 在这期间反而 886 → 764 MB（噪声远大于一个 tab 的几 MB，没有分辨率）。

## 结论

- **收帧不是成本**：帧交付后就是垃圾，合批窗口有界，隐藏 tab 也只在满 200 帧时画一次。
- **样式与布局不是成本**：流式期间 0–5 ms/秒。别去动 CSS / compositing。
- **成本是「把一条消息的 markdown + React 树建出来，并且流式期间反复建」**：冷画那一刀 138 ms 的
  JS 是它的静态价格；流式那 19–132 ms/秒是它的动态价格。
- **常驻是「窗口里的那场对话」**：窗口由服务端给（`harness.kernel.session/page-size = 50`），
  每点一次「更早」再 prepend 50 条——所以常驻会随阅读历史长，而今天页面同时存着两份表示
  （窗口的 entries 与 runtime 的 messages）。

## 四件事，三张票（`issues/`）

- **A（票 01）正在流的那条消息，别每个 flush 重建整条子树**——动态价格。**已落地**，见下面
  「票 01 落地」一节；量下来要治的不是子树，是那段 markdown 被重读的次数。
- **B（票 01 的第一步）先证实 `defer` 在生效**——`elements/markdown-text.tsx` 已经 `defer` +
  `unstable_memoizeMarkdownComponents`。**已量**：content 18k → 36k，`ScriptDuration` 377 → 592
  ms/秒（×1.57，内容 ×1.95），没有线性翻倍；真正的归属由同一场流的 CPU profile 给出（见下节）。
- **C（票 02）冷画那 176 ms**：渲染级虚拟化，或者更省事——老消息默认折成一行（工具卡今天就是这么
  做的，`message-parts.tsx` 的头写着为什么：内容根本不进 DOM）。
- **D（票 03）常驻的窗口**：给「更早」的 prepend 一个界，或虚拟化之后只留游标、条目按需取。
  这张票的第一步是先把「几百条的真会话」量出来——今天手上只有一条长消息，看到的几 MB 是噪声。

## 不用碰的

- 流式期间的样式/布局（0–5 ms/秒）、空闲会话（0.6 ms/秒）、收帧（几十 KB 封顶）。
- 「隐藏 tab 丢帧、回前台重读」：数据说这条路的收益也在「画」上（合批已经把它压到每 200 帧一次），
  而回前台要重新 hydrate 整场对话（那才是几 MB 的那部分）。要做也该先做 A/C。

## 票 01 落地（2026-09-30 第二次实测，真浏览器）

**改了什么**：`elements/markdown-text.tsx` 一行 prop —— `smooth={{ minCommitMs: STREAM_COMMIT_MS }}`
（60ms）。`defer` 与 memo 那两半照旧。

**这一次的机器与状态跟上面第一张表不同**（同一支 18k 脚本在这台机器上是 377 ms/秒，不是 19–132；
无头 Chromium、视口、当时机器上还有什么在跑都不一样），所以下面比的是**同一轮内的改前/改后**。

**为什么是这一行**。先按票里 B 那一步量：18,992 字的回答 vs 36,954 字，同一支脚本、同一个浏览器，
`ScriptDuration` 377 → 592 ms/秒（×1.57，内容 ×1.95）——**没有线性翻倍**，所以「每个 flush 重解析
整篇」这一条本身没被证实。接着开的 CPU profile 把话说清楚了：把 idle / program / GC（约 37%）摘掉，
**真正的工作里约 66% 是 markdown 解析**（`@assistant-ui/react-markdown` 30.0% + 它拉进来的
unist / micromark / hast 那几个包 9.8%），react-dom 5.4%，assistant-ui 的其余几层 8.1%，
我们自己的代码 0.8%。

也就是说：138 ms 那一刀确实是 markdown，但它**不是**「每个 flush 把整条消息子树重建一遍」——
消息子树很便宜，贵的是那段越来越长的 markdown 被**整篇重读**，而重读次数 = smooth 打字机的提交
次数 = 每动画帧一次（走查实测 52.2 次/秒；36k 那场 592 ms/秒除下来每次提交约 11 ms，与 profile
里 markdown 的占比吻合）。

**所以改频率，不改结构**。`useSmooth` 的 `minCommitMs` 正是干这个的：打字机照旧每帧往前推，但交给
渲染器的那个值——以及它引发的重渲染与重解析——每个区间最多提交一次。票里原来设想的「把正在流的那
条消息从列表里拎出来」因此**没有做**：它治的是子树，而子树只占 5.4%。

这也和票的判定规则接着：票说「若不翻倍，就按上面的形状把流式消息单独渲染」——那句的前提是「钱花在
消息子树上」，而 profile 说不是；所以这里按钱的实际归属改，改法与读法都写在上面。

**粒度是真的粗了，说清楚**：一次提交带的字数，走查测到中位 33 字（改前 8 字）。在跑得快的流上（脚本
这一场约 625 字/秒）读者看到的是「一串小跳」，不是逐个字符落下；按当初那台机器上真实 run 的节奏
（约 260 字/秒）则是两三个字一跳，看不出区别。要更平滑就把 `STREAM_COMMIT_MS` 调小，代价是解析次数
按比例回去。

**顺带**：`smooth` 落在共享的 `MarkdownText` 上，所以思考行正文的 markdown 也按同一个区间重建——
同一条理由（它同样是流式文本、同样整篇重解析），那一行还活着的预览是另一条路，不受影响。

| 场景（同一支脚本，3 次的中位数） | 主线程 task | 其中 JS | |
|---|---|---|---|
| 18k 字回答 / ~4,300 帧 | 528.5 → 275.2 | **377.2 → 178.2** | JS ÷2.1 |
| 36k 字回答 / ~8,250 帧 | 748.7 → 360.0 | **591.9 → 245.7** | JS ÷2.4 |

样式（11 ms/秒）、空闲 JS（0.7 ms/秒）两侧一致，布局反而 22 → 6 ms/秒；帧数与 `rafPerSecond`（56）
两侧相同，所以两条路是同一条。

**走查**（同一场 36k 的流，`MutationObserver` 记下屏幕上的字数每一次变化）：更新频率 52.2 → 14.0
次/秒（相邻两次的间隔中位 18.2 ms → 71.8 ms），每次更新带来的字数中位 8 → 33；走完的答案两侧都是
36,139 字，答案里的 `<p>` / `<strong>` / `<code>` / `.aui-md` **逐个数量相同**——markdown 照样是
markdown，没有被降级成一个纯文本节点。截图：`evidence/streaming-36k-before.png`、
`streaming-36k-after.png`。

**复现**：`evidence/README.md` —— 脚本、原始读数 JSON、截图，与每一步的命令。

**还没解决的**：剩 178–246 ms/秒，其中大头仍是那 14 次/秒的整篇解析。再往下只有两条路：把区间
继续放大（代价是文字更新的粒度），或者把解析变增量（已定稿的前缀与正在长的尾巴分两段画）——
后者与票 02 的虚拟化是同一条路上的东西，留到那时一起看。
