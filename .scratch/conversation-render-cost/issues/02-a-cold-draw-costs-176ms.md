# 02 — 冷画那 176 ms：老消息默认折成一行（或渲染级虚拟化）

**Status:** ready-for-agent
**Blocked by:** None

**要做的**：把**不是最近一两条**的助手消息默认折成一行（点击展开），或者接一个渲染级虚拟化
（只画视口附近）——两条路先挑一条：折叠那条小、见效直接、跟工具卡今天的手法同一套。

**为什么（2026-09-30 实测，真浏览器）**：一场已有会话**冷画一次**（50 条窗口里含一条 18k 字回答，
把会话从 DOM 拿掉再画回来）是 **176 ms 主线程，其中 JS 138.5 ms**、样式 13.5、布局 11.8，DOM
510 → 657 个节点。也就是说「打开一个已有会话」的价格几乎全在把那条长消息的 markdown + React 树
建出来。今天**窗口只约束「读多少」，不约束「画多少」**：服务端给一条 50 条的尾页（`page-size`），
而页面这边没有虚拟化依赖（`ui/package.json` 里没有），`Thread` 把窗口里的条目都挂进 React 树。

**要守的既有规矩**：

- `components/message-parts.tsx` 的头：工具卡为什么默认折叠、内容为什么不进 DOM——折叠这件事
  这套仓库已经有形状，别另发明一套；
- 折叠状态是**界面状态**，不是偏好：不落 `localStorage`（参考 `app.tsx` 里「哪个视图」那段为什么
  不持久化）；
- 服务端的窗口与 `?beforeSeq=` 不动（那是票 03 的地盘）；
- 动过 `ui/src/` 就要跑 `node scripts/dev.mjs --scripted` 并开浏览器走一趟。

**验收**：

- 同一场会话（同一条 18k 字回答）冷画一次的读数：`TaskDuration` / `ScriptDuration` 从 176 / 138 ms
  降到多少，写进 `spec.md`；
- `ui` 用例钉住可断言的那半（哪些消息默认折着、点击之后展开），并按惯例更新
  `test/ui.test.ts` 的 `EXPECTED_CASES` 与它上面那份账；
- 浏览器走查：展开/折叠一个长回答、滚动、发新消息之后「刚完成的那条」要是展开的；
- `npm run typecheck` / `npm run build` / `npm test` 绿。
