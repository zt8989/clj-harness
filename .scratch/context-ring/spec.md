# spec：上下文环读的是哪个数

**一句话**：对话页那个「上下文已用」的环由 `harness.edge.context`（记录折出来的读数）画，它答的是
「**上一发真调用**有多满」；环上的三色拆分，量的是**那一发被交给的数组**。

## 环的三样东西，各是谁

| 环上的东西 | 谁算的 | 说什么 |
|---|---|---|
| 百分比 | 厂商的 `prompt_tokens` ÷ **那一次调用**的窗口（`model/start` 的信封） | 上一发真调用有多满 |
| 三色拆分 | `harness.edge.pressure` 在那一发的 `model/start` 上拍下的**数组**（`anchor-face`），由 `context/shares` 量三桶字符数、`context/apportion` 摊到厂商的总数上 | 什么占了那一发（**估计**，文档里写明） |
| 摘要调用那一发 | **不算**（`harness.edge.context` 的 `own-calls`） | 环不能显示摘要那一发，见下 |

**只有 run 自己的调用算**（`ONLY THE RUN'S OWN CALLS COUNT`）：压缩的摘要请求是「一段对话 + 一句
指令」，不是这场会话自己能读到的量；不排除的话，一次压完环上会显示摘要那一发的数（2026-09-28 实测：
折了 308,071 tokens、环却停在 27%，看着像「压缩没生效」）。

**「那一发被交给的数组」只有一处规则**：系统消息在前，然后是对话（卡片已摘、压缩已折），最后是这一轮
run 自己的注入。这条例由 `harness.edge.pressure/messages-of` 拼，`context` **不重写一份**（它只量字符
数）—— 同一件事两个地方算，必漂，而这一票报的就是它漂了。两半读数出自**同一发**：百分比是厂商给那一发
的数，数组是那一发真的带出去的字节。

## 落地记录（2026-09-30，票 01 已落地）

**症状**：主人从浏览器报「上下文圈是黑的」（真会话跑动中）。

**根因两条，同在 `harness.edge.context`**：

1. `shares` 的「对话」桶取的是 `(:submitted run)` + `(:returned run)` —— ADR 0002 之后客户端只交
   **新消息**，老历史在会话里、不在这轮的行上，于是这一桶漏掉整段对话；`apportion` 再按这三桶（被漏算
   的）尺寸把厂商的总数摊下来，比例就飘了。真会话 `62f30024-…`（2026-09-30）：工具表 **55,405 字符**，
   环上画成 **68.7%**；那一发真正带出去的对话约 240 万字符，画成 24.8%。
2. `state->context` 只要日志最后一个 run 没有终结帧，就**整支不给 `:parts`** —— 理由是「run 的 message
   侧在终结帧之后一拍才落」。但等的是 **run** 的帧，不是那一发的：一发的 assistant 行紧挨在它自己的
   `model/end` **前一行**（真记录实测）。于是**每一个长 run 的全程**环上都没有分色，前端退回
   `UNKNOWN_HUE`（浅色主题里的近黑）——一跑几分钟，看着就是「圈是黑的」。

**修法**：三桶改成量**那一发被交给的数组**（band 在 `model/start` 上已经拍下了它，`anchor-face` 是它的
公开拼法），并去掉上面那两条 withhold 条件。于是：跑动中照画三色、比例回到真的、「整段对话」自然进来
（`replay/entries` 折出的对话 + 帧重建的返回侧）。

**落地后实测**（真会话 `a0621fce-…`，同一份日志，跑动中读；`dev/scratch_ctx_face.clj`）：

    usedTokens 477518 / windowTokens 1000000 = 48%
      system          1,531 tokens   0.3%
      tools          13,334 tokens   2.8%
      conversation  462,653 tokens  96.9%

    那一发被交给的数组：969 条消息 / 1,610,343 字符
    老口径（只数这一轮 run 的行）：136 行 / 261,513 字符

**顺手定的一件事**：「刚压过、还没发过新调用」那段**明确不改**（票里给的 (b)）。环显示的还是压缩前那一发
的数 —— 那是上一发**确实**那么满；另一条路（`compaction/end` 之后改显示这份对话自己的尺寸）会把一个
**估计**放到一个厂商的数下面，而这仓最老的一条规矩是两者要分得开（`:estimated` 就是为它存在的）。理由与
代码同源，写在 `harness.edge.context/state->context` 的 docstring 里。

**没动的一件**：`ui/src/components/context-ring.tsx` 的 `UNKNOWN_HUE`（分色还不知道时那支单色弧的颜色）
仍是 `text-foreground`。它现在只在**服务端说得出份额、却给不出数组**时出现，而这两件事出自同一发
（band 的 anchor，没有 anchor 就没有份额），所以那支近黑弧实际上到不了 —— 留着，是它本来就是「这个问题的
另一半没有」的兜底。

**改动落在哪**：`harness.edge.context`（`shares` / `state->context` / `records->context` /
`log-context`）、`harness.edge.pressure`（`messages-in` 公开、新增 `anchor-face`）、
`harness.edge.http`（`live-numbers` 与 stats 的折路把 face 传进去，折路只折一次 band）。前端**一个字节
没动**。

**代价，量过两轮（这一节是两个问题，别混成一个）**：

**一、一回调用里整份答案装配了几遍。** 原来三遍：`model/start` 一遍（那是要用的 —— 它答的是**上一
发**，见上），`model/end` **两遍** —— 推送（`live-numbers-slice`）与落库（`numbers-snapshot`）各自向
fold 要了同一瞬间的同一份答案。现在那个回调只装配一次，两个读者拿同一个值（`slice-of` / `snapshot-of`
是拆出来的两半算术）。`stats-test/the-numbers-are-assembled-once-per-model-fact` 数着钉住它：两发调用的
run，改前 7 次、改后 5 次（2 个 start + 2 个 end + run 收尾那一次）。

**二、量那一段对话要多少钱。** 第一版是**每次读**把整段逐条 JSON 编码一遍（`size-of`）：真会话上
**~65–100ms / 2 MB**（1500 条），而推送里每回调用要读两三次。第二版把这一步挪进 `pressure` 的 band
（`sized`）：**每条消息只量一次**，按 `[节点号 消息号]` 记住（节点号 = 记录行号；光用它不够 —— reasoning
节点是**插在**它所答的那条消息**前面**、共用同一个行号，实测这样记账会把 285 万画成 227 万再反过来：多算
四分之一，`pressure-test/two-nodes-under-one-id-are-still-two-sizes` 钉住这一条）。同一条真会话上：

    逐条量一遍（改之前每次读付的）   65–102 ms
    现在一次读（数已在手上）          1.2–1.4 ms

**它不是零，只是搬了家**：冷读整份记录（band 一边走一边记账，含折行本身）仍是 ~1.3s / 9177 行，而那份
记录里每条消息到现在只被编码过一次。两个数由 `dev/scratch_ctx_face.clj` 并排印出来，并且先对一次账：
**记账的数和「从零量一遍」的数必须一模一样**（真记录上是 `{:system 5311, :conversation 2283091}`，逐位相等）。

顺带结清的一条：`harness.edge.context` 从此**不碰数组**，只把 band 给的两个数按厂商的总数摊开；环读的地方
再也没有一次 JSON 编码。
