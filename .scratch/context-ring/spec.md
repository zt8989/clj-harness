# spec：上下文环读的是哪个数

**一句话**：对话页那个「上下文已用」的环由 `harness.edge.context`（记录折出来的读数）画，它答的是
「**上一发真调用**有多满」；而它下面那条三色拆分（system / tools / conversation）现在是错的 ——
**对话**那一桶只数了「这一轮 run 自己的消息」，没数整段对话。

## 环的三样东西，各是谁

| 环上的东西 | 谁算的 | 说什么 |
|---|---|---|
| 百分比 | 厂商的 `prompt_tokens` ÷ **那一次调用**的窗口（`model/start` 的信封） | 上一发真调用有多满 |
| 三色拆分 | `context/shares` + `context/apportion`：记录里三桶的**字符数**按比例摊到厂商的总数上 | 什么占了那一发（**估计**，文档里写明） |
| 摘要调用那一发 | **不算**（`harness.edge.context` 的 `own-calls`） | 环不能显示摘要那一发，见下 |

**只有 run 自己的调用算**（`ONLY THE RUN'S OWN CALLS COUNT`）：压缩的摘要请求是「一段对话 + 一句
指令」，不是这场会话自己能读到的量；不排除的话，一次压完环上会显示摘要那一发的数（2026-09-28 实测：
折了 308,071 tokens、环却停在 27%，看着像「压缩没生效」）。

## 读数（2026-09-30，真会话 `62f30024-…`）

环（`context/records->context`）：`usedTokens 612375`、`windowTokens 1048576`、**58%**，拆分

    system 39,812 （6.5%）   tools 420,867 （68.7%）   conversation 151,696 （24.8%）

记录里同一发的三样东西：

| 桶 | 记录里的真实尺寸 |
|---|---|
| 系统消息 | 5,007 字符 |
| 工具表（system 行信封上的 `:tools`） | **55,405 字符 / 53 个工具** |
| 这一轮 run 自己的消息 | 16 条、约 20k 字符 |
| 那一发真正带出去的对话 | **约 240 万字符**（厂商 612,375 tokens） |

三桶 chars 合计约 8 万，被 `apportion` 放大到 612,375 —— 于是**比例全飘**：工具真实不到 3%，
环上画成 68.7%；对话真实约 98%，画成 24.8%。

**根因**：`context/shares` 的「对话」桶取的是 `(:submitted run)` + `(:returned run)` —— ADR 0002 之后
客户端只交**新消息**，老历史在会话里、不在这一轮的行上（这两件事各自都对，凑在一起就是这一桶漏了
整段历史）。百分比不受影响（它是厂商的数），受影响的是「什么占满了窗口」。

## 另一个同一处的毛病（同一票里处理）

**刚压过、还没发过新调用**这段窗口期，环显示的是**压缩前**那一发的数（今天实测：会话已经折到
~104k est / 压力计 44%，环还停在 58%）—— 机制上没错（上一发确实那么满），但对读的人是误导：
那正是他刚按过「压缩」、想知道有没有用的时刻。
