# 04 — 请求进 model 信封，段机改判据

**What to build:** 这一轮**为这次调用写下、且在调用前就拼好的行**——system prompt、客户端的提问、
这次 run 派生的注入、以及「请求将发出时有多满」的压力读数——落在 `[model/start, model/end]` 里。
同时：轨迹 / `context` / `pressure` 共用的那台**段机**改成按 `step/start` / `model/start` 认。
从用户视角：读到一对 `model/*` 就知道这次调用手里有什么，不用自己攒。

**Blocked by:** 02（信封要靠逐条落盘才立得起来）。

**Status:** ready-for-agent

## 为什么

主人 2026-09-27 的第二句：「Model 的生命周期要包裹请求」。今天请求在 `model/start` **之前**、
回答在终帧之后，两头都在信封外。而写侧与段机**必须同票**：只搬请求不改判据，轨迹会把请求侧的行
算成「返回侧」（它今天按「第一条 `event` 之前 / 之后」切），读出来的形状就错了。

## 验收

- [ ] 边把请求侧的行**攒着**，等这次调用的 `:model/start` 到达时再写（信封必须先开）。
      只有一轮的**第一次**调用有这一段——第二次起，请求的增量是别的信封里写下的行。
- [ ] 段机的两条判据都换掉：**开段**（今天靠「run 的第一条 `message` 行」）与**哪一侧**
      （今天靠「第一条 `event`」）。新判据：**一次调用的请求侧 = 从它自己的 `model/start` 到它产生的
      第一条帧 / 消息之间的那些 `message` 行**。
- [ ] **旧记录仍按旧判据读**：两种形状都认，并有一条用例——同一场会话的两个版本（有信封 / 没信封）
      折出**同样的轮、同样的条目**。
- [ ] `harness.edge.context`（复用同一台段机）与 `harness.edge.pressure`（`messages-in` 取最后一段）跟着绿。
- [ ] `.scratch/trajectory-live/` 那个读侧补丁（「还没有被回答的调用」）在新的段机下仍然绿——
      它的前提是段，判据一换它就得跟着换。
- [ ] 代价如实写进文档：请求不再「发出前就在盘上」（差几毫秒）。
