# spec: hashline-edit（按锚点编辑，默认实现）

把 `pi-hashline-edit-pro`（MIT，RimuruW / Yugimob）的整套按锚点编辑搬进本仓：`read` 的每一行
带一个 4 字符锚点，编辑按锚点定位而不是按内容模糊匹配；被编辑过的行锚点保持、删掉的行锚点释放、
新行分配新锚点；锚点对不上就拒绝并**当场把当前区间连新锚点回给模型**，让重试不必先重读。

原版 `edit`（str_replace）保留为实现之一，由配置选择；本次的最后一票把默认切到 hashline。

> **本 spec 2026-09-15 被 `project-sidebar` 修订**：存储从"每文件一份 EDN sidecar + 原子写"改成
> **共用的 sqlite** `~/.clj-harness/harness.db`（界面元数据与锚点存储同库），建库与迁移链归
> `project-sidebar` 01。库装状态、文件装记录，配置（含本特征的 `:editing`）仍是文件——这条边界见
> `project-sidebar` 决策 2。受影响的是下面的「落盘持久化」、偏离表第一行与非目标里"不做跨进程锁"
> 那一条，三处都已就地改写。**票 02 因此新增阻塞边：`project-sidebar 01`。**

## 为什么要这一套

`old_string` 匹配有三个反复出现的问题，锚点各自解掉一个：

- **重复文本**：`old_string` 出现多次就得让模型自己想办法加长上下文，长出来的那一截又是一次猜测。
  锚点按行分配，天然唯一。
- **陈旧匹配**：模型凭记忆写 `old_string`，写错了却恰好命中别处，改坏了还不报错。锚点携带行校验和，
  文件在 read 之后变过就拒绝。
- **改完不知道下一笔怎么下**：str_replace 改完只回一句 "edited"，模型要改相邻行就得重读整个文件。
  改后的答复直接带上改动区间的新锚点。

## 决策

- **模式是配置，不是开关 API。** `~/.clj-harness/harness.edn` 的 `:editing`，可被绑定项目的
  `.harness/harness.edn` 逐键覆盖（复用 `harness.project/harness-config` 已有的两级浅合并）。
  每次调用现读，与 config.edn / harness.edn 的既有纪律一致——改配置不需要重启。

  ```edn
  {:editing {:mode :hashline        ;; :hashline | :str-replace
             :auto-read true         ;; write 之后附一段锚点读
             :anchor-grep true       ;; 用 anchor_grep 顶替内置 grep
             :require-path false     ;; replace/insert 必须带 path
             :strict-input false     ;; 拒绝可自动修正的输入而不是修完给 warning
             :boundary-dedup :on     ;; :on | :strict | :off
             :diff-context-lines 1}}
  ```

  **不放 config.edn。** 那份文件的形状是「三个旋钮，且只有三个」，写第四个进去是点名失败而不是悄悄
  丢弃；编辑策略是策略，归 harness.edn。

- **模式决定工具集的形状（**推翻 tool-toggles 的一条已裁定决策**）。** hashline 模式下这份工具表里
  **没有** `edit`；str-replace 模式下**没有** `replace` / `insert` / `anchor_grep` / `undo_last_change`。
  tool-toggles 明写「本特性之后，任何工具都不能再从工具表里消失」，理由是模型会把「被策略关掉」误读成
  「这能力不存在」然后去找 bash 绕路。本次推翻它，因为那条理由在这里换个方式成立得更好：

  - **拒绝要说得出替代品。** 调用一个本会话不服务的名字（陈旧的模型、重放的日志）得到的是指名拒绝，
    说的是「本会话按锚点编辑，用 replace；要改回去写 :editing {:mode :str-replace}」——能力去哪了、
    怎么拿回来，一句话说清。模型不会以为能力不存在，也不必自己摸。
  - **留在表里代价是实打实的。** 两个名字同时在场时，描述里必须花篇幅解释「哪一个在本会话是开的」，
    而模型看到 `edit` 就会用 `edit`；参考实现同样选择移除。
  - **实现面收窄到一处。** 这条豁免只归编辑模式解析器所有：它同时决定「服务哪张表」与「拒绝了怎么说」。
    `session-disable!` 那条通用轴一个字不动，它仍然是「可见但被拒」。

- **锚点表照搬，不自己造。** 4 字符、两位一段、按 tokenizer 实测筛过的 1353139 个条目，随仓带为压缩
  资源。造一份自己的 4 字符表很容易，但那样就丢了这张表唯一的意义——`anchor│` 在现代 tokenizer 上
  稳定切成三个 token。**这是 vendored 资产，MIT 许可，必须在 NOTICE 里署名 RimuruW and Yugimob。**

- **校验和换 SHA-256，其余规范化规则照搬。** 参考实现用 xxhash-wasm 的 h64；本仓不为一处校验和引入
  第三方哈希。契约的重心在规范化（去掉所有 `\r`、去掉行尾空白、超过 500 字节截断）与「同一行同一
  校验和」，不在具体摘要算法。取 SHA-256 的前 16 个十六进制字符。**两份存储互不相通，换了算法不产生
  兼容问题。**

- **落盘持久化（牛总裁定）。** 锚点归属与撤销记录跨进程重启保留——会话是长命的（jsonl 日志 + replay），
  重启后日志里的锚点还该能用。位置是 home 的元数据库 **`~/.clj-harness/harness.db`**（sqlite，与界面
  元数据同库；建库、`user_version` 上的前向迁移链与损坏隔离重建都在 `project-sidebar` 01），本特征占
  三张表：

  | 表 | 内容 |
  | --- | --- |
  | `hashline_snapshots` | 该文件上次被服务时的整文件校验和、行数、逐行锚点、逐行校验和（主键：文件绝对路径的 sha256） |
  | `hashline_undo` | 该文件最近一次 replace/insert 之前的正文、BOM、行尾、锚点、改后正文（主键同前） |
  | `hashline_sessions` | 本会话归属的事件折叠（session / allocate / free / minted / clear），按 thread-id 的 sha256 索引 |

  写入都在**一个事务**里（一笔编辑的临界区：推进归属 + 落撤销，要么都成要么都不成），不再需要"原子写"
  这套自制设施。损坏的处置从"改名单文件"变成"库级隔离重建"，说话的是库的日志行。**跨进程并发现在由
  sqlite 保证**——原先写的"不做跨进程锁"已推翻：参考实现引 SQLite 的第一动机仍然不成立（它是要解决
  一个本仓没有的多进程快照问题），但库已经在手，顺带得到的"两个写者要么串行要么报锁"比"两个写者静默
  损坏"好，所以从非目标里划掉。

- **会话归属仍然是 per-session 的。** 快照按路径存，归属按 thread-id 存：两个会话读同一个文件拿到不同
  锚点，互不踩。归属的持久折叠就是崩溃/重启后还能接着改的原因。

- **不新增日志行。** 编辑的每一次调用与结果本来就落在该 thread 的 message 行里（tool_call + tool 结果），
  锚点是可再生的推导物，不是新事实。工具生命周期沿用既有三相行，只多一个 outcome 取值。与
  tool-toggles / eval-self-extension 的「一份真相源」一致。

  **库的那三张表也是状态，不是索引**（`project-sidebar` 决策 2 画的那条线：库装状态、文件装记录）。
  它们装的是"现在这一行归谁、能退回哪一态"，不是"日志里发生过什么"：编辑的每一次调用与结果不镜像进库，
  它们属于那个 thread 的 jsonl；锚点与校验和也不是内容，是从源文件可再生的推导物。**唯一进库的文件内容
  是撤销记录里的那一份正文**，而且是刻意的、有界的——它按路径只保留最近一次、一次 `write` 就清空，它
  的用途是"把文件退回去"而不是"再放一份文件"。这条边界由 `project-sidebar` 01 的元断言守着（库里不得
  有任何装消息 / 帧 / 日志行的表）。

- **`write` 是锚点的边界，也是大文件的出路。** 一次 write 之后该文件所有锚点释放（内容已经与模型看到
  的不是一回事），撤销记录清除，`replace`/`insert` 下次要说「先 read」。同时**拒绝回显锚点的 write**：
  模型从 read 输出里连锚点一起复制进 content 是很自然的动作，写进去会污染文件、破坏后续 read 与 edit。

- **改后的答复是渲染出来的 diff，不是一句 "edited"。** `+锚点│行` / ` 锚点│行` / `-    │行` 三态，
  上下文行数由 `:diff-context-lines` 决定；被删掉的那行如果锚点还在同一份 diff 里活着，前缀位留空以免
  误导；边界去重剥掉的行以 `dedup│` 行显示且**不可当锚点用**。模型照着 `+` 与空格行的锚点就能下下一笔
  编辑，而不必重读。

- **一条消息里对同一文件的多次编辑合成一次提交。** 同一回合的多个工具调用在本仓是并发跑的
  （`harness.loop/drive!`），同一文件的两笔各自针对 read 时的同一个基态成立，后写覆盖先写且不报错——
  这是静默数据丢失，不是体验问题。因此：按解析后的目标路径分组、区间必须互不相交、全有或全无、最后一次
  调用给出合并后的 diff、一次撤销退掉整批；并且**按路径串行**，让两个会话也不能交错写同一个文件。

- **`anchor_grep` 走 ripgrep。** 沿用参考实现的 flags（`--json --line-number --color=never --hidden
  --glob !.git --max-count`）与 10 秒超时，另加指数级正则的拒绝。`rg` 不在 PATH 上是**点名失败**，
  不是静默降级成爬目录。

- **模式与工具有自省面。** 模型可以问本会话在哪个模式（`harness.editing/editing-mode`），prompt.md 的
  文件工具段落改成模式中立的说法并点出这个入口——prompt 是冻结的，按模式拼两套会破坏 prefill 缓存，
  而工具描述本来就是 per-thread 的，锚点语法归它们去讲。

## 与参考实现的有意偏离

| 参考实现 | 本次 | 为什么 |
| --- | --- | --- |
| SQLite（`node:sqlite` / `bun:sqlite`） | 共用的 home 元数据库 `~/.clj-harness/harness.db` | **这条 2026-09-15 改了**：原先写"本仓不引入数据库"，依据是"单进程拥有 home，不需要事务级并发"。`project-sidebar` 推翻了那个依据——一次编辑要在同一个临界区推进归属与撤销记录，事务是刚刚好的工具，而库已经在手（界面元数据要它），于是同库不同表 |
| xxhash-wasm h64 | SHA-256 前 16 位十六进制 | 不为一处校验和引第三方依赖；规范化契约不变 |
| `/hashline-config` TUI 覆盖层 + `config.json` | harness.edn 的 `:editing` | 本仓的配置面是文件；这里没有 pi 的 TUI |
| `pi.setActiveTools`（把内置 `edit` 从活动表里摘掉） | 编辑模式解析器决定服务哪张表 | 本仓没有扩展 API，但不需要：`harness.tools/specs` 本来就在组装时读 thread-id，模式只是它的又一路输入 |
| `tool_call` 钩子上的 `registerWriteHook` | hook-engine 已落地，`PreToolUse` 是现成的点（`{:tool_name :tool_input}`，exit 2 即拒绝）；但守卫**先长在 `write` 的工具体内** | 一个形态相关、只服务于 write 的改动，长在它服务的那个体里比长成一条钩子声明更好读；将来要挪是一次机械搬迁 |
| 多进程快照的 `withFileMutationQueue` | sqlite 自己的串行化 | 第一动机（多进程快照）本仓仍不需要，但库已经在手，"两个写者要么串行要么报锁"白拿 |

## 非目标

- 不改 `RunAgentInput`、不改 AG-UI 帧形状、不新增 jsonl 行种类。
- 不做多 harness 实例共享一个文件的并发编辑协议（库保证的是不写坏，不是"两笔编辑合并"）。
- 不把 `bash` 挡在编辑之外（锚点是编辑纪律，不是沙箱；真正的边界是审批 park）。
- `write` 的守卫长在工具体内，不长成一条 `PreToolUse` 钩子声明——它是 write 自己的形态约束，不是一条
  用户可以自行取舍的策略。hook-engine 的 `PreToolUse` 点已经存在（`{:tool_name :tool_input}`，exit 2
  即拒绝并回传原因），要挪过去是一次机械搬迁。
- 不给 `read` 加图片视觉：非文本一律点名拒绝（参考实现在这一点上是转交给 pi 的内置 read，本仓没有
  那个宿主能力）。
- 不做 `anchor_grep` 之外的新搜索工具。

## 验收主线

离线全量 `harness.test-runner` 全绿。**开发期 hashline 是 opt-in**（`harness.edn` 里显式写
`:editing {:mode :hashline}`），默认仍走 str-replace，因此逐票落地时既有断言不动；**最后一票翻默认**，
那时才改写既有断言，逐条列在那一票里。

端到端要覆盖三段真实路径（真实 HTTP 端点 + 脚本化模型）：

1. read 拿到锚点 → 按锚点改 → 改动区间的新锚点直接用于下一笔编辑（不重读）；
2. 文件在 read 之后被外部改过 → 编辑被拒且当场拿到新锚点 → 用新锚点重试成功；
3. 撤销把文件与锚点一起退回前一态；重启进程后（清内存、从 `harness.db` 重读）同一批锚点仍然可用。

### 01 落地记录

`src/harness/editing.clj` 是解析的唯一真相：`defaults` + 两级 `:editing` 块逐**键**合成，校验分两步
——未知键**两份文件都查**（被盖住的错字也要报，因为它是「从没打算被当真」的请求，不是一次合并的
输家），取值**只查生效结果**（否则项目层无法修好用户层写坏的值）。失败信息一律带**级别的名字与绝对
路径**：`harness.edn :editing 必须是 map，但 user 级在 <路径> 说的是 :hashline`。

`harness.project` 抽出了 `harness-edn-levels`（两个未合并的层 + 各自的文件路径），`harness-config`
改成它的浅合并消费者——**行为一字未动**，有测试钉住（`harness-configs-shallow-merge-is-untouched`）。
抽取的理由是「缺失是空配置、损坏是硬失败」这条纪律必须有**一份**实现：`harness.editing` 借的是它，
不是又抄一遍。

测试在 `test/harness/editing_test.clj`（13 tests / 184 assertions），并进了 `test-runner` 的
`test-namespaces`。用例覆盖：默认即 str-replace（回归保证）、逐键覆盖、未绑定只看用户层、每次现读、
三种坏配置各点名文件、未知键哪怕被盖住也报、七种取值各自的指名失败、以及「信息里说的合法值就是真正
接受的值」这条正反两面的对账。

### 03 落地记录

`harness.editing/families` 把「哪个模式服务哪些工具名」写成数据，`family-of` 从它派生，`served?` 是
唯一的判定——所以这机制**没有一件工具一行代码**：04–07 把锚点工具注册进来，过滤器自动就认它们。名字
不属于任何一家的工具（`bash` / `read` / `write` / `eval` / hooks…）恒被服务。

`tools/specs` 是唯一做减法的地方（`filter served?`），`tools/run!` 在执行缝的第二支做同样的判定，
消息由 `editing/unserved-message` 产出：**名字、本会话按什么编辑、替代工具、改配置的写法**，四件事各一
句。`.scratch/tool-toggles` 那条「工具永不从工具表消失」由此被推翻，理由写在 `families` 的注释里——
被拒的名字说得出替代品与恢复路径，比「可见但被拒」给的信息更多；而两个编辑工具同时在场的代价是实打实
的（模型看到 `edit` 就会用 `edit`，两套锚点归属随即打架）。

执行缝的顺序定成 **disabled → 模式 → 缺参 → 审批 → PreToolUse 闸门**。disabled 先于模式是
tool-toggles 要的顺序，含义也真实：会话自己扔的开关压过它继承的策略，所以答案先给「你自己能撤销的那
件」。但**第二件事实不被隐瞒**——`disabled-message` 在两个都成立时把两件都说了，并且**不做
「re-enable 就好」的假承诺**（对模式减掉的工具，re-enable 之后再打一次还是同一个答案）。

测试在 `test/harness/editing_mode_tools_test.clj`（13 tests / 49 assertions）。锚点那一族的断言用
**会话注册的替身**跑——本票要验的是过滤器，不是那四个工具的躯体；替身还顺带证明了「按名字生效、没有
per-tool 代码」这条性质。用例覆盖：默认表逐条不变、hashline 拿走 `edit`、str-replace 不服务锚点族、
两套模式按会话隔离（两个项目、同一个相对路径、只有一边能改到文件）、拒绝信息四个要素齐全且永不说
`unknown tool`、拒绝先于缺参与审批（不 park）、disable 压过模式且两件事实都说、以及坏配置在 `specs`
就炸而不是悄悄换一种编辑方式。

### 02 落地记录

**锚点表是 vendored 的，但不是照抄的。** 上游给的是 5.4 MB 的 JSON 字符串（gz 后 2.8 MB）；本仓带的
是**同一批锚点的位图**——`resources/hashline/anchor-table.bin.gz`，913,952 字节（gz 后 85 KB），因为
池的密度只有 18.5%。位图还正好是这些操作要的形状：「第 i 个锚点」是一次 select、「这个锚点排第几」
是一次 rank、「这个锚点存在吗」是一次 bit test，都不需要那些字符串真的存在。代价是**一个只有 1.35M
个成员的集合被压成了一个位置**，所以载入时必须逐项校验：长度、以及**整份未压缩字节的 sha256**
（`d3a1643f…`，配方写在 `harness.hashline.anchors` 的 docstring 里，任何人都能照着上游原件复算）。
对不上就点名失败，绝不放行成一个「更小的池」——那会让两行拿到同一个名字。

**一处与上游的有意不同，写在 docstring 里当断言钉住。** 上游把会话探针的种子混进**进程 id**，本仓只
用会话键。理由是这一票存在的意义：锚点要跨重启可用，而按 pid 播种会让同一个会话在两个进程里给出两套
锚点——那正好是「必须论证」而不是「可以测试」的那种性质。

**对齐的两种路径，来由不同。** 有 `:spans`（调用方知道自己干了什么）时逐槽位对齐，位置未动且校验和
相同的槽位**保留锚点**——这就是「把这一行换成它自己」不动名字的原因；没有 `:spans`（文件在盘上被别的
东西改了）时退回最长公共前后缀、中间全 mint。后者只会 mint 得比必要的多，永远不会留下一个不再描述它
那一行的锚点，且**刻意不是通用 diff**：真正的 diff 能在别人编辑器的改动里保住更多锚点，也会是这个
命名空间里最复杂的一坨，等有人真的需要再说。

**存储的形态是「四张表 + 一次事务」，且没有任何缓存。** 每次问都开库、问、关；没有 atom、没有 delay、
没有会话对象。所以**重启对这个命名空间是恒等操作**——重启后仍能用的原因不是「我们把状态存下来了并
加载回来了」，而是「答案从来就不在内存里」。这也是四张表的键长成那样的理由：快照按 `(path,
thread_id)` 而不是按 path，因为快照里装的是**锚点**，而锚点是**某个会话**铸的、别的会话不许用；按
path 单独存会把 A 会话手里的锚点递给 B。

**临界区在这里，不在工具里。** 一笔编辑的读 → 校验 → 写盘 → 推进归属 → 落撤销必须整段独占，
`harness.loop/drive!` 又让同一回合的工具调用并发跑——没有这把锁，同一文件的两笔编辑会各自读到同一个
基态、各自算出自己的新内容，后写的赢、**两笔都报成功**。库自身的隔离级别不解决它：事务让一次写原子，
不让一个「读-判-写」序列独占。所以 `with-path-lock` 按**canonical 路径**加锁（两种写法必须同一把锁），
`advance-with-undo!` 是落库那一半的唯一事务，中间的文件写由调用方在锁内完成。

**被这一票顺手加固的一处既有测试**：`db_test` 里两张写死的表名清单（`["projects" "sessions"]`）与
列清单，是那道「库不镜像日志」边界的执行机构——新表进库必须有人写下它是状态还是记录。四张
`hashline_*` 表现已逐条登记，含列清单；`prior_text` / `resulting_text` 的命名是**对着那条正则挑的**
（`content` 会撞上它），并且名字本身就说清了是文件文本、哪一侧。

**测试**：`hashline_anchors_test`（29 / 6618）与 `hashline_store_test`（14 / 66，含一个 8 线程 × 25 次
的真并发用例断言临界区不与自身重叠）。断言数被前者的 rank/select 往返（6000 条）与去重抽样拉高。

### 04 落地记录

**`read` 是同一个工具名、两副面孔，靠一条显式的 `:describe` 逃生口。** 用户要的是「覆盖内置 read」，
所以不做两个工具名。`harness.tools` 里加了 `tool-face`：一个工具的可变部分是 **description 与
parameters**，只有声明了 `:describe` 的工具才会变——今天只有 `read`。`:required`、`:run`、缝要读的
标记一律不动，于是**调用的行为**仍然只由会话决定，不由描述决定。

**文本闸门只长在锚点那一侧。** 二进制 / 图片 / UTF-16/32 / 目录 / 超 100MB 都点名拒绝，且每条都说出
**为什么**和**换什么办法**（`bash sed`、`iconv`）。但 str-replace 模式的 read **一个字都没变**：它读
二进制文件读得跟以前一样。理由不是「宽容」，是**必要性**——会出问题的只有锚点那一侧，因为只有它会
拿着一个解码成乱码的字符串去铸锚点。把闸门加到老路径上是没人要的行为变更。

**字节预算量的是「模型收到的东西」，不是行。** 超长行的行文只有两百来字节，量行本身会让页面在那一行
提前截断、把后面所有行的锚点一起藏掉，而模型根本看不到原因。所以先算出这一行要发什么、再量它。这条是
被测试逼出来的：最初的实现量行，于是「一行 6 万字 + 一行短行」的文件只回来 1 行。

**`serve!` 是「会话关于这个文件知道什么」的唯一写入口。** 文件没动过时（整文件校验和相同）直接复用
存下的锚点——所以第二次读同一个文件**根本不走锚点表**，且两次结果逐字节相同。文件动过时用**无 spans**
的对齐：不是我们的编辑，没人在说它是怎么变的，那就保住没动过的行、其余重铸。**写快照在出行之前**：
写失败就让调用失败且一个锚点都没露过面；反过来会先发出一批store 不认识的锚点，下一笔编辑会全数拒绝。
（06 把这段抽取成了 `sync!`，因为「把视图对齐到盘上的内容」不止 read 一个调用方——「重对齐」成了那条
共用入口，07 的 write 边界接的是同一条。）

**顺带一条被本票落地修掉的既有缺陷**：`approval-reason` 对**没有 path 的围栏工具调用**会去问
`project/out-of-bounds?` 一个 nil，然后在 java.io 深处抛 NPE，把真正有用的「缺参」信息盖掉
（`{"function":{"name":"edit","arguments":"{}"}}` 打到绑定会话上就是这条）。现在 `some?` 先挡一道，
缺参检查得以上报。

**测试**：`hashline_read_test`（19 / 116）。覆盖行形状、`│` 是 U+2502 而不是普通竖线、空文件仍有一个
可寻址的空行、翻页与 footer 给的 offset 首尾相接、超长行保留锚点、五类拒绝各点名、读两次锚点相同、
文件在脚下变过之后没动的行锚点仍在、两个会话读同一文件拿到两套锚点、绑定重根与越界 park 不受模式影响、
以及两副面孔的描述与参数各自正确。

### 04 追加：`served`——「拥有」和「见过」是两件事

**推翻 02 的一句话。** 02 落地时记的是「哪几行被真正展示给模型，是某一次调用的事实，不属于会话」。
04 落地时发现那条站不住：`read` 会翻页，**mint 出来的锚点对应的是真实存在的行，但模型没看过**。让一笔
编辑用其中一个锚点，等于让模型去改一行它从没见过的东西——正是这一整套要消灭的那种「猜」。所以
「见过」必须被记下来。

**它是什么、不是什么。** `hashline_snapshots.served` 是一个**集合**（存成 JSON 数组），装的是
该会话**确实收到过**的锚点。两次推进：`advance!` 把它与**存活下来的锚点求交**（对齐的结果，剪掉已不
存在的），`mark-served!` 只**加**（编辑回给模型的那几行）。一笔编辑两步都做，顺序是「先推进、再标记」。

**为什么是一条新的迁移级而不是改 02 的 DDL。** 链是 append-only：02 那一步已经在一些库里跑过了，
改它会让那些库握着一份 harness 不再认得的 schema。所以是 `ALTER TABLE … ADD COLUMN served TEXT NOT
NULL DEFAULT '[]'`，`user_version` 到 3。

**顺带记一条 Clojure 陷阱**：`(distinct a-set)` 在 1.12 里会抛 `nth not supported`——1-arity 的
`distinct` 用 `nth` 解构参数，对集合直接炸。集合本来就是去重的，`vec` 就是全部需要的转换。

### 05 落地记录

**一笔编辑是一个六步流水线，`harness.hashline.replace` 就是这六步的顺序**：解析载荷（`edit/parse`）
→ 用锚点定文件（`target-path`）→ 校验盘上的文件仍是模型看过的那个（`verify!`）→ 算出新正文与新锚点
（`apply-range` + `anchors/align`）→ 落撤销、写盘、推库（同一个临界区里）→ 回一张 diff。命名空间
docstring 写的就是这个顺序，因为**顺序本身是这一票最容易写错的东西**（写盘与落库谁先、撤销记录在写
盘前还是写盘后，每一步都有个错法会让模型拿到一条不存在的锚点）。

**「锚点即地址」的推论：`path` 不是必填。** 一个锚点在一个会话里只属于一个文件，所以文件是从
`remove_from` **推导**出来的，工具表里也没有 `path` 这个参数（`:require-path true` 时才有，给别人显式
点名的场合用）。给了 path 就**必须与锚点归属一致**，不一致指名报错——「点名了 A 文件却在改 B 文件的
行」正是这条检查存在的理由。

**改后的答复是这一票的重点，也是一次真实的 bug 现场。** 答复不是 `edited`，是改动区间的当前状态：
上下文行 + `+` 行 + `-` 行，每行带当前锚点；`-` 行的锚点列**留空**（那些行没了，印一个锚点在旁边就是
印一个已经不再指向任何东西的名字）；边界去重剥掉的行单独一行 `dedup│…`。这个形状本身就是「不必重读」
的出口，有用例直接钉住：拿答复里 `+` 行的锚点发起第二次 `replace`，成功（`the-anchors-in-the-answer-
are-immediately-usable`）。

**`render-diff` 返回 `{:text :shown}`，多出来的那个 `:shown` 是必须的。** 新铸的锚点是「已拥有但没被
任何人看过」，`served` 集合（04 追加）不补上就会让**下一笔**编辑被「这一行你从没看过」拒绝——也就是
说本票的核心验收会以「第二笔失败」的形式暴露。谁算「看过」只有渲染那一步知道（它就是印出锚点的那一
步），所以在别处再算一遍等于维护第二份索引区间清单。所以这个集合跟着文本一起回来，`mark-served!` 紧随
其后。

**顺手修掉两处真缺陷**（都是测试逼出来的，不是重构）：

1. **`edit/parse` 把调用方的 warnings atom 顶掉了。** 它内部 `(let [warnings (atom [])] …)` 把
   `replace/perform!` 传进来的那个遮蔽了，于是「已修正你手抖的这五处」的提示**从来没到过模型面前**——
   自动修正悄悄发生了，而模型只看到一次成功的编辑。现在 `:warnings` 由调用方传进来（不传才新开一个），
   `the-slips-are-fixed-and-reported` 钉住。
2. **`replace` 的 read 与 `perform!` 的 read 不是同一次读。** `serve!` 收 BOM 一起算校验和、`perform!`
   走 `files/read-file` 把 BOM 去掉了，于是**任何带 BOM 的文件，第一次编辑都必然被拒为「漂移」**——一条
   关于没人动过的文件的拒绝。现在 `read!` 也走 `files/read-file`：一份文件一次读法，两处比的必须是同
   一批字节。

**一处刻意的措辞分叉：`not an anchor` 与 `not read` 是两个答案。** 都在 `unresolvable!` 里，判据是
`anchors/anchor?`：名字不在锚点表里（`Hasu` 是 4 个字符但表里没有）说明它**从来不是锚点**——「去 read」
在这里是把模型送回去重复同一个错误；而一个真实的、本会话不持有的锚点，read 恰恰就是解药。两条都拒绝，
只有一条值得重试。

**一条被测试修正的既有用例**（不是被实现迎合的测试）：`a-context-row-is-usable-too` 原先按**位置**取
第一条上下文行，而 `:diff-context-lines` 默认 1、被改的行**前面**也有一行上下文——于是它拿到的是
`alpha`，却断言改完之后文件是 `GAMMA2`。用例说的是「上下文行的锚点可用」，那就该**按内容**取那一行；
按位置取是在断言行序，只是没说出口。

**区间反转是警告不是拒绝**（`resolve-range`）：比的是**锚点数组里的位置**，不是锚点的池编号——池编号被
刻意设计成与行序无关，拿它比大小等于比较两个故意无关的数。这条错法在实现里真实存在过，症状是三帧
之外的 NPE（span 的键名 `:start/:end` 与 `align` 读的 `:old-start/:new-start` 不是一套）。

**测试**：`hashline_replace_test`（30 / 99）。覆盖真值表（`[]` 删除、`[""]` 空行、单行/多行/首尾、
纯插入的两种写法）、答复形状（`+` 行有锚点、上下文行有锚点、`-` 行留空）、**核心验收**（不重读接着
改）、`:diff-context-lines 0`、边界去重三态、五类自动修正各一条 + `:strict-input` 全拒、NUL 拒绝、
清空文件拒绝并指向 `write`、畸形入参逐条点名、未读/未展示/漂移三种拒绝、no-op 不写盘且保住撤销历史、
撤销记录的 BOM 与行尾往返、以及工具描述里那四件必须说清的事。

**给 06 的地基**：05 只做「输入合法且一切正常」的路径，四种拒绝都只是一句指名的话（`verify!` 的
漂移 / 未展示，`unresolvable!` 的不是锚点 / 不属于本会话），四个 `:reason` 分好等 06 往上面加东西。

### 06 落地记录

**拒绝是一次交付。** 这是本票的立论，也是它为什么值得单独一票：锚点方案胜过 `old_string` 的地方不在
「改得成」——两套方案都改得成——而在**改不成的时候**。`old_string` 答「找不到」，模型只能重读整个文件；
这里拒绝**把刚才谈的那些行连同它们现在的锚点一起带回来**，而且那些行算「已展示」，所以下一笔直接成功。
四条用例把这条钉死：漂移后重试、只挪动了别处的行、未展示的行、以及兜底命中。

**漂移与未展示是两种病，两副药。** 漂移（`drift`）说的是**文件**变了——某几行的校验和对不上，或者行数
变了；未展示（`unseen!`）说的是**模型**没看过那几行（被截断的 read 铸了锚点却没发出来）。前者用
`serve/sync!` 把会话的视图重对齐到盘上的内容，再把区间的行按**新锚点**印出来；后者视图本来就是对的，
印出来就是。两者共用一个 `range-rows`，因为「把我说的这几行连名字一起给你」只有一种形状。

**漂移的信息分开报两件事**：「哪几行对不上」（一行就点名，多行给区间与条数）与「行数变了」（`it now has
6 lines, it had 8`）。它们是两个事实——某行被编辑了，和整个文件被增删过——合成一句话会让模型在「邻居挪了
位、但我要改的那行没变」时以为自己看错了行。

**超长区间只印前 40 行**（`heal-rows`），并明说「区间一直到第 80 行，`offset=` 看剩下的」。这是刻意的
取舍：那条拒绝要能**读完**才有用，而八十行的一堵墙读不完；何况那么长的区间本来也没法一笔重试完。

**兜底（`locate` 的 `:else` 分支）为什么这么窄。** 场景是「归属表丢了、模型手里还捏着过期锚点」：视图还
认这个锚点、归属表不认、而调用方**说了文件名**。此时用锚点在视图里的位置找到那一行，再要求这一行的内容
在该文件里**唯一**——两条内容一样的行意味着这个锚点可以指两处，而猜是哪一处正是这套机制要消灭的东西。
所以「唯一定位」执行（并明说这是兜底，`claim-anchors!` 把归属补回去，免得下一次又要兜），「不唯一」和
「找不到」都回「去 read」。兜底命中时那句「ownership table」是给日志看的，不是给模型看的——它是**这条
路径不寻常**的证据。

**顺手修掉 05 的一个真 bug，而且它很重。** `mark-served!` 原来是**整列覆盖**（`SET served = ?`），而
调用方给它的是**这次答复印出去的那几行**——于是任何一次编辑之后，凡是没被那几行覆盖到的行（也就是模型
刚读过的绝大多数行）全部变成「从没展示给你」，下一次编辑必然被拒。05 的 `advance!` 那边写着「intersect」，
所以读代码看不出来；症状是「编辑一次之后什么都改不了了」。现在它在事务里读旧值再求并集。用例
`an-edit-does-not-unshow-the-lines-it-did-not-touch`（在 05 的命名空间里，因为它属于那笔编辑）钉住。
同一处还补上了**交集**那一半的实做：`advance-on!` 原先只是把调用方给的集合照抄，`align` 已经把
`:survived` 剪过一遍所以当时看不出问题，但「存下来的集合永不收缩」这件事不该依赖上游剪过——现在它自己
剪。

**测试**：`hashline_refusals_test`（12 / 65），另加 05 的两条（未展示行带锚点回来、编辑不取消已展示）。
覆盖：漂移后重试端到端（**本票的核心**）、只挪动别处、漂移的两类措辞、超长区间不刷屏、拒绝信息里没有
内部标识（哈希 / 指针 / 表名 / 异常类名）、未读过的文件、不是锚点的名字、兜底命中的三种结局（唯一 /
不唯一 / 无视图）、以及「七种拒绝都是信息不是崩溃，而且拒绝完会话还能用」。

**给 07 的地基**：`forget-file!` 与 `clear-undo!`（02 落地时就写好了）现在有第二个调用方了——
`sync!` 这条路让「视图重对齐」有了一个共用入口，07 的 write 边界接的是同一条。

### 07 落地记录

**一次 write 之后，那个文件与模型手里的锚点没有关系了**——不是「大致不对」，是锚点命名的是**行**，而行
已经是别的行了。所以成功的 write 做三件事：释放该路径在本会话的**全部**归属、清空该文件的撤销记录、
为刚写下的内容发一套新锚点。`store/forget-file!` 是**总的**释放而不是「写这一笔涉及的那些」：留下来的
锚点会一直被算作「已拥有」，对一个再也用不上它们的会话来说那是净损失，而且旧的视图还在的话，下一笔
编辑会拿一个已经不存在的文件去校验。

**`:auto-read` 才是这一票的重点。** 刚写完一个文件，模型的下一手多半是改它——而 write 恰好把锚点收走
了。让它为此再 read 一次，是为一个这通调用**当下就能给**的事实付一次往返。所以成功的 write 附上该文件
开头的带锚点行，并把这些行登记为「已展示」（与 read 同一套登记）。默认 20 行（`auto-read-lines`），
尾部照旧给 `offset=`。`read` 出来的这套锚点是**新铸的**——因为释放发生在读之前：顺序反过来就会把
write 刚刚作废的那一套又读回来。

**回显守卫是 write 自己的形态约束，不是一条策略。** 模型从 read 输出里复制内容，把 `锚点│` 前缀一起抄
进去是**很自然**的动作。真写进去，文件被污染还不是最糟的——之后每一次 read 都会把 `Hasu│` 当成正文再
发一次锚点，**错误会自我繁殖**。所以拒绝，并点名第几行的哪个锚点。它长在工具体里而不是长成 PreToolUse
声明：这是锚点模式下 `write` **是什么**，不是「有人可能想配成别的样子」。（钩子点在那儿
——`{:tool_name :tool_input}`，exit 2 即拒绝且 stderr 回传——真要挪过去是一次机械搬迁。）

**守卫窄，是因为误拒更贵。** 判据是「行首是 4 个字母数字 + `│`」**且**「那 4 个字符是这个文件在本会话
服务过的锚点」。前半条挡住普通竖线开头的正文，后半条挡住别的文件的锚点与从没见过的四字母。认错一个
回显，代价是文件里多一行垃圾；拒掉一段正文，代价是模型写不进它要写的东西——后者严重得多。用例里四条
「不是回显」的场景与一条「是回显」的控制组并存，就是为了让「守卫根本没生效」不可能通过。

**写盘统一走 canonical 路径。** 库按路径记账，所以同一个文件的两条写法必须在铸锚点之前合成一个键；
否则模型会拿到一套「换个写法就失效」的锚点——一个幻影，而且看上去像锚点机制在骗它。`serve/sync!`、
`serve/read!`、`replace/perform!` 与 `write/perform!` 的入口都过 `store/canonical`，用例
`both-spellings-of-one-path-share-one-set-of-anchors` 钉住。这条是被测试的**报错形状**逼出来的：测试用
`(str file)` 去问库，得到 nil，看起来像「没有那一行」——macOS 的临时目录还是走 `/private/var` 符号链接
的，所以连 `(io/file tmpdir name)` 都与库里的键不同。三个测试命名空间的 `path` 辅助函数因此都改成了
`store/canonical`。

**`write` 是第二个按模式换面孔的工具。** 参数不随模式变（还是 `path` + `content`），但描述必须变：一个
没有锚点的会话不该被读一段「写完之后锚点会怎样」。`tool-face` 的 docstring 从「只有 read」改成「read 与
write」，这就是那条逃生口的第二条用例。

**测试**：`hashline_write_test`（15 / 53）。覆盖释放（旧锚点失效且编辑它们得到「先 read」）、`auto-read`
补发新锚点、清撤销、写到新文件、回显拒绝（含四条非回显的控制）、被拒的 write 三者皆不变（文件 / 归属 /
撤销）、`auto-read` 的输出体积与 footer、`:auto-read false` 的措辞、自动读失败时 write 仍报成功、两条
路径写法共享一套锚点、越界照旧 park、str-replace 模式一字未变、以及两套模式下描述各自正确。

### 08 落地记录

**撤销的单位是「一次调用」，不是一行。** `replace` 可能重写了九行，模型要拿回来的是「它开口之前的那
个文件」。所以工具叫 `undo_last_replace` 而不是 `undo`——名字把单位说清楚，也把「它有多浅」说清楚：
一个文件只留最近一次编辑（一行记录），一次 `write` 清掉（07），再撤一次得到的是「没有可编辑的」。

**它拒绝，而不是覆盖。** 这是本票真正的立论。记录里同时存着改前与**改后**的正文，执行前拿盘上的内容
与「改后正文」比：不一致说明这次编辑之后文件又被改过（人在编辑器里存的、另一个工具、一条 bash），
此时**什么都不做**、**记录保留**、并说明「文件已经不是那次编辑留下的样子了，硬退会把后来的改动一起
吃掉」。撤销功能唯一能造成破坏的地方就是这里，所以这里写得最细。

**撤销要把锚点一起还回去，不只是文本。** 模型撤销一笔编辑，通常是为了**改一笔别的**，手里拿的还是撤
销前那批锚点。只还原文本而让库里那套锚点留着，得到的是一个「锚点描述的正是刚刚被撤掉的那个状态」的
文件——模型下一笔必然被拒。所以记录里多了 `served`（哪几个锚点模型见过）与 `mode`（权限位），于是：

- 迁移链加一级（v3 → v4）：`ALTER TABLE hashline_undo ADD COLUMN served TEXT NOT NULL DEFAULT '[]'`。
  又一次 append 而不是改 v2 的 DDL——那条已经在别人库里跑过了。
- 权限位以前根本没记（`mode` 列一直空着）。现在它记的是 `mode-bits` 编码出来的一个整数，撤销写回的是
  **编辑当时捕获的那一份**，不是文件此刻碰巧有的那一份——「还原」就是还原。
- `served` 不可从锚点推导（翻页 read 会铸出没展示过的锚点），所以和视图那边同理，必须一起存。

**锚点回填用 `advance-on!` 反向走**（`store/restore!`），而不是「把这些锚点写下去」：记录里的某个锚点
可能在它被释放之后**已经铸给别的文件了**，此时那句带主键的裸 INSERT 会拒绝——这正是想要的。用例
`an-anchor-that-moved-elsewhere-refuses-the-undo` 手工把锚点塞给另一个文件来构造这个局面，得到的是
「这个编辑已经退不回去了」而不是一次双占。`restore!` 的 `:probe` **不回卷**：那些锚点已经发出去过，
从旧 probe 重铸会给两行铸出同一个名字。

**顺手修掉 06 留下的一处路径 bug，而且是模式的核心路径。** `perform!` 里那句「`path` 与锚点归属不一致
就拒绝」拿**原始参数**去比归属（`g.txt` vs `/proj/g.txt`），于是 `:require-path true` 的会话**每一次
指名文件的编辑都会被判为不匹配**——恰恰是这个模式存在的意义所在的写法。现在先把 `path` 按会话解析再
比较。用例 `a-path-that-agrees-with-the-anchor-is-not-a-mismatch` 钉住三个方向（同名通过、异名拒绝、
缺省在 `:require-path` 下拒绝）。之所以一直没被发现，是因为在此之前所有用例都不带 `path`。

**测试**：`hashline_undo_test`（15 / 59）。覆盖往返（逐字节、BOM、CRLF、权限位）、锚点回来后可用
（**本票的核心**，且撤完还能拿答复里的行接着改）、撤两次、没编辑过、`write` 后、**被改过之后拒绝且
三者皆不变**、被删的文件从历史恢复、`path` 缺失与空串、另一个文件不受影响、记录跨重启（直接问库）、
锚点被别的文件占用时拒绝、越界照旧 park、以及描述必须说清的三件事。

### 09 落地记录

**为什么必须成批，而不是「按顺序一笔一笔跑」。** 一个回合的工具调用是并发跑的（`harness.loop/drive!`），
两笔编辑各自对着「read 时的那一份基态」成立、各自算出自己的新内容：谁后写谁赢，先写的**无声消失**，
而且**两边都报成功**。这不是锁能解决的问题——两笔各自都是对的，错的是把它们分开执行。所以同一条消息
里、解析后目标路径相同的 `replace` 合成一批：**对着批前基态校验**、区间必须互不相交（重叠是**拒绝**，
不是「谁先谁后」的谜题）、合并成一次写盘 / 一次推进 / 一次撤销。

**谁来执行，由「看得见整个回合」的地方决定。** 工具只看得见自己那一次调用，所以 `harness.tools` 在
`register-turn!` 里把整个回合的调用算成一张计划表：同组里**最后**那一次执行（模型的最后一条结果就是它
的），前面几次立刻回一句「已并入本批第 N 笔」，一个字节都不碰。**没有任何一次调用需要等另一次**——这是
刻意的：如果让第一笔去等后面几笔，那么后面任何一笔被拒绝、被审批 park、或者干脆没跑，第一笔就会挂住，
而 park 的那一笔的 tool message 是要等到 resume 才落地的。

**计划表算的是「这次调用改哪个文件」，不是「这次调用合法吗」。** 第一版让它走完整的 `edit/parse`，结果
是**参数畸形的调用根本不进批**——而那正是最需要被报出来的调用。现在它只问一个问题（哪个文件），用
`edit/bare-anchor` 宽松地取锚点，取不到再看 `path`；畸形载荷照样成批，然后在批里被指名拒绝。用例
`one-bad-edit-refuses-the-batch-and-says-which` 与 `a-call-that-cannot-be-targeted-is-not-in-the-batch`
各自钉住一半：**能定位但载荷坏的**进批并整批拒绝（说清是第几笔），**定位不到的**（锚点不是锚点、
没有 path）自己跑、自己报错，不拖累别人。

**重叠判据是半开区间**，`(>= end next-start)`：`[0,2)` 与 `[2,4)` 只是首尾相接（「在这一行前后插入」
就是这种形状），不算重叠。第一版写成 `(>= (:end range) (str/start range))`——拿同一个 range 跟自己比，
于是**任何两笔都被判重叠**；用例里 `two-edits-in-one-message-are-one-commit` 立刻炸了。

**`render-diff` 重写成「spans 序列」的形状**，因为一批有多个改动区。现在的规则是：一个游标从前往后走，
每个 span 印出「光标到它起点之间的上下文（超出 `:diff-context-lines` 的用 `+   │...` 收尾）→ `-` 行 →
`+` 行」，最后一个 span 之后再印一段尾部上下文与尾部的省略行。**`shown` 集合终于和渲染走同一段循环**：
之前是第二个 `map`，两处区间必须手工保持一致——而它正是「模型能不能用这个锚点」的判据，错一次就是
「下一笔被拒」。重写时确实漏了一次（只把上下文行算进 shown、漏了 `+` 行），被
`the-anchors-in-the-answer-are-immediately-useful` 当场抓住。

**一次撤销退整批**：撤销记录是**批前正文 + 批后正文**，所以 08 那边一个字都没改就成立。

**测试**：`hashline_batch_test`（11 / 51）。覆盖一次提交（两笔都落地、前一笔不渲染 diff、后一笔的 diff
里两处改动都在）、合并后锚点可用、一次撤销退整批、no-op 批不写盘且保留撤销历史、重叠整批拒绝、
某笔载荷坏整批拒绝并点名、未展示的行整批拒绝、不同文件各自独立、定位不到的调用自成一体、**并发用例**
（三笔并发发起，断言三处都改了、行数不变、库里锚点与文件一致、一次撤销全回来、只有一笔报「写了」），
以及描述里必须写明的三件事。
