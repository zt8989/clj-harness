# 08 — `undo_last_replace`：把文件**和锚点**一起退回前一态

**What to build:** 一次 `replace`（或 `insert`）之后发现改错了，一条命令退回改之前的状态：
**正文、BOM、行尾、文件权限，以及那一批锚点**。撤销的单位是「一次调用」，不是一行——这也正是它叫
`undo_last_replace` 而不是 `undo` 的原因。

**按文件、单层、跨重启。** 记录按路径存（05 已经写下），所以在一次进程重启之后仍然能撤销；一个文件只
保留最近一次编辑（参考实现的 `undo` 表就是按 path 主键的单行）；一次 `write` 会清掉它（07）。
批里的多笔编辑算**一次**记录，一次撤销退掉整批（09）。

**撤销要能拒绝。** 撤销记录里同时存着改前的正文与**改后的正文**。执行前拿当前磁盘内容与「改后正文」
比：不一致就说明这次编辑之后文件又被改过（人手动改的、另一个工具改的），此时撤销**什么都不做**并说明
原因，记录**保留**。硬退回去会无声地吃掉别人后来的改动——这是撤销功能最容易造成的破坏。

**文件被删了怎么办。** 撤销记录里有改前正文，所以删掉的文件可以被恢复，并说明是从撤销历史恢复的。
这是撤销记录天然能提供的能力，不额外为之设计。

**Blocked by:** 05（记录的写入在那一票），06

**Status:** ready-for-agent

- [ ] `path` 必填，空字符串与缺失各给一条指名错误
- [ ] 没有记录时：明确说「这个文件没有可撤销的编辑」——把「没东西可退」和「退失败了」分开
- [ ] 一次 replace 后撤销：正文**逐字节**回到改前（含 BOM、CRLF/LF、文件权限位）
- [ ] 撤销后锚点回到改前那一批，**并且立即可用于下一次编辑**（端到端：改 → 撤销 → 用撤销前 read 的
      锚点再改一次，成功）
- [ ] 撤销后撤销记录被删除，「再撤一次」得到的是「没有可撤销的编辑」
- [ ] 编辑之后文件又被改动过 → 撤销**被拒绝且什么都没改**（磁盘内容、锚点归属、记录三者不变），
      信息说清「文件在编辑之后被改过，因此没有退回，记录保留」，并建议先 read 看清现状而不是硬撤
- [ ] 编辑之后文件被删除 → 撤销**恢复该文件**，并说明是从撤销历史恢复的
- [ ] 记录跨重启可用：清掉内存、只读库，重启后仍能撤销（与 02 的快照同一张库、同一个事务）
- [ ] 一次 write 之后撤销：报「没有可撤销的编辑」（07 已清空）
- [ ] 撤销只影响目标文件：另一个文件各自的撤销记录不受影响
- [ ] 相对路径按会话绑定重根；越界路径照旧 park 等审批
- [ ] 工具描述说清：只退最近一次 replace/insert、write 会清掉、文件被改过时会拒绝而不是硬退
