# 01: 一行本身长得像 JSON 数组时，`replace` / `insert` 写不进去

**Status:** needs-triage
**Blocked by:** None

**事实（2026-09-30 实测）**：`harness.cap.hashline.edit` 的 `replacement_lines`（`insert` 的 `:lines`
走同一个门，`insert.clj:78`）有一条**刻意的宽松**——整个字段、或**任何一个元素**，只要「去空白后以 `[`
开头、以 `]` 结尾、且能解析成字符串数组」，就把它**解包**成若干行（`.scratch/hashline-edit/spec.md:605`
写着这条宽松是为「整个 JSON 数组塞进一个元素」那种手滑准备的）。

于是**一行内容本身长得像 JSON 数组时，它没法被原样写进去**：

| 元素 | 现在会变成 |
|---|---|
| `"[]"`（去空白后是 `[]`） | 解包成**零行**——这一行**消失** |
| `"[\"a\",\"b\"]"` | 解包成**两行** `a`、`b` |

两次都会往 `warnings` 里放一句（`Unwrapped a JSON array pasted into ...`），但**写下去的字节和调用方要求
的不一样**，而调用方是模型：它多半不会去读那句警告，甚至可能看不见（答案里没有）。

**怎么发现的（可复现）**：给一个 Clojure 源文件加一行 `  []`（一个空 arglist）时，`replace` 的
`replacement_lines` 里那一行没落进文件，工具回的就是那句话；`insert` 也一样（同一处，先「No change」，
再被解包吃掉）。本次是 `harness.test-runner/var-timing?` 与 `timing-flag` 各丢过一次 `[]`，最后用 `sed`
手工补上才把 07 写完。

**要定的**（所以是 needs-triage）：是**收窄**这条宽松，还是给它留一个「这真的是字面量」的出口。无论哪条，
**不许静默改内容**：

1. 空数组没有第二种读法——`[]` 作为**元素**不可能是「删掉这一段」的意思（那是整个字段的用法）⇒ 元素解析出
   **空数组**时**具名拒绝**，而不是解包成零行；
2. 或者只在解析出 **≥2 个字符串**时才解包（`["a"]` 与 `[]` 留作字面量）——但那会让 `["a"]` 的含义随元素
   个数变化，比第 1 条更需要先写下来；
3. 或者只在**整个字段**是一个字符串时才解包（元素级的解包整个撤掉）——代价是那条手滑修复回到「报错」，
   而 spec:605 说那是真实发生过的。

**验收**

- [ ] `replacement_lines` 的元素字面量 `"[]"` 与 `"[\"a\",\"b\"]"` 要么**原样写进文件**，要么被**具名
      拒绝**——不能悄悄丢掉、也不能悄悄拆成别的行数
- [ ] 既有的两个宽松场景（整个字段是一个 JSON 数组字符串；一个元素里粘了一整个数组）仍有用例钉着
- [ ] `harness.cap.hashline.edit-test` / `insert-test` / `replace-test` 与全量套件绿
