# 09 — 同一回合的多笔编辑：合成一次提交，或者一次都不提交

**What to build:** `harness.loop/drive!` 把**同一个回合里的多个工具调用并发**跑在各自的线程上。这在
锚点方案下会静默丢数据：同一个文件上的两笔编辑各自针对「read 时的那一份基态」成立，各自算出自己的新
内容，谁后写谁赢，先写的那一笔**无声消失**，而且两边都报告成功。参考实现用「按助手消息成批」来堵这个
洞，本票照做，并且额外按**路径串行**，让两个会话也不能交错写同一个文件。

**批的语义（全部落在工具层，不改 `loop` 的并发模型，也不新增日志行）：**

- 同一回合里、**解析后目标路径相同**的 `replace` / `insert` 调用合成一批。**批的单位是消息**，
  不是整个回合——模型下一轮看到 diff 之后再改，是新的一批。
- 批内每一笔都对着**批前的基态**校验（不是对着前一笔的结果），合并时按位置降序拼装。因此
  「两笔都改到同一行」是一个**可检测的错误**，而不是一个先后顺序的谜题。
- 区间必须互不相交；相交则**整批拒绝**，说清是哪两笔、各自的行区间。
- **全有或全无**：任何一笔不合法，整批不写盘，并且要把「是第几笔、因为什么」说清楚，而不是只把那一笔
  标红。
- 最后一次调用给出**合并后的完整 diff**（05 的渲染），前几笔的返回是「已并入本批第 N 笔」，不重复
  渲染。一次撤销退掉整批（08 的记录以批为单位）。
- 整批合起来是 no-op 时**不写盘**，撤销历史保留。
- 目标路径解析不出来的调用（锚点无归属、路径不合法）**不参与成批**：它自己跑、自己报错，不拖累
  其他笔。参考实现有一条同类规则，值得抄下来。
- 模型侧要能看懂：工具描述里写明「同一回合对同一文件的多次编辑会合并为一次提交、一次撤销」，以及
  「批内区间不能重叠」。

**并发控制。** 一笔编辑的临界区是「读文件 → 校验锚点与校验和 → 写盘 → 推进锚点归属 → 落撤销记录」，
整段要放进 02 提供的**按路径互斥**里。没有它，同一回合的两笔并发会在读到同一个基态后互相覆盖，
本票的其他断言都测不出来。

**Blocked by:** 05, 07, 08

**Status:** ready-for-agent

- [ ] 同一回合两笔不同区间的编辑 → 一次写盘、返回一份合并 diff、两笔的锚点都是改动后的有效锚点
- [ ] 一次撤销退掉整批，正文回到批前
- [ ] 批内区间重叠 → **整批拒绝**，信息点名第几笔与第几笔、各自区间，且**一个字都没写盘**
- [ ] 批内某一笔不合法（锚点过期、参数畸形）→ 整批不写盘，信息说清是第几笔因为什么
- [ ] 批内合起来 no-op → 不写盘、撤销历史保留
- [ ] 目标路径解析不出来的调用自成一批：它报自己的错，同回合其他文件上的编辑正常提交
- [ ] 两笔分别落在**不同文件**上 → 各自独立提交，互不影响
- [ ] 并发真的并发：同一回合对同一文件的两笔编辑**并发发起**，结果是「一次提交且内容正确」或
      「整批可解释地失败」，不存在「两笔都报成功但只落了一笔」（这是本票的存在理由，要有意识地构造
      并发用例，并在断言里检查最终文件内容与锚点状态一致）
- [ ] 锚点归属与撤销记录的推进是**原子的**：并发结束后，文件的当前内容、会话里的锚点、撤销记录三者
      自洽（用改动后回给的新锚点直接再改一次成功）
- [ ] 前几笔的返回与最后一笔的返回不重复渲染 diff：模型不会看到同一批被渲染两次
- [ ] 工具描述写明批的行为与「批内区间不能重叠」
