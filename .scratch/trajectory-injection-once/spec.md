# spec: 轨迹里的注入物 —— 同一段文本整场只画一次，画的都是记录里真有的

> **已被推翻（2026-09-24，主人设计原则）**：轨迹要真实还原 jsonl 的 `kind=message`——不隐瞒、内容不转换，
> 所以下面「同一段文本整场只画一次」那条去掉了：某个 run 写了 `message` 行就画，重复也照画。
> 本 spec 的其余结论（切片错位、`submitted` 侧的修正、旧日志不追溯）仍然有效。见 `.scratch/trajectory/spec.md`
> 与 `CONTEXT.md` 的「轨迹」。

**一句话**：轨迹的「上下文」那一列原来是把每个 run 的 submitted 侧整段铺开，于是 5 轮的会话里开场块被画了
5 次（看起来像开场发生了 5 次）、而 `/<名字>` 的技能正文只碰巧在第一轮露面；同一条 turn 里还混着一条
**客户端自己发的消息**被画成「注入的 context」——那是切片错位顶出来的。本特征让那一列如实：
**同一段文本整场只画一次**（开场块只在第一轮，技能正文只在用它的那一轮），并且画的每一格都能指到记录里的字节。

## 要解决什么（都对着一份真记录量过）

拿 `80de94f6…`（本仓真会话，第一轮是 `/to-tickets`）折一遍，改之前是：

| turn | opening | run context |
|---|---|---|
| 1 | AGENTS.md + `<skills>` | `<skill name="to-tickets">…` |
| 2 | 同样两块**又画一遍** | `103 需要 02 需要 04 拆出来 ` ← **客户端自己的话** |
| 3 | 又一遍 | `/using-git-worktrees 开工` ← **客户端自己的话** + `<skill …>` |
| 4、5 | 又一遍 | — |

两处病根：

1. **读者把「每个 run 扛了什么」当成了「这一轮的上下文」。** 服务端没有会话，所以每个 run 都会把开场块重新拼
   一遍、把历史里还留着的 `/名字` 重新派生一遍——“照搬”就等于把同一段字节画在每个 turn 底下。
2. **记录的两半是按条数切的，而内核在客户端消息中间插正文。** `run-agent!` 记 returned 侧用的是
   `(subvec 最终历史 (count messages))`，每插一条这个切片就整体早一格；早出来的那一格正是客户端最新那条消息，
   于是它被当成注入物画了出来。第一轮的正文能看见，纯属它恰好落在切片起点上——「体现在轨迹中」不是保证，是运气。

## 决策

1. **同一段文本整场只画一次。判据是整段文本的字节**，不是来源也不是轮号：那是读侧唯一说得清的「同一段东西」。
   去重记在**会话**这一层（与 `system` 条同一层），实现上就是把「画过什么」从轮上挪到整条轨迹上问
   （`harness.edge.trajectory/add-context`）。
2. **「变了再画一次」不是第二个分支，是同一条判据的另一面**：变过的字节没人见过，于是在它变了的那一轮再出现一次
   ——`system` 条早就是这条规矩（`the-system-message-appears-again-only-when-it-changes`），本特征只是让上下文
   那一列与它一致。反过来「绝对只画一次、变了也不画」不行：那会让轨迹继续画旧字节，就是自造。
3. **记录如实：submitted 侧 = 第一次模型调用真正收到的那一份。** `harness.edge.http/run-agent!` 在**记 `message`
   行之前**先施加一次 `harness.cap.project/before-llm`（内核每次模型调用前还会再施加，幂等），并把这一份同时
   交给内核当起点。于是 `(subvec … (count messages))` 的那个「条数」就是记录上那一份的条数，两半不再错位。
   **这一步是承重的**：内核自己插一条，切片就被顶偏一格。
4. **读侧的匹配不再要求连续。** `/<名字>` 那条消息会一直留在历史里（客户端每轮重发全部消息），所以正文每轮都被
   重新派生并插在它后面——**夹在客户端两条消息之间**。旧的连续匹配在那里找不到任何东西，会把整块当开场块；
   现在按序匹配，夹在中间的那些进 `:between`，画成 `run` 上下文、照旧按第 1 条去重。
5. **旧日志不追溯。** 读侧画的是记录里的字节。本特征之前写下的那些错位记录不会被「修对」——把它修对就是猜。
   证据：`evidence/old-log.txt`。

## 非目标

- **不改 AG-UI 帧、不加 jsonl 行种类**：记录里已有的行够用，本特征是把 submitted 侧**记对**，不是加一行。
- **不动模型的提示词内容**：正文照旧每轮派生——客户端手里从来没有它，不派生就真没了。改的是记录与轨迹。
- **不动 `system` 条那条既有规矩**（只在第一轮出现、字节变了再出现一次；右侧面板永远显示选中那一轮的字节）。
- **不做轨迹的实时流式、不做「每次调用等宽」的画法**（`.scratch/trajectory/spec.md` 的既有非目标）。

## 已知局限

- 「是不是同一段」的判据是**整段文本的字节**：两段逐字相同的注入物只画一次。带上标签的那些
  （`<instructions path=…>`、`<skill name=…>`）基本不会被误伤，但**本 run 的 context** 没有标签——
  两份逐字相同的尾随上下文只画一次。
- **旧日志里那条错位记录不会被修正**（决策 5）。
- 轨迹仍然只画**已落盘**的部分：正在跑的最后一轮里，注入要等 `:run/done`（`message` 尾落在终帧之后）才看得见。

### 落地时撞出来、票面没写的事

1. **`subvec` 按条数切，前提是「起点就是记录上那一份」。** 这是本票的核心：注入必须在**记 submitted 之前**
   折进去。写票时只想到「returned 侧不错位」，「submitted 侧缺了注入＝记录说谎」是同一处病的另一半。
2. **错位会顶出客户端自己的话。** 它不只是「多条/少条」：切片早一格时，被顶出来的那一条是客户端最新那条消息
   （`80de94f6` 第 2、3 轮都量到了）。把客户端自己的话画成服务端注入的东西，是本特征最不该出现的自造。
3. **连续匹配的失效是静默的**：它退化成「整块都是开场块」——那会把客户端自己的话画成 opening。
   所以 `align` 的用例断言的是**客户端有条有据**（`:own` 匹配得上），不是「画出来几条」。
4. **一条 `a-bound-thread-writes-into-its-project-over-the-real-edge` 的红只见过一次**（全量首跑，
   `POST /api/project` 拿到 404——那不是本仓任何一条路由会给的答复），之后三连全绿、单跑该文件也绿。
   形态像本机临时端口被别的监听者抢走，**没有复现**，如实记在这里。
