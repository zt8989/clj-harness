# 02 — `/<skill>` 用一次，就在那一轮如实画一次

**What to build:** 人在输入框打 `/名字 `，技能正文要在**用它的那一轮**如实出现在轨迹的上下文列里，恰好一条，
而且那一列里**不能有自造的东西**。今天正文确实画出来了，但同一个 turn 里还混着一条不是注入物的东西：
**客户端自己刚发的那句话被画成了「注入的 context」**（`80de94f6` 的第 2、3 轮都看得见）。

病根在**记录**，不在画法：

- returned 侧记的是 `(subvec 最终历史 (count messages))`。内核在**客户端消息中间**插正文（`/<skill>` 的派生正文、
  `skill` 工具加载的正文），每插一条这个切片就整体早一格；早出来的那一格正是客户端最新那条消息，于是它被当成
  注入物画了出来。第一轮的正文能看见，纯属它恰好落在切片的起点上——所以「体现在轨迹中」今天是碰巧，不是保证。
- submitted 侧也不如实：它记的是 inbound 的输出，而这一 run 真正交给模型的第一份消息里**是有正文的**（那个幂等的
  pre-LLM 函数在第一次模型调用之前施加过）。记录的契约是「模型实际看到了什么」，少记注入就等于说模型没看到。

交付：**submitted 侧记的是这一 run 真正提交的那一份**（注入算进去），returned 侧的切片因此重新对齐；折法侧
客户端那一段的匹配要容忍夹在中间的注入物，并把正文归到**用它的那一轮**、画成 `run` 上下文。施加那一步是幂等的，
所以「边先施加一次记下来、内核再施加」等于没施加——两条路可选，选哪条都要把这一条写进注释。

## 验收

- [ ] **新构建**在真 HTTP 边上跑一条两轮的会话（脚本 provider，第一轮是 `/alpha …`）：第二轮记录里那个正文在
      **submitted 侧**（第一次模型调用真收到的那一份）、**不在** returned 侧；把它折出来，第 2 轮的上下文列里**没有**
      客户端自己那句话，正文只在用它的那一轮出现一次。
- [ ] **旧日志不追溯**：`80de94f6` 那条会话是旧构建写的，它的记录就长那样，折出来仍旧那样（第 2 轮里还看得见
      `103 需要 02 需要 04 拆出来 `）。读侧**不猜**——把一个错位的记录「修对」就是自造，本票修的是**写下来**的东西。
- [ ] 一条把 `/<skill>` 用在第 N 轮（N ≥ 2）的会话：那一轮的上下文列里有那条正文，一次；第 N+1 轮起不再重复
      （01 的规矩）。
- [ ] `skill` 工具那条路不变：正文仍跟在它那条 tool 结果之后，画成 `run` 上下文。
- [ ] `message` 行的契约仍然成立：submitted 侧逐条 = 第一次模型调用真正收到的那一份（注入在内），returned 侧
      = 内核在那之后追加的；手工搓的记录能断言这两半。
- [ ] 客户端那一段的匹配在「注入夹在中间」时仍然找得到——用户条画的是模型真收到的那一份，`:id` 来自 `input`。
