# 13 — 轨迹成为会话的一个视图：一次读，之后由写流增量推

**What to build:** 票 12 把折法从「收一份向量」变成「折一条流」，但它仍然是**每个请求折一遍**。
本票再进一格，落成主人 2026-09-24 定的口径：

> 打开一次会话，除了第一次加载，之后都是增量推送，不再读 JSONL；打开一次轨迹也是。
> 关闭再打开、切换导致内存丢失，就再读一次 JSONL 再增量推送——允许。

一句话：**轨迹的状态住在会话上，由写流推进；路由只是它的一个读者。**

**交付：**

- **折法挂上会话的两条缝**（形状照 `harness.edge.pressure` 的 `band-step`，票 03/04 的先例）：
  `sessions/register-step!` 在 load 时注册一步，`harness.edge.http/log!` 每 append 一行、
  `row-written!` 就把它原地推进。读的那一边同样是这一步：`replay/fold-consumers` 在内存里
  走一遍，会话的 build 走查走一遍，写流走一行一遍——**一份折法，三种驱动**。
- **按需安装 `:trajectory` 的值**：第一次有人要轨迹，走**一趟** `sessions/fold-record` 把值折好，
  装进会话的新缝（`register-fold!` 只在 build 时喂、晚注册拿不到历史行，所以要一条「按需装值」的
  门）。此后 `sessions/fold-value` 直接答，**一次 jsonl 都不再读**。
- **路由是长连接**：`GET /api/threads/<stem>/trajectory` 仍是 NDJSON（票 06 的形状），但**不关**——
  先把**已定稿**的轮一次吐出去（这就是「第一次加载」），再把每个**新定稿**的轮推下去。
  会话被淘汰 / 连接关了就丢值；下次开再走一趟（票面允许，是这个设计的正常代价，不是 bug）。
- **不碰下行**：轨迹不进 `events.mux`，下行仍只承载对话（票 06 的约束照旧）。

**边界（与对话视图同一条）：** 一轮**定稿** = 下一轮开口，或记录到底。悬置恢复（parked→resume）会往
**同一轮**里追加，所以「运行中的那一轮」是边走边长的；这条判据必须和对话「运行中展开、停下折叠」用同一个
（`trajectory/run-segments` 的开段规则已经是这条）。早一拍说某一轮完了，轨迹就会和对话对不上。

**为什么不需要给 JSONL 加字段：** 这份折法是**单向前进**的一趟。三条 prepass 本来就是 `reduce`/`loop`；
唯一跨段的查表（`tool-lifecycles` 的四时刻、`call-index` 的名字与参数）在「下一段开口」那一刻一定都齐了
——一场会话一次只跑一个 action。加字段只买到一件事：**从任意一行起步、一次都不读整份**；而「内存丢了重读
一次」已经允许，那笔账不值得用一份会漂的第二真相去换（记录格式是 spec 的非目标，决策 5 的账本是闭的）。

**Blocked by:** 12 —— 折法成 step（含 `tool-lifecycles` / `call-index` 并进这一趟）是这一票的地基。

**Status:** ready-for-agent

- [ ] 第二次及以后要同一条轨迹：**不开文件**（用一个「读了几次」的计数，或临时把文件挪走来证）。
- [ ] 写流推进：一轮运行期间，新定稿的轮**在同一条连接上到达**，客户端不需要再发一次 GET。
- [ ] 内存丢失（会话淘汰 / 连接关）后重开：结果与第一次逐字段相同（再读一次是票面允许的）。

## 内存的账

`:trajectory` 值比对话的 `:entries` 大（system 字节、工具表、usage 都在里面），所以它**按需装**而不是
在 build 时 eager：没人看这条轨迹就不折它，会话淘汰（idle TTL）或连接关掉就把值收回去。这也正是票面
「内存丢失就重读一次」那句的落点——值不是权威，记录才是。
