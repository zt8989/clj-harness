# 01 — 子agent 的定义与工具表派生

**What to build:** 一份子agent 的**定义**，以及一条真读法：**给一个主会话的 thread-id 和一个子agent 名，
算出这次委派实际服务的工具表**。定义里两个内置——**通用**（`:all` 基线，不排除任何东西）、
**探索**（`:read-only` 基线）——加上人后来在设置里新建的。派生必须**在委派发生的那一刻现算**，
而不是setup 时冻下来：主会话的有效工具表本身是会变的（编辑模式、会话新增、MCP 服务器的名单）。

两种基线，语义写死：

- **`:all`** —— 主会话此刻的有效工具表，减去这个子agent 声明的排除项。
- **`:read-only`** —— 只留**能证明是只读的**那些名字。来源不能证明只读的（`:source :mcp` 的、
  本会话 `session-register!` 进来的）**一律不进**，宁可少给。

两条**任何配置都做不到**的硬规则：`eval` 与委派工具本身，永不出现在任何子agent 的表里。这不是
"排除项的默认值"，是派生的后置条件——设置面板把 `eval` 写成可用的那一刻，保存就该被拒。

**收窄这一层要泛化。** 今天 `harness.kernel.tools` 里只有一份 narrow（编辑模式安装的那一份，
later wins）。子agent 的能力边界是第二份，而两份的判据都是 thread-id：多份按安装顺序问，
**第一份说不服务的**用它的拒绝语。只有一份在的时候，行为与今天逐字节相同。

**Blocked by:** None — can start immediately

**Status:** ready-for-agent

## 验收

- [ ] 给定一个主会话（hashline 模式、带会话新增的工具、带一个 MCP 桥接来的工具），派生出
      「通用」的表 = 主会话的有效表 − `eval` − 委派工具；派生出「探索」的表只含只读名，
      那个 MCP 工具与会话新增的那个名**都不在**——两条各有用例。
- [ ] 名字不在子agent 表里时，调用被拒，且拒绝信息**按名说清"这个子agent 不服务它"**
      （不是 `unknown tool`，也不是主会话那句"被谁关掉了"）。
- [ ] 对**同一个名字**，主会话服务、子agent 不服务，两边同时成立、互不影响（同一个进程里两个 thread，
      用例同时断言两侧）。
- [ ] 编辑模式的收窄没有被这次泛化改坏：`:hashline` 下 `edit` 仍然不在表里，拒绝语仍是原来那句。
- [ ] 派生是**读法**，不写任何东西（没有缓存、没有 per-thread 的载体在这一次就落地）；
      谁属于哪个子agent，由 02 在委派时按 thread-id 记。
- [ ] `node scripts/test.mjs --backend` 全绿。
