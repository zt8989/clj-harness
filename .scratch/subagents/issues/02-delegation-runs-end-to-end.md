# 02 — 委派跑通：把任务交给子agent，拿回它的结论

**What to build:** 主 agent 的工具表里多一个**委派工具**。它收 `{子agent 名, 任务}`，把任务交给那个
子agent：子agent 以**自己的 thread-id**、在 01 派生出的那份受限工具表里跑完一轮，它的**最终答复**
作为这次工具调用的结果回到主对话。从客户端看，这**就是一次普通的工具调用**——没有新帧、新协议、
新端点要认。

这一票是整组的 tracer bullet：定义（两个内置）、派生、嵌套 run、记录、身份，全部要走通一遍，
而且是**能演示**的那一票。

要点：

- **绑定继承。** 子会话绑到父会话的项目上，相对路径的重根与围栏跟它在主会话里一模一样。
- **模型档继承父会话这一次的解析结果**（用户在会话里换过模型，子agent 不该跑回默认档）。
- **身份说清。** 子agent 的 system message 要点明它是哪个子agent、它的能力边界是什么、
  它不能再委派——否则它会以主 agent 自居，去找一个自己没有的工具。
- **委派工具的描述**要说清什么时候值得委派、可用子agent 的名字从哪来；名字是会话此刻的定义，
  所以它的面（描述/参数）跟着会话走。
- **同一轮里的两个委派**各自一条记录，并发跑，互不串台（工具调用本来就并发，委派不新开一条特例）。
- **委派开始与结束时，`SubagentStart` / `SubagentStop` 真正触发**——这两个点今天只是登记过的数据，
  没有任何触发源。
- **子agent 里被挂住的调用不静默。** 本票的答案是：那句"这次调用需要人批准，子agent 不能等人"
  原样回到子agent 手里，它自己换个办法。让人来批是 06。

**Blocked by:** 01

**Status:** ready-for-agent

## 验收

- [ ] 端到端可演示：对一个绑定在项目上的会话说"用探索看看 X 是怎么实现的"，主 agent 委派出去，
      子agent 只读地读完，结论回到主对话，主 agent 据此作答。
- [ ] 该次委派在 `~/.clj-harness/projects/<workspace>/<子 thread>.jsonl` 留下一份完整记录：
      它自己的 system 消息、每一次工具调用与结果、最终答复；主会话那条 jsonl 里**只有一条**
      委派工具的结果，没有子agent 的内部消息。
- [ ] 「通用」与「探索」在同一次会话里各委派一次，两次的工具表不同：
      「探索」读不到写类工具、「通用」有它们但没有 `eval`——用例直接断言两次 run 发出的工具表。
- [ ] 子agent 里没有委派工具：让子agent 试着委派，得到的是"这个名字不在你的表里"。
- [ ] 子agent 的最终答复就是主会话那条工具结果的内容（不是摘要、不是再生成一遍）。
- [ ] `SubagentStart` / `SubagentStop` 各触发一次，且在记录里有对应的审计行。
- [ ] 一条消息里并发两个委派：两条记录各写各的、互不串台（各自的工具调用落各自的 jsonl）。
- [ ] 子agent 的工具调用被 park 时，回到子agent 手里的那句话说明是"需要人批准"，
      **不是**工具自身失败、也不是静默跳过。
- [ ] `node scripts/test.mjs` 全绿（本票不动 `ui/`）。
