# spec: subagents（子agent）

主 agent 可以**把一个任务交给一个子agent**：子agent 带着一份被收窄过的工具表跑自己的一轮，
结论作为那次工具调用的结果回到主对话。默认有两个内置子agent——**通用**（继承主agent 的全部工具，
`eval` 除外）与**探索**（只继承只读的那些）。侧边栏能看到有哪些子agent、跑过哪些；设置面板能编辑
内置这两个，也能新建。

## 决策

- **触发是委派，不是手选（2026-09-19，牛总裁定）。** 主 agent 手里多一个委派工具，`{子agent 名, 任务}`；
  人不在会话里选子agent，子agent **不再能委派**（任何子agent 的工具表里都没有那个委派工具）。
- **每次委派是一条独立会话（牛总裁定）。** 子agent 有自己的 thread-id、自己的 jsonl、自己的轨迹，
  可以单独回看、单独统计。主会话里只留一条委派工具的结果。
- **侧边栏既列配置也列运行记录（牛总裁定）。** 点「子agent」展开侧边栏：内置两个 + 自定义的，
  以及正在跑的、跑过的。不是一张只读配置清单。
- **被排除的工具在子agent 表里缺席，而不是"可见但被拒"。** 这与主会话的 tool-toggles 决策
  （关闭 = 可见、调用被拒）不同，而且是有意的：主会话的关闭是一条**策略**，子agent 的排除是它**声明的
  能力边界**，先例是编辑模式的收窄（`:hashline` 下 `edit` 不在表里，调用被拒并说明替代）。
  子agent 自己那份 system message 会把它有什么、没有什么说出来，所以"看不见"不等于"没人告诉它"。
- **只读基线宁缺勿滥。** `:read-only` 基线下只留**能证明是只读的**名字；来源不能证明的（MCP 桥接来的、
  本会话自己新增的）一律不进。`eval` 与委派工具永不在任何子agent 的表里，任何基线、任何配置都做不到。
- **子agent 继承父会话的项目绑定。** 相对路径的重根与围栏跟它在主会话里一模一样——不这么做，
  一个探索子agent 会以进程的工作目录为根，那是本仓最不想要的那种惊喜。
- **内置两个由代码提供，`harness.edn` 同名条目覆盖。** 内置删不掉（可以改），自定义的可以删。
- **收窄从一份变成多份。** 今天 `narrow` 是一份（编辑模式安装的那一份，later wins）；子agent 的能力边界
  是第二份。多份按安装顺序问，**第一份说不服务的**用它的拒绝语——两个策略都拒同一个名字时，
  先开口的那句更具体。
- **模型档继承父会话这一次的解析结果。** 用户在一个会话里换成了便宜模型，子agent 不该悄悄跑回默认档。
  （这一条是本组新增的判断，不是牛总原话；不认同就改 02 的验收。）
- **库装状态、记录装记录的那条线不破。** store 里只装"这条子会话属于谁、叫什么"；
  "跑完没有"由那条 jsonl 自己回答（既有 rebuild / stats 已经会读），"正在跑"是进程内的一张表，
  随进程退出消失（与后台作业同一条规矩）。

## 非目标

- 不做用户手选子agent（整场会话按某个子agent 的工具表跑）——这是另一种形状，本特性不做。
- 不做子agent 的并行编排 / 团队 / 消息互通（`TeammateIdle` 仍然只是一个登记过的点）。
- 不改 AG-UI 协议：委派在主会话里**就是一次普通的工具调用**，客户端没有新帧要认。
- 不做子agent 自己的预算、时限、模型旋钮（旋钮是会话的三个，子agent 不新开一档）。
- 不改「工具永不离表」那条对本会话成立的决策；本特性收窄的是**另一个会话的表**。
