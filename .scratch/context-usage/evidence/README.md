# 证据：上下文占用（model 左边那颗圈）

**走查用的是脚本替身**（`node scripts/dev.mjs --scripted`，临时家、退出即删），**没有跑活厂商**。
替身声明的窗口 `128000` 是**替身的数字**（`test/harness/fake.clj` 的 `:context-window`），
与任何厂商无关——它存在的理由是：脚本替身伺候的会话一条 `provider/init` 都不写，
分母只能来自那一次调用自己的 `model/start` 行（票 01 的全部理由）。

## 数与对数

那一次会话（`fe60135c-…`）跑了两轮，记录里两对行：

- 第 1 次调用：`model/end` 报 `prompt_tokens 60000`，那一次调用的 `model/start` 上
  `:context-window 128000` → 圈 `47%`（60000 / 128000，四舍五入），面板 `~60K / 128K`。
- 第 2 次调用：`prompt_tokens 70000` → 圈 `55%`，面板 `~70K / 128K`。**数字自己动了，不需要刷新页面。**

面板里三个篮子（`系统提示词 ~7.2K` / `工具定义 ~49.7K` / `对话消息 ~13.1K`）加起来是 `70K`，
**恰好**是头部那个分子——那不是碰巧：服务端就是拿三部分的字符数去摊那一个总数的
（`harness.edge.context/apportion`），套件里有一条恒等式钉着它。

## 一次走查当场撞出来的东西

第一轮跑完，圈**停在上一格**（77%，上一次调用的数）而没有跟到最后一次调用。原因不是折法：
记录的写者比它自己的终帧晚一拍——run 的 message 尾巴落在 `:run/done`，而客户端是在终帧那一刻去问的，
那一拍里三分还数不出来（`usedTokens` 有、`parts` 没有）。修法是 `components/composer-numbers.tsx`
里那两次按需的追一问（run 结束后隔一拍、打开面板时）。这是**走查**才有的发现，
两套套件当时都是绿的：套件直接问端点，没有「客户端在哪个瞬间问」这一层。

## 这里**没有**的证据

- **没跑活厂商**：所以「厂商报的 `prompt_tokens` 与目录声明的窗口在真模型上对不对」没有现场证据。
- **摊法没在真机上调过**：三个篮子彼此之间的估偏差（工具表 JSON 的 token 密度、中文正文字符与 token 的比）
  没有任何测量。要量它需要真厂商报的数与同一份请求的字节，这台机器上没做。
