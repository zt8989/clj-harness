# 02 — 挂死、崩掉、改声明：一个坏掉的服务器自己站起来

**What to build:** 01 让一个**听话的**服务器能用。这一票让一个**不听话的**服务器不拖死任何人：调用挂死会在
超时后变成这次调用的错误结果（run 继续）；服务器进程中途死了，下一次用它会**重连**（重新 spawn、重新握手、
重新列工具）并照常把事办完；`mcp.edn` 里那条声明改了，下一次用它走的就是新的命令；服务器吐出来的
不是 JSON-RPC 的一行，会被**指名**当成协议错误，而不是被当成日志静默跳过。

**Blocked by:** 01

**Status:** done（2026-09-16，分支 `mcp`）

## 决策

- **每个请求一个超时**，默认 60000ms，可按服务器用 `:timeout` 覆盖。超时的结果是一条**指名**的错误结果
  （server 名 + tool 名 + 毫秒数），不是异常、不是空结果——模型要能读懂「这次没成，因为超时」。
  超时后**这条连接要丢掉**（重连走回下一票/本票的重连逻辑）：一个还没回话的请求留在原地，后面每条消息
  都会跟它错位。
- **连接是缓存，不是事实。** 一个连接的身份是（会话的项目身份 × server 名 × **这条声明的形状**）：
  - 进程死了（stdout 到 EOF / 写入失败）→ 下一次用它时重连，**工具清单重新列一遍**（服务器重启后可能多一个
    少一个工具，表要跟着变）；
  - 声明改了（命令、参数、环境、超时任一不同）→ 下一次用它时重连，不看名字相同就复用；
  - 声明不见了（文件里删了这一条）→ 它的工具离开工具表，进程被收掉。
  这三条就是「配置每次现读」在长活连接上的对应物：文件是现读的，连接不能装作文件没改过。
- **协议错误要指名，不要宽容。** MCP 规定 stdout 只走协议消息、日志走 stderr，所以 stdout 上一行不是
  JSON 就是**这个服务器的错**：连接标记为坏、原因里带上那一行（截断到可读长度）。**不静默跳过**——
  「服务器在往 stdout 打 banner」如果被吞掉，下一个出现在协议位置上的怪东西就没人知道它是从哪来的。
  子进程的 stderr 永远**只当诊断读**（可入状态面），绝不参与协议。
- **不许留僵尸**：进程自己退出、我们主动收掉、超时清理，三条路径都要把进程回收干净（`waitFor` + 必要时
  `destroyForcibly`），并且不许有线程继续读一个已经死掉的 stdout。
- **一个坏服务器不影响别人**：这一票所有失败都止步于「这个服务器的工具用不了」，run、其余服务器、
  其余会话一律照常。失败一律落一行 `mcp/server` 审计行（边是唯一写入者，见 01），且**重连成功也落一行**
  ——「它自己站起来了」是有人需要知道的事实。

## 验收

- [x] `:timeout` 生效：服务器挂住不回话 → 这次调用的结果是**指名**超时的错误结果，run 照常收尾并继续
      下一轮；那条连接被丢弃
- [x] 测试从外部杀掉子进程（`.destroy`）→ **下一次调用重连成功**并把结果交回来；审计行里能看到
      断开与重连这两件事
- [x] 重连后**工具清单重列**：假服务器换一套工具再重启，表跟着变（新增的进表、消失的离表）——两条断言
- [x] 改 `mcp.edn` 里那条声明（换命令/加参数）→ 下一次用它连的是新命令；只改超时也算改（同一个断言家族）
- [x] 从 `mcp.edn` 里删掉这条声明 → 它的工具不在表里了，子进程被收掉（断言进程已不在）
- [x] 服务器往 stdout 打一行非 JSON → 连接标记为坏、原因指名那一行；**不是**静默跳过
- [x] 子进程写 stderr 一行 → 握手与调用完全不受影响
- [x] 一个服务器坏掉时，另一个服务器的工具在这一轮里照常调用成功（隔离断言）
- [x] 三条收尾路径（自杀 / 主动收 / 超时）都不留僵尸进程，也不留读死掉的 stdout 的线程
- [x] 离线全量 `harness.test-runner` 全绿

## 落地（2026-09-16）

改动都在 `harness.mcp` 的连接生命周期与 `harness.shell` 的收尾，另加假服务器的三个观察口：

- **超时把连接一起丢掉**（`drop!` = 标记死 + 杀进程）。理由写进代码了：一条还在飞的请求不会乖乖消失，
  它迟早会答，而它之后每一条消息都会错位一格——把整段对话杀掉，是下一次调用能确定自己在读什么的唯一办法。
- **重连就是「再连一次」**，没有「复活」路径：坏掉的对话没法续，只能新开一段。上一段的死因随新连接带出
  （`:restarted-after`），所以审计行里断开与重连是同一行里的两件事，而不是一个悄悄回来的服务器。
- **声明被删要走一遍清扫**（`reap!`）：工具离开工具表是白来的（`tools-for` 走的就是文件里还写着的东西），
  但**进程**不会——没有任何别的地方会去看文件不再说的那一条。这是三条里唯一需要主动做的事。
- **收尾是杀一棵树，不是杀那个子进程**：我们握着的进程是 shell，而命令常常是包一层的东西（`npx` 是常态，
  它自己再起真正的服务器）。先收集子孙（父进程一死它们就被重新挂到 init 上，那棵树再走不到了），
  再让直接子进程停下，还站着的直接杀掉。
- 假服务器加了三个口：`exit` 工具（调用中原地消失）、`MCP_FAKE_ROSTER_FILE`（每次 `tools/list` 现读，
  所以「重连后重列」是可观察的）、`MCP_FAKE_LIFECYCLE`（start/term/exit + pid，所以「进程真的被收掉」
  是可证明的，而不是从行为推断的）。

**测试抓住的第三个真 bug**，与 01 那个是同一族：`#(:close! handle)` 是个**返回函数**的闭包而不是调用它，
于是「回收」这条路上什么都没被杀掉——而它读起来像「进程没死」，不像「少了一对括号」。收口办法是把
`stderr`/`alive?`/`close!` 三个透传都写成显式调用，并在注释里点明这一类错误。

**一处测试写法上的诚实修正**：最初三条断言都要求「term」（我们发了信号），但服务器在 stdin 关闭后
会自己退出，于是同一个「进程没了」的结果有两种机制。现在先问操作系统（用服务器自己记下的 pid 调
`ProcessHandle`），再记录它是被信号停下还是自己走的——契约是「它不在了」，不是「我们 SIGTERM 了它」。

## 追加（2026-09-16）：第四条收尾路径——JVM 自己退出

票面的验收只列了三条收尾路径（自杀 / 主动收 / 超时），**漏了第四条**，而它是配一个真实服务器
（`npx @playwright/mcp@latest`）时立刻暴露的：**一个进程退出时，上面三条一条都不会跑**，
而服务器是**另一个进程**，不会跟着我们走。跑两次测试留下两个 `npm exec @playwright/mcp` 进程。

修法是在第一次建立连接时装一个 JVM shutdown hook（`ensure-exit-hook!`），退出时走同一个
`shutdown!`。装在**第一次连接**而不是加载时：没用过 MCP 的进程没有东西要收。

**验证**（手工，两次，含一个真服务器）：修之前，每次运行留一个 `npm exec` 进程；修之后，
假服务器自己写的 lifecycle 文件里是 `term` → `exit`，`pgrep` 什么也找不到。

**没有给它留一个测试，理由记在这里**：我先写的那个 forked-JVM 测试（照 project_test 跨进程验绑定的
先例）让**子进程挂了十三分钟没有输出**，而父进程卡在 slurp 上。那是一个真问题、也值得单独一张票
——两个 JVM、一个 home、一个 store（sqlite 的跨进程故事正是把它引进来要解决的，所以怀疑是锁）
——但它不是这一票的问题，而**一个会挂住的测试比一个写明了的缺口更坏**。缺口写在这里，票另立。
