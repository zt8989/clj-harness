# spec: 常驻内存的账 —— 一次 profiler 走查的三笔账与三张票

**一句话**：这台进程占 2.4 GB 里**没有 2 GB 的泄漏**——绝大部分是「还没回收的垃圾」加上一个**每 2 秒
调度、单轮却要 3.9 秒**的后台时钟在把堆撑大；真正**不会被回收**的是三处：一个永不停手的后台 pass、
一个没人拿着的 watcher 挡住会话清扫、以及记录流的短环把同一条记录存了两遍。

2026-09-29 对着活着的会话（thread `cc8ac0a8-…`）实测。**这张 spec 记读数与裁定；四张票记要做的活。**

## 读数（都是实测，不是推算）

**堆本身**

| 项 | 读数 |
|---|---|
| 工作集 / 私有提交 | 2,461 MB / 4,223 MB |
| `-Xmx`（默认 = 物理内存 1/4） | 4,086 MB |
| Full GC 前 | committed 3,971 MB，used 1,500 MB |
| **强制 Full GC 后** | committed **494 MB**，used **171 MB** |
| Metaspace / 类空间 / CodeCache | 54 MB / 11 MB / 23 MB |

**⇒ 一次 GC 就吐回 3.5 GB。** 所以「2 GB」是堆被撑大后的水面，不是活着的对象。

**撑大它的那个东西**

`harness-projection` 线程的累计 CPU 是 **9,914 秒**（进程才活了 6 小时），占整个进程 CPU 的 46%，
是第二名的 230 倍。间隔是 **2000 ms**，而一轮 pass 实测 **3,914 ms**——固定速率调度下它永远追不平。
一轮遍历 store 里的每一个会话（当时 106 个有日志），只换来 **8 行 / 6,184 字节**新数据。每一轮里，
每个会话都要查一次进度，而 `harness.infra.db` 的连接纪律是 per-call：**一次查询 = 一条新连接 +
一遍迁移**（一次平凡的 `SELECT 1` 实测 8–15 ms）。42 秒的 JFR 分配采样指着的也正是这些形状
（row-map 的迭代、`java.lang.reflect.Method.copy`、`SQLiteConfig.apply`、读文件的缓冲）。

**活着的 171 MB 是什么**

254 MB 的堆快照（自己写了个 HPROF 反向引用解析器）：**857,460 个 `byte[]` = 94.61 MB，其中
92.50 MB 的引用者字段是 `java.lang.String.value`**——它们就是字符串文本本身（JDK 紧凑字符串），
不是洩漏的缓冲区。文本的归属，逐个 atom 点算：

| 持有者 | 文本 | 注 |
|---|---|---|
| `kernel.session/registry` | **45.19 MB**（300,167 个字符串） | 31 个会话，最大的一个 3,299 条 entry |
| `infra.stream/kept`（记录流的短环） | **11.19 MB** | 18 个 thread-id、5,172 条 item |
| `mux/runs` + `mux/facts` + `jobs/registry` + `mcp/*` + `parked-registry` | 合计 < 0.2 MB | 零头 |

**为什么那 45 MB 不走**

`evictable?` 要四件事同时成立。逐个会话实测 31 个：无 run ✔（29/31）、字节已落盘 ✔、空闲超 30 秒 ✔
（29 个已经空了 **52 分钟到 6.6 小时**）——但 **`watched?` 对 31/31 全为真**。而对照活连接：

- `edge.mux/connections`：**2 条活连接、共 8 条订阅**
- `kernel.session/watchers`：**32 个键挂着 126 个 watcher 函数**
- ⇒ **118 个 watcher 没有连接在背后**，单个会话上最多挂了 19 个。

## 三件裁定

1. **内容投影的后台时钟停掉**（票 01）。理由不是「它慢」，是**今天没有任何读方**：全仓没有一条
   `SELECT ... FROM messages|tool_calls`（只有投影自己在写和删），`projection/lag` 没有端点报它，
   前端的「搜索」全是客户端过滤。关掉它今天不损失任何读法；ADR 0008 的三条（记录是唯一真相、
   投影只读、可整份重算）一个字不改。**放回来的条件写进票 04。**
2. **空闲的会话要真的被放掉**（票 02）。要修的不是 `evictable?`，是**watcher 的归属**：
   它只能跟着活连接走。CONTEXT.md 早就把这件事写成事实了（「服务端除了活着的连接**不记谁在订阅**」、
   generation 一节把「会话空闲 30 秒被放掉」当前提）——今天那条只有连接才有效的规矩，在
   `session/watchers` 这张表上失效了。
3. **记录流的短环只留解析后的 `row`**（票 03）。`:line` 在生产代码里**没有消费者**：拉流那对入口
   （`consume!` / `after`）只被测试调用，推流的 `listen!`（按会话）一个调用点都没有，唯一的
   production 消费者是内核的进程级监听，它只要 `:row`。**一条必须写下来的约束**：`row` 重新序列化
   **不等于**那一行字节（键序、空白都不同），所以「要原始字节」的正确来源是**文件**。

## 不做的事（本次票里不碰）

- **类加载器那笔账**：12,802 个已加载类 / 2,756 个类加载器 / 54 MB metaspace，来自反复的 `eval`
  与 `(require ... :reload)`（每次编译挂一个新的 `DynamicClassLoader`，只增不减）。字节数不大，
  但它单调增长且永不卸载——真要紧时单独开一票。
- **`harness.infra.db` 的连接纪律本身**：per-call 开连接是全局的，不止投影在用。本族只要求在
  投影自己的那一层把它说清并按它做（票 04），不顺手改全局。
