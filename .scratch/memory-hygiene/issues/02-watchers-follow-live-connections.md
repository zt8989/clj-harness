# 02: 会话被放掉这件事要真的发生——watcher 只能跟着活连接

**What to build:** 「空闲 30 秒的会话被放掉」今天做不到：放掉的条件里第三条是「没人看着它」，
而实测 **32 个会话键上挂着 126 个 watcher 函数，背后只有 2 条活连接、共 8 条订阅**——**118 个 watcher
是孤儿**，单个会话上最多挂了 19 个。所以这条票要修的是**watcher 的归属**，不是放掉的判据：

- **归属只有一个来源**：活着的订阅。连接走了，它注册的 watch 必须同时消失。
- **重连不留孤儿**：客户端重连会拿到新 token，旧 token 那一份 watch 不许留下。
- **孤儿清掉之后**，没有任何 run、字节已全部落盘、没有任何活订阅的会话，超过空闲上限要真的被放掉
  （连同内存里那份对话）。

这与 CONTEXT.md 已经写下的规矩一致——「服务端除了活着的连接**不记谁在订阅**」，以及 generation 一节
把「会话空闲 30 秒被放掉」当作前提。今天只有这张表偏离了那条规矩。

**一条不许破坏的性质**：连着看的窗口**仍然是一枚钉子**。feed 不许因为清扫在 30 秒处断掉——清掉窗口
会让读者每半分钟断一次，这正是当年加这条判据的原因。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] 一条订阅断掉之后，对应会话上的 watcher 计数归零（不必等空闲上限）
- [ ] 一次「断开后带新 token 重连」之后，watch 的总数**不比活订阅数多**（重连不留孤儿）
- [ ] 一个没有任何 run、字节已全部落盘、没有任何活订阅的会话，超过空闲上限之后被放掉——有一条测试
      证明它不再占着内存里那份对话
- [ ] 仍然连着的窗口不受影响：持续看着的窗口不会在 30 秒处被断掉推送
- [ ] watch 的条数不会随时间只增不减：把「watch 的条数 ≤ 活订阅的条数」写成一条断言
