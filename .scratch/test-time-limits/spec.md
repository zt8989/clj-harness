# spec: 单元测试的硬限制（超时即点名 + 打栈 + 退出 2）

2026-09-20 立。**要的是：给单元测试加硬性限制，超时即报错退出，防止下次卡住发现不了。** 这一条没进
tracker，是给这次改动补的记录，原话是

> 给单元测试增加硬性限制，超时即报错退出，防止下次卡住发现不了。

前情不是那个 bug，而是那个 bug 留下的教训：`harness.kernel.tools-test` 卡住那次（反射热循环，根因修在
`63a4d82`，同一类里剩下的三处修在 `522f70c`），代价全在**看不见**上——日志停在最后一行 `Testing …`，
再没有下文；定位靠三次手工 `jstack`；有一轮没人看着的进程活了四天。所以这一票要的不是更快，是
**停不下来的时候，必须有人说话**。

## 定下来的六件事

**一、两个限制，各管一段。** 一个命名空间 **300s**（`CLJ_HARNESS_TEST_NAMESPACE_TIMEOUT_SECS`），
整轮 **1800s**（`CLJ_HARNESS_TEST_RUN_TIMEOUT_SECS`）。数字是**余量不是目标**：健康时全量约 110s、
最慢的命名空间约 16s（都是当台机器 2026-09-20 量的），300s 是它的十九倍。限制一旦会在慢机器上误报，
就会被调到形同虚设——所以放宽的出口就是这两个环境变量，而配错的值**直接拒绝**（`limit-ms`：
非正整数字符串抛 `ex-info`），不静默退回默认值：设了硬限制却拿到没有限制，是对这一轮跑的假陈述。

**二、逐个命名空间跑，汇总由 runner 自己打。** clojure.test 的 `run-tests` 是「一串命名空间一份汇总」，
那样限制挂不到**某一个**上。改成逐个 `test-ns`（它打的还是同一行 `Testing …`，且不打印汇总），计数自己
加，最后用 `t/do-report` 报一份 `:summary`——输出与以前逐字一致（`Ran 965 tests containing 12015
assertions.`）。

**三、换一条线程是唯一的办法。** 不返回的工作从外面中断不了：那次卡住是循环里的反射调用，没有 sleep、
没有锁，`interrupt` 无从下手。所以 `run-with-deadline` 把工作交给一条 **daemon** 线程，到点就不再等它；
线程**不会被杀**（也没人能安全地杀它），是**被丢下**的——这是对一个状态未知的线程唯一诚实的处置，
而进程紧跟着就退出。栈就在这一刻取（`(.getStackTrace thread)` + 线程状态），也就是那次没人想到要留的
`jstack`。

**四、报告走 stderr。** 有一种卡住恰恰是 stdout 没人读了（管道那头走了，写的人停在写里），报告如果也写
进那条流，就是那条永远到不了的消息。`isolation-verdict` 的失败行本来就是这么做的，理由一样。

**五、三个退出码，含义不同。** **0 绿、1 红**（用例失败或判据失败，判据一直折在 1 里）、**2 撞限制**：
第三种的下一步动作和第二种完全不同（去看那个卡住的命名空间，不是去看那条红的断言）。撞限制时
**部分汇总照打，但带一行标语**（"the namespaces that finished, before the limit:"）——一轮没跑完的
汇总不当成整轮的结论。撞限制时栈里那个命名空间的计数**没有**（它与那条线程一起被丢下了），报告直说。

**六、已经在跑的命名空间，不被整轮预算打断。** 整轮预算只在**两个命名空间之间**查：能点名一个命名空间
的，是它自己那个预算。所以一轮的最坏墙钟是「整轮预算 + 一个命名空间的预算」，换来的是每份报告都能
指向一个具体的名字。`require` 整张名单那一步也用命名空间预算（它是一次调用，点不出单个名字，栈里那个
文件就是答案），于是**加载阶段卡住**也在限制之内。

## 顺带的两件事

- **每个命名空间跑完打一行 `[16.3s] harness.kernel.tools-test`**：慢的那家要能事后看出来；卡住时，
  那行 `Testing …` 底下**没有**这一行，缺的那行就是它。
- 启动横幅多一行 `time limits: 300s per namespace, 1800s for the run (…)`：报告里的数字从哪来，一眼能对。

## 怎么验的

- **分支由用例驱动**（`test/harness/test_runner_test.clj`，与判据同一套路：纯输入 + 一个永不返回的 thunk）：
  到点返回 `:timeout` 且栈里点得出那个函数名、线程状态 `WAITING`、抛出的东西是**报回来**不是扔出去、
  三种报告的措辞、报告只走 stderr、非数字限制被拒、0/1/2 三个码。不需要真卡一次才能验。
- **端到端**（真跑，故意把限制调到荒谬）：`CLJ_HARNESS_TEST_NAMESPACE_TIMEOUT_SECS=2` 跑
  `harness.kernel.tools-test` ⇒ 6 秒（含 JVM 启动与加载）后 exit 2，报告点名 + 打出栈
  （那次栈里正好是 `harness.infra.shell$run` → `ProcessImpl.waitFor`，一个**合法**的等待，
  说明栈确实说的是「它此刻在哪儿」）；`CLJ_HARNESS_TEST_RUN_TIMEOUT_SECS=8` + 两个命名空间 ⇒
  exit 2，报出「14.9s had elapsed … 1 of 2 namespaces had finished」与没跑到的那个名字；
  `CLJ_HARNESS_TEST_RUN_TIMEOUT_SECS=abc` ⇒ 退出 1 + `test time limit must be a positive number of
  seconds, got "abc"`，且**没有**留下临时目录。
- 全量：965 用例 / 12015 断言 / 0 失败 / 0 错误，exit 0，约 1m50s（改前 956 / 11980，多出来的是本票
  新增的 10 条用例）。

## 没做的

- **没有杀掉超时那条线程**：见第三件。真要在退出前把一个卡死的线程清掉，只有 `Runtime.halt` 级别的
  手段，而那会连收尾（临时目录）一起放弃；现在的取舍是「先说话，再退」。
- **没把整轮预算做成精确的墙钟上限**：见第六件，最坏是「整轮 + 一个命名空间」。
