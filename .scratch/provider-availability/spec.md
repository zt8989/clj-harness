# spec: 有密钥的厂商才被展示，且「获取可用模型」真的能拿到

## 问题（主人一句话，实测后拆成两件）

> 「设置中 model 中只有环境变量存在对应的 key 才展示，而不是展示所有，点击获取可用模型现在什么也获取不到。」

### 一、「获取可用模型」对任何厂商都回一个空表

表单上那颗按钮走的是 `POST /api/providers/models`，真的去问厂商 `GET <base-url>/models`。
那条真实实现里，厂商那份 JSON 是**按字符串键读进来**的（`clojure.data.json` 的默认 `:key-fn`
就是 `identity`），却用**关键字**去取 `data` —— 取不到，于是 `keep` 走了一个空序列。
**任何 2xx 应答都得到 `[]`**：厂商列了三十个模型，勾选列表是「这个提供方没有列出任何模型」。

这条坏法一路发到人手里，是因为测试里那把**缝**（`*list-models*` 的 `alter-var-root` stub）
把真实解析整条换掉了：三条用例都在测「stub 给了什么就回来什么」，
没有一条喂过一份**厂商形状的 body**。缝本身是对的，缺的是缝下面那一层能被单独喂。

（实测：`(json/read-str "{\"data\":[{\"id\":\"gpt-x\"}]}")` → `{"data" [...]}`，
`(:data …)` → `nil`。）

### 二、Models 页把所有厂商都摆出来，包括必然 401 的那些

设置 → Models 现在列**整个目录**：内置三家加上你自己加的，每一行都标「有密钥 ✓ / 没有密钥」。
主人的判据是：一家没有密钥的厂商摆在清单上，就是把人往一次必然失败的 run 上领
——他要的是「有密钥的才展示」。

## 目标

1. 点「获取可用模型」，回来的勾选列表就是厂商此刻真的列出的 id；厂商形状的 body 能被单独喂进测试，
   缝不再能把这类坏法藏住。
2. 「厂商被展示」这件事等于「这个家有一把钥匙指向它」——没有钥匙的厂商默认不出现在
   设置 → Models 的清单里（可展开的一句话交代它们在哪、怎么让它们回来）。
3. 同一条规则适用于 composer 的模型选择器：没有钥匙的厂商，它的模型不上菜单。

## 定下来的决策

- **「有密钥」= `:key.present?` 为真，不分来源。** 密钥可以来自配置家的 `.env`，也可以来自真实环境变量
  （`.env` 优先，见 providers 的规矩）。主人说的「环境变量」按「这个家配了这把钥匙」读，
  否则一个把钥匙写进 `.env` 的家会看不到任何厂商。这个事实**不带值**，它今天已经随
  `GET /api/providers` 一起回来了，所以第 1 件里 It 侧不用新增服务端形状。
- **默认不展示 ≠ 藏死。** 没有密钥的厂商收在一句可展开的话后面（「还有 N 家没有密钥」），
  点开仍是今天那行、能进去补一行 key。全部隐去会让人拿不到内置表的 id，
  而「加一条 provider 补上 openrouter 的 key」正是要照着那个 id 做的动作。
- **正在用的那个不藏。** composer 选择器里，本会话此刻被服务的模型/厂商即便没有密钥也画得出来
  （沿用「不在模型目录里」那种画法）。把正在用的东西从菜单里抹掉是更大的谎。
- **票 01 与 02、03 之间没有阻塞边**：一条是服务端解析的缺陷，一条是展示口径，
  各自能独立落地、独立验收。

## 非目标

- 不动密钥的解析与挂载（`api-key` 仍然只有那一处）。任何新增字段都只报 `:present?` 这种事实。
- 不因为「没有密钥」就拒绝一次 run / 拒绝一次写：那是厂商的事，不是这张票的事。
- 不改内置表，不改 `credential-name` 的派生规则。
- 不为「环境变量」与「.env」各立一套判据——仍然是一个 `env-source` 一个答案。
