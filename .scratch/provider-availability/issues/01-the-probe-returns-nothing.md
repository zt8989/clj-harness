# 01 — 获取可用模型：把厂商列的模型真的拿回来

**What to build:** 表单上点「获取可用模型」，回来的勾选列表就是厂商此刻真的列出的 id
（对着任何 OpenAI 兼容的 `/models` 都成立）。今天它对**任何** 2xx 应答都给一个空表，
于是不管厂商列了三十个还是一个，人看到的都是「这个提供方没有列出任何模型」。

坏在解析那一步：厂商那份 JSON 是**按字符串键**读进来的，却用**关键字**去取 `data`——
取不到就是空表。测试里那把缝（把出网那一次调用整个换成 stub）正好把真实解析也换掉了，
所以三条用例都在测「stub 给什么就回来什么」，这个坏法一路发到人手里。

**先做的准备（让改动变容易）：** 把「厂商应答的 body → id 向量」摘成一个**纯函数**，
真实实现只剩「出网 + 这个函数」。这样测试可以直接喂一份厂商形状的 body，不出网，
缝也不再盖住这一层。

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] 一份厂商形状的 2xx 应答（`{"data":[{"id":"gpt-x"},{"id":"gpt-y"}]}`）走**真实**那条路
      （不 stub 缝）得到 `["gpt-x" "gpt-y"]`，用例本身不出网。
- [ ] `id` 不是字符串的行被跳过而不是让整条失败；`data` 缺席、不是数组、或行不是 map
      一律得到空表——「厂商没列任何东西」是一种正常回答，不是错误。
- [ ] 解析从出网里摘了出来：只喂 body 就能覆盖它。这是这张票的重点——**缝下面那一层得能被单独喂**。
- [ ] 四条拒绝路照旧：401/404 带厂商**自己的原话**，非 JSON 有自己的句子，超时有自己的句子且与前者分得开。
- [ ] 应答里任何深度都没有密钥值；这条路由仍然**不写任何东西**（jsonl、`config.edn`、`.env` 都不动）。
- [ ] 表单侧真机走查一张截图（对着一个本地假 endpoint 即可，不必出网）：勾选列表里是厂商列的 id，
      勾了能进模型目录，模态默认 `:text`。
- [ ] `clojure -M:test -m harness.test-runner` 失败名单逐条不变、数量不增；
      既有的 stub 用例一条不改、一条不删。
