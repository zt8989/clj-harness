# 04 — 消息部件：工具调用卡与常展开的 reasoning

**What to build:** 助手消息里不再只有文字。工具调用渲染成一张卡（工具名、参数、状态、结果），没有为
某个工具注册专用 UI 时走同一张通用卡；reasoning 有独立渲染，且**在流结束后仍然展开**——这是这个仓库
有意与默认行为分道的地方（默认一停就折叠，内容要再点一次才看得见）。文本、工具、reasoning 按真实顺序
交替出现。

对位的是 `ui-tool-cards` 与 `cljs-ui` 里已经验收过的那套行为：渲染器不是可选的装饰，没有渲染器的工具
调用在界面上等于不存在——细节在线上跑得好好的，只是没人画。

官方 `Thread` 元素已经留好了槽位，这一票主要是**覆盖槽位而不是从零搭消息区**：
`components` 上有 `ToolFallback`（无专用 UI 的工具调用）、`ToolGroup`（一串连续工具调用的包壳）、
`ReasoningGroup`（一串连续 reasoning 的包壳）三个槽，另有按工具名注册的 renderer 优先于 `ToolFallback`。
`components` 是模块级常量或在组件里 memo 住——它是 props，每次 render 换一个新对象会让整棵消息子树白重渲染。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 工具调用 part 渲染成卡：工具名、参数、状态（运行中 / 成功 / 失败）、结果；结果为空时显示
      「无结果」这类明确状态，而不是一块空白
- [ ] 参数以原始 JSON 呈现，不被折叠、截断或摘要——人要看的是将要执行的确切内容
- [ ] 未注册专用 UI 的工具走 `ToolFallback`：新增一个工具不需要改前端就能看见它的调用
- [ ] 需要专用呈现的工具按**工具名注册 renderer**（不是去堆 `ToolFallback` 里的条件分支），且注册的
      renderer 确实优先于兜底
- [ ] 同一轮里并发的多个工具调用各自成卡，不合并成一张、不丢其中任何一个；`ToolGroup` 只做包壳，
      不吞掉组内调用
- [ ] reasoning part 独立渲染：流式期间显示进行中，流结束后**内容仍然展开**；手动可收起；新的一段思考
      再次自动展开
- [ ] `showThinking`（默认 true）确实开着——它是 `THINKING_*` / `REASONING_*` 事件渲染成可见推理的开关，
      关掉就什么都不显示。本票要的是显示，所以这一条是「确认没被误关」而不是「去打开」
- [ ] 文本、工具卡、reasoning 在一轮内按 part 的真实顺序交替出现，不重排、不合并
- [ ] 「流结束后仍展开」与官方默认行为不一致，这一处差异**在代码里注明原因**，不要留给下一个人去猜
      为什么这里跟官方文档写的不一样
- [ ] 抄来的组件若要改才能满足上述行为，改处标注本地修改；能靠覆盖槽位解决的就不改上游代码
- [ ] 真 Chromium 验收：标记会话，让模型调 `read` / `write`，卡片与 reasoning 按上述行为出现，截图留档
- [ ] 验收方式是逐条对位，不是「看着差不多」：工具名与参数逐字比对，reasoning 在 run 结束后确实没被折叠
