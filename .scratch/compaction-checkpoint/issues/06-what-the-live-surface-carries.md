# 06 — 查清楚：live 面比记录折叠大出来的那 1/3 是什么

**What to build:** 一个答案，不是一段代码。同一条记录（`a0621fce-…`）、同一段折叠
（`context/compacted` 的 `:shadowed` 就是行 17..4944），两边的价钱对不上：

| 谁报的 | prompt token |
|---|---|
| 真事那一发（记录第 9520 行 `model/end`） | **260,165** |
| 我按记录重建、发给同一个 provider 的那一发（`dev/scratch_fold_prompt_ab.clj`） | **171,798** |
| 我们自己的估价器（同一段面） | **190,195**（估） |

差出来的约 1/3（88k token ≈ 350k 字符）判不了是 live 的**推理文本**（记录里 516 条 assistant
message 自己带着 962,629 字符 `reasoning_content`，但 live 面未必与之逐字相同）、
**per-run 注入**（`plan` 的 docstring 说记录折叠「drops every run's injections except the last one」）、
还是别的（网关自己加的东西）。

为什么要答案：压缩的每一个决定（触发阈值、保留尾巴的预算、头部的大小、必须更小那一条）
都建立在「量的是同一个数组」上。`.scratch/compaction-shape` 记的正是上一次「量的和送的不是同一个
数组」的事故；这一次的差要么是真的（那就得说清谁多带了什么），要么是我们某一处折错了（那就是 bug）。
