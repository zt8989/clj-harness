# 04: 两种读法上台面

**What to build:** 今天两套读者挂到同一条流的两个 API 上——**推流**：`events.mux` 的订阅与
会话的门铃挂 `listen!`；**拉流**：`replay` 的折法、轨迹那条 NDJSON、窗口取页挂 `consume!`，
断线补沿用 `after` 与同一条游标语义。**推给谁、拉给谁，从此是同一件事的两种挂法**，而不是两套各自
演化的机制。

**Blocked by:** 02、03

**Status:** ready-for-agent

- [ ] 一条新行（任何 `:producer`）推给监听器，同时能被从旧游标起的消费者读到——同一条用例钉住
- [ ] 断线补齐与今天等价：游标是行号，缺口一段不漏不重
- [ ] 旧记录照旧（两种形状都认），读侧边界不变
- [ ] mux / 门铃 / 折法 / 轨迹 / 窗口的既有用例全绿

## 已落地的一半（2026-09-28）

**item 带上行的两种形状**：`{:thread-id :seq :line :row :producer}` —— `:line` 是落进文件的字节
（线上读者要的），`:row` 是它来自的那个 map（进程内的读者要的，别再回头解 JSON），
`:producer` 说谁写的（票 03）。`log!` 两样都交。判据：`harness.infra.stream-test` 新增
`an-item-carries-the-row-and-who-wrote-it`（监听器与从旧游标起的消费者都拿到同一件 item）。

## 余下的（还没搬）

把**老读者真正挂上来**，一个一个换：

1. **门铃**（`harness.edge.sessions/row-written!` 与 `record-grew!`，今天是 `log!` 直接调）
   → 会话上线时挂一个 `listen!`，`log!` 不再认识任何一个读者；
2. **mux**（事实环 + 每连接订阅）、**窗口的 mark**、以及 **replay / 轨迹 / 窗口的拉法**
   挂 `consume!` + `after`（`after` 是短环，长缺口仍读文件——这是设计，不是妥协）。

**动手前必须想清的一件事**：直接调是**没有竞态**的（写一行就叫一次），挂监听器则有一条窗口——
**挂上之前写下的行，监听器永远收不到**。所以挂的点必须**不晚于第一条写**（会话建起来时就挂），
否则窗口会以为记录没长、门铃会漏响。这是我暂时没敢直接搬的原因。
