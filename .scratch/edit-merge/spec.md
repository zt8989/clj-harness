# spec: 编辑只留一个名字 —— 照 omp 的策略把编辑动作并成一个 `edit`

**参考**：omp（`can1357/oh-my-pi`）的 `docs/tools/edit.md`（2026-09-17 读的原文）。
它的 `edit` 是**一个工具、一个 `input: string`（必填）**字段，载荷是「段 + 操作」的补丁语言；
模式由**配置**选（`resolveEditMode()`：模型专用变体 → `PI_EDIT_VARIANT` → `edit.mode` → 默认 `hashline`），
四种模式（`hashline` / `apply_patch` / `patch` / `replace`）**整体换掉 schema、prompt、例子、渲染器**
（`apply_patch` 那条甚至换掉 wire name，但**分派仍到同一个内部工具**）；
而**检索是拆开的**：`read` / `grep` / `glob` / `ast-grep` 各自独立，且 `read` / `grep`
**划定「看得见的行」**，编辑到看得见之外的行会被拒。

**一句话**：本仓今天锚点模式下有四个编辑名字（`replace` / `insert` / `grep` /
`undo_last_replace`），str-replace 模式下是另一个名字（`edit`）。本特征把**改写**并成一个 `edit`
——两个模式同一个名字、锚点模式下载荷是一段补丁语言——而**检索**（`grep`）与**撤销**
（改名 `undo_last_edit`）保持独立。这就是 omp 的「编辑合并、检索拆分」。

2026-09-17 立。六张票，见文末「交付顺序」。

## 问题

1. **同一个动作被拆成好几个名字，只因为寻址形状不同。** `replace` 改一个区间、`insert` 在某行
   前/后插一段，两者用的是**同一张锚点表、同一条落盘路径、同一个批计划器、同一套陈旧判定**，
   差别只在「你指的是一个区间还是一个缝」。omp 的策略正好把这一类判给合并（它的整套动作
   `PUT` / `CUT` / paste / `MV` 都在一个载荷里）。
2. **一个模型调用只能改一个文件。** 载荷是一张 JSON 表，文件由锚点反推（`replace` / `insert`
   的 `:park-reason` derivation 就是这么干的），所以「同时改两个文件」今天要靠**同一条消息里发两个
   调用**，再靠批计划器合成一次写。omp 的载荷天生多段（一个 `[PATH#TAG]` 一段，一次调用改几个文件）。
3. **模型手里没有「搬」这个动作。** 把一段代码从 a.clj 挪到 b.clj，今天只能是「读出来 → 写过去 →
   删原地」，三次调用、三段上下文。omp 有 `CUT … @name` + `PUT <N @name` 与 `MV`，这需要**寄存器**。
4. **模式与名字绑在一起。** `edit` 这个名字只在 str-replace 模式存在，锚点模式的四个名字在
   另一侧——于是「模型按什么编辑」这件事在工具表上是**换名字**而不是**换脸**。本仓其实已经有
   「同名、换脸」的机制（`read` / `write` 的 `:describe`），omp 的 `edit` 正是这个形状。
5. **所以本仓的工具表在编辑这一块与参考实现分道扬镳**，而分道扬镳的收益并不明显：
   模型要记四个名字与它们各自的参数，其中两个（`replace` / `insert`）讲的是同一件事。

## 决策

1. **形状照 omp：`edit` 一个名字、一个载荷。** 锚点模式下它是一个必填的 `input`（字符串），
   动词全在载荷里（`PUT` / `CUT` / paste / `REM` / `MV`）；**模式仍由配置选**
   （`harness.edn` 的 `:editing {:mode …}`），**永不**是调用参数——omp 的四种模式一个都不是
   调用参数，这是它最该照抄的一条。两个模式**共用 `edit` 这一个名字**，脸由 `:describe` 换
   （决策 8）。
2. **寻址用本仓的锚点，段头只写 `[path]`。这是与 omp 唯一的实质分歧。**
   omp 是 `[PATH#TAG]` 加**行号**（`PUT 4.=4:`），因为它的 tag 是**按文件**的、由规范化内容算出来；
   本仓的锚点是**按行**的（`a3f9│content`），铸造、归属、已展示、陈旧判定全挂在它上面。
   照抄 `#TAG` + 行号等于把锚点降级成「文件版本号」，那是把本仓已经落地的东西拆掉。
   代价：载荷比 omp 啰嗦（一行一个 4 字符名字）；收益：陈旧与「看得见的行」的粒度停在**行**上，
   而且 `[E_RANGE_STALE]` 那套「回带新锚点、重试不必再读」可以**逐行**给。
3. **`N*`（整块）不搬。** omp 的 `PUT N*:` / `CUT N*` / `PUT >N*:` 要一棵语法树（tree-sitter），
   本仓没有 AST（`rg` 是纯文本搜索）。这三形**指名拒绝**，话里说清「本仓按行寻址，请给显式区间」。
   **这是明示的减法，不是漏掉**，也要写进工具描述，免得模型一直试。
4. **多段照搬，语义也照抄。** 一个载荷可以含多个 `[path]` 段，一次调用改多个文件；
   **所有段先解析校验、再按序落盘**（fail fast：任何一段语法/锚点/空改动有问题，一个文件都不改）；
   OS 写失败**可能**留下已经落盘的前缀——omp 明说这条，本仓也明说，不假装原子。
5. **寄存器照搬。** 匿名寄存器是**批内**的（每次调用开始是空的），具名寄存器**活在会话里**，
   且**只在它的写成功之后才发布**；重复 paste 不消耗它。这是本特征**唯一新增的会话状态**，
   住在进程内存、按会话分家（与 `kernel.tools` 的 overlay、parked 记录同一个立场，见
   `.scratch/immutable-data/` 那节纪律）。没有它 `CUT` 就没有去处，跨文件搬代码无从表达。
6. **撤销不进 `edit`，而且改名：`undo_last_replace` → `undo_last_edit`。**
   omp 的 `edit` 没有 undo（它的 `rewind` / `checkpoint` 是另外的工具）；本仓的撤销读的是
   「每个文件最近一次」的**逆**，不是「地址 + 落盘」，所以它是另一个工具。名字跟着单位走：
   撤销的单位从「一次 `replace`」变成「一次 `edit`」——这正是本仓自己那条「名字把单位说清楚」
   （`undo_last_replace` 当初就是从 `undo_last_change` 改过来的）。
7. **检索不进 `edit`。** ~~`grep` 保名~~：omp 把 `grep` / `ast-grep` 独立，而且 `read` / `grep`
   正是「看得见的行」的来源——检索与编辑是两件事，合并它们会把「我看到了什么」和「我改了什么」
   混进同一次调用。~~也**不改名成 `grep`**：本仓没有非锚点的 grep 与它争，而这个名字说清了它给的
   行是**带锚点的**。~~

   > **加注的复议（2026-09-22，`.scratch/omp-parity` 票 01）**：划掉的两半分开说。**检索仍然不进
   > `edit`**——那半照旧成立。但它**改名成 `grep` 了**，而且理由正是这里写的那一条反过来读：本仓
   > 确实没有非锚点的 grep 与它争，所以「anchor」那半只是在说一件显然的事；名字与 omp 对齐，
   > 配置键一并从 `:anchor-grep` 改成 `:grep`。
8. **描述就是语法说明书。** omp 的 schema / prompt / 例子 / 渲染器随模式整体换；本仓对应的机制是
   `:describe`（名字不变，description 与 parameters 随会话换）。所以锚点脸的描述要**自带动作表
   与两个例子**——模型关于这门语言的全部知识都从这里来。str-replace 脸仍是 `old_string` /
   `new_string` 那套，一个字不改。
9. **围栏要看得见载荷里的路径（本特征最容易出漏洞的一处）。** 今天 `replace` / `insert` 的
   `:park-reason` 靠一条 derivation 从**锚点**反推文件；载荷进来之后，文件由**段头**给出，
   所以 derivation 要多一条「从段头取路径」。**`REM` 与 `MV` 必须在段头解析出来之后立刻能被判**，
   否则一条 `REM` 会在没有门禁的情况下删掉项目外的文件。因此段头解析必须是**纯函数**、且对畸形
   载荷宽容（答 nil，把报错留给参数检查那一行）——与今天 `fenced-path` 的立场逐字相同。
10. **拒绝词汇照抄齐**（omp 的 `Common failures` 那一节就是清单）：缺失/畸形段头、未知锚点、
    锚点落在文件外、落在**没展示过**的行、逆序或重叠的区间、空 body、给不吃 body 的动作配了 body、
    未知寄存器、无名 paste 出现在一次明确的 cut 之前、「统一 diff 污染」（`@@` / `-旧行`）、
    `REM` / `MV` 冲突与非法目的地、**逐字节无变化**（改了等于没改是错误）、以及 no-op 三连的
    循环守卫。每一条都要**指名**，因为模型只能靠话术改。
11. **UI 两行。** `subjectOf` 的 `edit` 要读载荷的**第一个段头**（`TOOL_ICONS` 里 `edit` 已经有
    铅笔图标，不用动）；`replace` / `insert` / `undo_last_replace` 那三条 case 跟着名字退场/改名。
    这是本特征唯一的前端改动。
12. **批计划器收窄，但不退场。** 载荷已经装得下一条消息里的大部分改写，可「同一条消息里两个
    `edit` 调用撞同一个文件」仍然要合成一次写（否则后写的赢、两个都报成功——这条理由一个字没变）。
    `batchable?` 从 `#{"replace" "insert"}` 变成 `#{"edit"}`，而**旧的区间算术搬进载荷解析**：
    「重叠的编辑要拒」「同一个原始锚点被两次指向要拒」在 omp 那边是**载荷内**的校验，
    在本仓它将同时是载荷内与跨调用两个层次的事，两处的判据必须**共用一份**实现。

## 非目标

- **不搬块/语法树**（决策 3）：`N*` 三形、以及任何依赖 AST 的解析。
- **不加第二、第三种模式**：omp 的 `patch` / `apply_patch` 不搬，本仓只有两套编辑实现。
- **不引入 `PI_EDIT_VARIANT` 那样的环境变量与模型专用档**：本仓的模式只有 `harness.edn` 一档。
- **不做 staged（`xd://resolve` / `xd://reject`）审批流**：那是 omp 的 `ast_edit`，本仓的审批是 park。
- **不动锚点本身**：铸造、归属、已展示、陈旧判定、`read` 的 `a3f9│content` 输出形状一个字不改。
- **不给 `REM` / `MV` 加新的审批类型**：它们与 `write` 同一类（项目内的文件级副作用），
  围栏照旧（出界 park），要审批的会话自己 `session-require-approval!` 装规则。
- ~~**不把 `grep` 改名**（决策 7）~~ **已推翻**：2026-09-22 起它就叫 `grep`（`.scratch/omp-parity`
  票 01），**不动 `write` 的定位**（要么创建、要么整份覆盖）。

## 验收主线

一条真会话，七件事看得见：

1. `read` 一个文件 → 一次 `edit` 的载荷里 `PUT a1..a2:` 换两行 → 文件内容对，答案是**新的锚点行**。
2. **一次调用改两个文件**：载荷三个段、两个 `[path]`；其中一段畸形 → **一个文件都没改**
   （fail fast），答案指名说那一段哪里错。
3. **搬代码**：`CUT a1..a3 @fn` 在一个文件、另一个文件的段里 `PUT <a9 @fn` → 代码真的过去了；
   具名寄存器在**下一次调用**里还能 paste（它活在会话里），而匿名寄存器在本次调用之后就没了。
4. **两个模式一个名字**：`:editing {:mode :str-replace}` 的会话调 `edit`，参数是
   `old_string` / `new_string`（老样子）；锚点模式调 `edit`，参数是 `input`；两次拿到的**描述不同**。
5. **拒绝面**：逐条打畸形载荷（未知锚点 / 没展示过的行 / 逆序区间 / 空 body / 无名 paste /
   `N*` / 逐字节无变化），每条都得到**指名话术**，没有一条是裸异常或「未知工具」。
6. **围栏**：载荷里有一个段头的路径在项目外（以及一条 `REM`）→ **park**，不是静默执行；
   未绑定项目的会话照旧放行。
7. **全量**：`timeout 900 clojure -M:test -m harness.test-runner` 与 `cd ui && npm test` 都过；
   UI 里锚点模式的 `edit` 一行显示**第一个段头**。

## 跨特征对照

- **`.scratch/hashline-edit/`（已落地）**：本特征是它的**工具面**复议——锚点本身一个字不动，
  改的是「它们挂在几个名字上」。它那条批决策（一条消息里的多个锚点编辑合成一次写）在本特征里
  **缩水但不消失**（决策 12），它的区间算术搬进载荷解析，且两份实现必须共用（决策 12 末句）。
- **`.scratch/bash-lifetime/`（已落地，未合回）**：它的票面用过一条论据——「本仓编辑工具集也是
  一个动词一个名字」——来支持 `bash_background` / `bash_output` / `bash_kill` 三个名字。
  本特征让那条例证**作废**：三个后台名字的理由回到它自己那条硬理由（**起 / 读 / 停是三个状态机**，
  不是同一件事的三种拼法），与编辑无关。按本仓的惯例，落地那天要往**它**的 spec 加一段**加注的复议**
  （旧话不动、被推翻的那一行划删除线），而不是只在本文件里记一笔——`.scratch/` 是历史，历史用**加注**
  改口，不用重写。
- **`.scratch/tool-toggles/`（已落地）**：`edit` 一旦两种模式都有，「模式减法」那张表就只剩
  `grep` / `undo_last_edit` 这些名字的加减，`cap.editing/families` 的注释与
  `unserved-message` 的话术要跟着改（它们现在把 `edit` 当**另一个模式**的工具）。
- **`.scratch/immutable-data/`（已立票未落地）**：寄存器是本特征唯一新增的会话状态，
  按那节纪律**按键分家**（`thread-id`），读写都在同一个 `swap!` 里完成。
- **`.scratch/trajectory/`（已落地）**：工具表在 `model/start` 上，本特征只改表的**内容**，不动机制。
- **`docs/architecture/kernel.md` 的模式表**与**`client.md` 的两张表**是「现状」那一侧，
  收口那票要跟着改。

## 交付顺序

`01 → 02 → 03 → 04 → 05 → 06`，每一步都真的挡住下一步：没有载荷与 `PUT` 就没有可解析的语言；
没有多段与围栏就先在项目边界上是错的；没有寄存器就搬不了代码；没有跨模式同名就还没合并；
守卫与拒绝词汇只能在动作齐全之后才写得准；收口在最后。
