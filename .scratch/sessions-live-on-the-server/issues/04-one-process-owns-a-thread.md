# 04 — 认领：一个 thread 归一个进程

**What to build:** 一个 thread-id 同一时刻归**一个进程**。后到的进程只读或拒绝，**并说出理由**。
锁文件，或库里一行 owner——二选一，选完写清为什么。

**Blocked by:** 01

**Status:** ready-for-agent

## 要落地的判断

1. **为什么必须有**（ADR 决策 7）：记录是异步的、允许落后的，两份权威交错写进同一个 append-only 文件
   之后**没有任何东西能把它们分开**——一行 JSON 里没有「这是谁的帧」这个字段。
2. **与 `running?` 的分工**：`running?`（`http.clj:517`）是**进程内**的注册表，它答不了另一个进程里
   有没有人在跑同一场。本票补的是**跨进程**那一半，不替换它。
3. **认领的粒度是进程，不是 run**：会话表（票 01）住在进程里、寿命是空闲 30 秒，所以「谁持有这一场」
   的答案必须是**进程级**的；一个 run 结束不该让出认领（那样下一轮就要重新认领，而重建是冷的）。
4. **认领与空闲 30 秒的关系**：票 01 放掉会话之后，认领要不要一起放？**要**——否则一个空闲的会话会
   永远占着一个进程，而那正是「限制同时运行的会话数」想避免的。两票的接口要在这一票对齐。
5. **后到的那个**：只读（能看、不能发）还是拒绝（打不开）——选一个。**我倾向只读 + 明说**：能看历史、
   不能发动作，说清「另一个进程正在服务这一场」。打不开比看得见但发不出去更难看。
6. **陈旧的认领**：进程崩了，锁文件怎么办。要定：pid 活性检查、还是带心跳的时间戳、还是「人手动清」。
   **不许**只写「正常情况下会释放」。
7. **与 `.scratch/parallel-sessions` / `.scratch/immutable-data` 的既得分家规矩对齐**：进程内那些
   按会话分家的状态（锚点、待办）不能因为这一票而多出一份。
8. **认领易主 / 会话放掉 ⇒ feed 的 generation 作废**（ADR 0003 决策 6，票 05 判断 7）：释放认领的
   那一刻，就是副本窗口作废的那一刻——两边要在**同一个时刻**说同一件事，接口在这一票对齐。
9. **非 owner 的只读进程能不能看 feed。** 判断 5 倾向「只读 + 明说」，而 feed 只由 owner 提供，所以
   「只读」还剩两种做法：**代理**（非 owner 从 owner 拉一条流再转发）或**降级**（只给存量 + 轮询，
   没有增量）。**我倾向降级**：代理引入一条跨进程的长连接与它的寿命、重连与背压，而「只读」要买的
   只是「看得见历史」。选定之后要写下来，并且验收里说清非 owner 的页面上**有没有**增量。

## 验收

- [ ] 第二个进程对同一场发起动作 → 拒绝（或只读），**理由里说得出是哪个进程**（有用例，起两个 JVM）
- [ ] 第一个进程正常退出 → 认领释放，第二个进程可以接手（有用例）
- [ ] 第一个进程被 `kill -9` → 陈旧认领有明确处置（有用例；不许「等它自己好」）
- [ ] 空闲 30 秒放掉会话时，认领一起放（有用例）
- [ ] 认领易主 / 放掉时，原先连着的 feed 收到**终态**（与票 05 同一条，不是静默断）
- [ ] 非 owner 的只读页面按判断 9 选定的那个行为：要么有增量（代理），要么没有（降级）——有用例说清
- [ ] 进程内 `running?` 的既有用例全绿
