# 05 — 会话 feed：尾页、增量、补页（服务端一条 source）

**What to build:** 服务端把一场会话当作**一条 feed** 供出去。打开拿**尾页** + `baseSeq` + `hasMore`；
此后窗口内的新条目**推**给连着的副本；更早的历史按 `beforeSeq` **一页一页拉**。序号单调，而且
**能从记录重放出来**（同一条消息重建两次、刷新之后序号相同）。`rebuild` / `sofar` 的 **live** 语义
改成读内存。会话被放掉（空闲 30 秒）/ 进程不再是它的 owner（票 04）⇒ **generation 作废**，副本重开尾页。

决策见 `docs/adr/0003-the-feed-is-a-window.md`。

**Blocked by:** 01

**Status:** ready-for-agent

## 要落地的判断

1. **序号的坐标系，以及它为什么只能是「记录偏移」。** 三个约束要同时成立：
   - **不改记录格式**（非目标）⇒ 序号不能是写进 jsonl 的新字段；
   - **必须能从记录重放出来**（ADR 0003 决策 9）⇒ 序号不能是纯内存计数器；
   - **卡消息与只给模型看的消息，在两套折叠里的去留不同**——票 01 的 `without-cards` 把卡丢掉，
     而客户端**要**画卡 ⇒「对话第几条」这个坐标系对两边不成立。

   同时满足三条的只有**记录的日志偏移**：append-only、一个写者，第 N 条就是第 N 条。
   **代价要写下来**：内存里比记录新的那几条还没有偏移，所以会话要按 `next-seq` 铸号，而写者（票 02）
   必须把它们**逐条**写成对应条数的记录。这是会话与写者之间的一条**契约**，不是巧合——票 02 有对应
   的一条判断与用例，两票在这一点上是同一件事的两半。

2. **尾页的条数是一个写下来的数字。** 参考实现用 50（`events.open({ maxMessages: 50 })`）。照抄可以，
   但仓库的规矩是判据要说得出数字**且说得出它是判断**：docstring 里写清「这是一个人的判断」，
   不是「测出来的最优」。

3. **一条 feed 三个动词，落在同一个窗口状态上。** `tail`（打开/重开尾页）、`append`（推）、
   `prepend`（补页）。别做成两个接口——`hasMore` 与 `baseSeq` 必须只有一处说了算，否则推送与补页
   会各自算一次，然后打架。

4. **传输：SSE 还是 WebSocket。** `POST /api/agent` 已经证明 SSE 这条路（`http.clj:622` 的 emitter，
   连着「http-kit 小写 header、状态与头只能骑在第一次 `send!` 上、对端 RESET 了 `send!` 仍答 true」
   那几条踩出来的坑）；WebSocket 要新依赖与它自己的重连。**我倾向 SSE**：不加依赖，而且
   `http.clj:645` 那条教训的处置（close handler）是现成的，复用比新学一遍便宜。选哪个都要写清
   「一条 feed 一条连接」的**寿命与取消**。

5. **`since` 的语义。** 副本说「我有到 N」，服务端从 N+1 发。N 落在窗口外（被放掉 / 重开 / 认领易主）⇒
   **拒绝并说出 generation**，让副本重开尾页——不从头发（那会重复），也不静默断（那会让副本以为到齐了）。

6. **`rebuild` / `sofar` 的 live 语义。** live 会话 ⇒ 读内存，`close-off-open-run!`（`http.clj:1827`）
   **不参与**——它是对**死掉的**会话做的事；冷启动 / 归档 / 作者工具（`evals`）⇒ 仍读记录。
   这条分岔写进路由的 docstring，并有用例钉住。`sofar` 的 `:state`（running / parked / settled）
   要和页一起回，作为 baseline 的一部分，不要拆成两次读。

7. **放掉一个会话时 feed 怎么办。** 连接必须收到终态（「这一场被放掉了」），不是静默断；副本据此
   重开尾页。这与票 01 的 `sweep!`、票 04 的认领释放是**同一个时刻的三件事**，接口要在这一票对齐。

8. **`stats` / `trajectory` 的 live 视图。** 它们今天读记录（`stats/log-stats`、`trajectory`），在落后
   窗口里会显示一份更短的会话。要定它们**怎么读到内存那份**：同一个 seq 的读法？还是一份内存快照？
   （原票 05 的判断 7 搬到这里，因为它读的是同一条 source。）

## 验收

- [ ] 打开一场有 300 条消息的会话：第一个响应只带**尾页**（条数 = 写下来的那个数字），且 `hasMore`
      为真（有用例）
- [ ] `beforeSeq` 补一页：拿到紧挨着的那一页，`baseSeq` 前移，**不重叠、不丢**（有用例）
- [ ] **序号能从记录重放**：同一场重建两次、以及刷新之后，同一条消息的序号相同（有用例）
- [ ] 内存比记录新的那几条：会话铸的序号与写者落盘后的偏移**一致**（那条契约的用例，与票 02 同一条）
- [ ] 增量推送：一场正在跑的会话，连着的副本在**没有轮询**的情况下看到新条目（有用例；走查再抓一次）
- [ ] `since` 落在窗口外 ⇒ 拒绝并说出 generation，不静默从头（有用例）
- [ ] 会话被放掉时 feed 收到终态，不是静默断（有用例）
- [ ] `rebuild` 对 live 会话不调 `close-off-open-run!`；对死掉的会话照旧调（有用例）
- [ ] `node scripts/dev.mjs --scripted` 走查：发一条、看它跑完，全程没有 `sofar` 轮询
