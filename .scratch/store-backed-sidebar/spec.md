# spec: 左侧全部来自库 —— 上次发送时间、单行、缩进槽、发送才建会话

主人一段话定了六件事：

> 刷新按钮显示从磁盘和库加载，我的原则是**左侧所有会话信息都是从 sqlite 加载，除了运行状态**，
> **去除文件大小**，参考截图，**只显示上次发送时间**，然后**按照上次发送时间排序**，
> **点击新增不立刻会话，发送才新建**，**项目和会话要有明显的缩进，留下的缩进刚好显示 loading 状态**。

一句话概括这次改动的方向：**侧栏从「库 + 磁盘两份事实的 join」变成「一份库事实 + 一个进程内事实」**。
`GET /api/projects` 今天每行要 stat 一个日志文件（大小、mtime），还要为任务走一遍树；改完之后它
**只读库**，加上进程里的 `running`（那一条是你说的例外）。换来的代价与它的替代方案都写在下面。

## 一、一件事一件事地读

### 1 「左侧所有会话信息都从 sqlite 加载，除了运行状态」

列表的每一行以后只由两处回答：

| 行上的东西 | 谁回答 |
|---|---|
| 这行是谁（id）、归哪个项目、归档没有 | 库里那行 |
| 叫什么（第一句） | 库里 `sessions.title` |
| **上次发送时间** | 新增的库里 `sessions.last_sent_at` |
| 在跑没有 | 进程内的 live-runs registry（你说的例外，也是唯一一个文件答不了的问题） |

因此**磁盘那一半整块退场**：`bytes` 没了、`lastActivity`（mtime）没了、任务行不用再按 stem 问整棵树
（`task-row` 的 `by-stem` 参数和 `projects-get` 里那次 `replay/threads` 树遍历一起删掉）。
副作用是这一版把「列表要把整棵树 walk 一遍」这件事从侧栏的每一次刷新里拿掉了——刷新从此是一次
SELECT 加一次 registry 查。

### 2 「上次发送时间」是怎么来的

**每次 run 的 input 到达时写一次**（`run-agent!` 里，与 `log!` 同一处），列 `last_sent_at`
（epoch millis）。所以它记的是**人按了发送的那一刻**，不是日志最后被写的那一刻——一次跑五分钟，
这一行的时间停在按下去的时候（这正是「发送时间」的意思）。

- 与标题**同一条语句**写掉：`UPDATE sessions SET last_sent_at = ?, title = COALESCE(title, ?) WHERE id = ?`
  （`cap.project/remember-send!`）。标题那条「只写一次」的规矩从 `title IS NULL` 变成 `COALESCE`，
  仍然是同一句 SQL 里的同一个判断，仍然不可能被第二次 run 改写。
- **续跑（resume）也算一次发送**：它是人点了继续、带着整段历史 POST 过来的，走的就是 `handle-run`。
  不做特例——特例的代价（一个「什么算发送」的清单）比它解决的问题大。
- **老会话要回填**，见下一条。

**回填，而且这是这一版唯一一次读磁盘。** 迁移步 `sessions-remember-their-last-send`
（`ALTER TABLE sessions ADD COLUMN last_sent_at INTEGER`）里顺手把老行填上：值取**那条日志文件的
mtime**——正是列表从前显示的那个数，语义上就是「上次活动」；新写入的值是发送时刻，两者差一次跑的
时长，写进 docstring 里。不填的话，本机 53 条老会话会在侧栏上**一个时间都没有**，而这一列恰恰是
主人要的东西。这一步做完，磁盘那条路就彻底没有了：`code` 里不再有「没有就去看文件」的兜底分支。

（`infra/db.clj` 做这一步需要知道日志在哪：`harness.infra.home` 已经有 `projects-dir`，stem→文件
的查找也归它——**infra 里不许出现 edge 的依赖**，所以不是 `replay/locate`。）

### 3 「去除文件大小」「只显示上次发送时间」「按上次发送时间排序」

- 行上的第二行（`mtime · bytes`）整条去掉，**时间挪到第一行右端**（截图那样）。
- 时间是**相对**的：`刚刚 / 56 分钟 / 1 小时 / 3 天`，超过 7 天给日期（`9/14`）；**完整绝对时间进
  hover 的 tooltip**（与 thread-id 同一个 tooltip：`title` 属性里两行）。
- 排序：`lastSentAt` 降序。**NULL 排最后**（老 `newest-first` 把「没有日志」当最新——那是
  「刚建的行」的意思；现在没发送过 ≠ 刚建，因为发送才建会话，能留下 NULL 的只有旧客户端注册过的空行
  与日志被删掉的会话，两种都该沉底）。
- `session.neverRun`（`还没跑过`）留着，只为 NULL 那一行；`session.noLog` 与 `formatBytes`
  在侧栏不再有调用点（`formatBytes` 若别处也不用就删，实现时按 grep 定）。

### 4 「点击新增不立刻会话，发送才新建」（你选的那条路）

- 点「新建任务」/「项目中新建会话」：**只 mint 一个 id、在页面里打开一个空会话**，不写库、不刷新。
  列表上什么都不出现——库里还没有这一行。
- 第一次发送时，会话才诞生：任务由 run 那条路自己注册（`handle-run` 的
  `register-run-session!`，本来就在）；项目会话**由页面在发送那一刻先 `POST /api/project`
  绑到刚才那个项目**（页面记得「这个 id 属于哪个目录」）。`bind!` 是 upsert，所以即使 run 先到、
  会话先以任务身份建出来，紧接着的 bind 也会把它移进项目——顺序不影响最终归属，只影响一瞬间的
  分组（那一刻列表通常还没刷新）。
- **这条路的代价是「绑定会落在 run 中途」**：那一刻写手正在写这条会话的日志，而这个 bind 会把那份
  日志**搬**到项目 workspace。两者的次序必须由同一把锁定（票 05），否则一次会话会被劈成两份文件。
- **于是「新会话」要出现在列表里，必须有一次刷新**，而触发点不能是「发送那一瞬间」（那时服务端
  还没收到 run）。取**这次 run 结束**：侧栏看到「我握着一个有标题、却不在列表里、也不在跑」的会话，
  就再问一次库（每个 id 每次页面加载最多问一次，不可能成环）。刷新现在是一次 SELECT，便宜。

### 5 「项目和会话要有明显的缩进，留下的缩进刚好显示 loading 状态」

- 会话行**整体缩进**到项目行图标右侧；缩进那一条**就是 spinner 的槽**：跑起来时
  spinner 出现在槽里，标题的起点不动（不跑时槽是空的）。缩进宽度 = spinner 宽度 + 间距，
  所以「留下的缩进刚好显示 loading 状态」是量出来的一个数，不是估的。
- 行变**单行**（你选的）：`[槽: spinner][标题 …][右: 相对时间]`，hover 时右侧出现归档/更多。
- **当前会话只用底色**，`CURRENT` 那个词去掉（目录里 `session.current` 一并删，两个语言都删）。
  `等你回应`（parked）与归档区那个项目名仍在右侧、在标题的截断元素**之外**——
  这条规矩是从上一版量出来的，不能因为行变短就把它挪回去。

## 二、非目标

- 不显示文件大小、不在列表里读任何日志（`GET /api/threads` 仍是诊断用的原始树视图）。
- 不删除 `POST /api/sessions` 这个端点（run 那条路与旧数据都在用它表达「让它存在」）。
- 不做「会话按项目分组之外的分组」、不做搜索、不做重命名。

## 五、走查实测

`node scripts/dev.mjs --scripted .scratch/store-backed-sidebar/evidence/script.json --ui-port 5219` +
`.scratch/store-backed-sidebar/walkthrough.mjs`（真 Chromium、脚本家、隔离家；每一格按 session id 认，
所以可以重复跑）。七张截图在 `evidence/`，量到的数：

| 验收 | 怎么量的 | 结果 |
|---|---|---|
| 行上没有文件大小 | 每一行的 `thread-list-item-meta` 不存在、markup 里没有 `N B/KB/MB` | 通过（老会话行也是） |
| 列表只从库来 | 刷新键的 tooltip | 「从库里重新读取列表」（没有「磁盘」） |
| 点新增不立刻建会话 | 点「新建任务」前后列表的 id 数组 + **直接 `GET /api/projects`** | 两边都没有新行；页面确实在一场有 id 的新会话上 |
| 发送才建会话 | 第一句之后（**中间没点刷新**） | 行出现、在**最上面**、右端「刚刚」、tooltip = id + 绝对时间；库里那行 `firstUserText`/`lastSentAt` 对得上、`projectId` 为 null |
| 项目里的新会话落在那个项目下 | 项目下那块的行 + 库里 `projectId` | 行在**那个项目**下（不在任务块）、库里 `projectId` 正确 |
| 项目和会话有明显的缩进 | 项目名 x、图标 x/宽、行标题 x | 图标 14 + 宽 16 → 名字 36；**行标题也是 36** |
| 留下的缩进刚好显示 loading | 空槽的 x/宽、跑起来时 spinner 的 x/宽、标题 x（跑前/跑时） | 槽 14×14、`gap-1.5` 6；spinner 落在槽的范围内；标题 **36 → 36**（不动） |
| 发送过一次再刷新行仍在 | 按刷新键 | 项目下与任务块两边都还在、时间还在 |
| 绑定不报假错 | 行底下有没有 `thread-list-item-error` | 没有（**这一格最初是红的**，见票 05） |

## 六、落地时与计划的出入

- **票 02 的 `relativeTime(ms, now) → string` 实现成 `relativeAge(sentAt, now) → 结构`**：
  「超过 7 天给日期」要 `toLocaleDateString`，而那是渲染的事；纯函数只答**哪一档**，
  词从调用方词表取（和 `sessionTitle` 同一个形状）。
- **缩进没有写在 `sidebar.tsx` 里**（票 02 是那么计划的），而在会话行自己的类名里：
  `ps-2`(8) + 槽(14) + `gap-1.5`(6) = 36 = 项目行的 `px-1.5`(6) + 图标(16) + `gap-1.5`(6)。
  写在行上是因为**槽必须永远画出来**（不跑时是空的），否则标题的 x 会跳；
  数在两份文件的注释里，走查量。
- **`formatBytes` 没有删**（票 02 说「若无调用点则删」）：`file.tsx`、`context-card.tsx`、
  `suites/stats.ts` 还在用。
- **待绑定项目用的是 `app.tsx` 里的一个 ref**（`pendingBinds`），触发点是已有的 host 上报
  （`reportTitle` 非 null = 第一句真的发出去了），不是新加一条发送回调。失败落进
  `openErrors[id]`——**那一行**上的一句话（与「历史读不出来」同一处）。
- **侧栏补刷新那一条**用 `asked` ref（每个 id 每次页面加载最多一次），输入是 `liveTitles` /
  `statuses` / 列表 id 的并集，所以成不了环。
- **多了一张票（05）**：走查第一遍就逮到「绑定撞上正在写的 run」——一句假的拒绝、以及**真的会把
  一次会话劈成两份**的那种交错。修法是让 `log!` 与 `/api/project` 共用 `log-lock`
  （连「这条记录写哪个文件」都在锁内），并配一条十二次换绑 + 不停写手的用例（修之前 3/3 红）。
  这是这次改动**唯一**动到后端写入路径的地方，它不在原计划里。
- **`sidebar.refreshTitle` 的措辞改了**（「从磁盘和库重新读取列表」→「从库里重新读取列表」）：
  主人那句「刷新按钮显示从磁盘和库加载」读成「列表不该再从磁盘加载」，所以按钮的说法跟着事实走。
- **`newTaskError` 那份状态删掉了**（票 03 只说「旧行为拆干净」）：它服务的注册动作没了，
  留下一份永远为 null 的状态只会让人以为还有一条会失败的路径。
- 老会话的标题仍然**不回填**（上一版的判决），而 `last_sent_at` **回填**——两者相反，
  因为一个是主人推翻守卫换来的新事实，另一个是列表从前就在显示、只是换了住处。
