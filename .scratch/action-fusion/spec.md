# spec: Action Fusion（本地序列住在 eval 里）

**一次 eval 调用就是一次融合**：模型在一个 eval 里调用工具表里的任何工具，按返回值决定下一步，循环做批量
操作——**中间没有模型**。`edit` 之后紧接着跑测试的那两轮，在这里变成一次调用里的两行代码。

**这个机制不依赖大模型**：合并发生在本地执行序列里，是一段控制流，不涉及任何生成或理解。
（SoL-Pi 的四个机制里 Action Fusion 与 ObservationPack 如此；Evidence-Preserving Reducer 要委托一个更便宜的
模型代读日志，Online Context Compact 要做「重写的成本能不能被未来省回来」的经济性判断，那两个依赖模型。）

**这一版不新增任何工具、不改任何工具的定义。** 融合是**调用层**的事，不是**工具定义**的事。

## 复议（2026-09-15，牛总）

初版把融合做成了**工具 schema 上的一个新参数**，撤销：

- ~~一次工具调用可以带 `then_run`：一条 shell 命令。~~
- ~~缝在工具体成功之后把它跑掉，把两个观察合成**一条**工具结果。~~
- ~~`specs` 给每个工具的 schema 补上这个属性，描述只有一份。~~
- ~~缝把它从参数字典里摘掉再交给工具体（`session-configure` 拒绝未知键是那条的动因），而让 hook 的
  `tool_input` 看得见它。~~

**撤销的理由（牛总）：不改变 tools 自身的定义；多个命令的执行靠 tools 与 eval。**

那一版做下来的四个决定随之一起没了：schema 注入、参数摘除、hook payload 的两份参数、
「一次调用两个观察」的结果格式。**留下的那条判断是这一版的纲：融合属于调用层，不属于工具定义。**

## 决策

1. **不改任何工具的定义。** 工具表、每个工具的名字 / 描述 / 参数 schema、执行缝的三个出口，**一个字节都不动**。
   本特征的第一条硬断言就是它：`specs` 的返回值与改动前**逐字节相同**。

2. **eval 是本地序列的住所，而且它今天就住得下。** 已实测：`harness.kernel.tools/run!` 在 eval 里照常工作，
   `harness.kernel.tools/*thread-id*` 在工具体里是绑好的，所以内层调用寻址的是同一个会话——相对路径照样重根、
   `bash` 照样以项目目录为 cwd。缺的不是能力，是**便利**与**诚实**。

3. **本地序列里的调用走完整的执行缝，一条都不少。** 已实测：一个 `:matcher "bash"` 的 PreToolUse 门禁
   拦住了一次从 eval 里发出的 `bash`，eval 拿到的是那条理由（当值，不是异常）。这是**刻意**的：
   一条只能看见顶层调用的规则，用 eval 包一层就能绕过去。

4. **手搓 JSON 不该是使用它的代价。** 内层调用今天要手写 provider 形状的
   `{:id .. :type "function" :function {:name .. :arguments <json-string>}}`，还要自己 JSON 编码参数——
   一次可以忍，循环二十个文件不行。加一个「名字 + 参数 map」的入口（`call!`），`thread-id` 默认到当前会话。
   **它是 `harness.kernel.tools` 里的一个函数，不是工具表里的一条定义**——这正是决策 1 允许的那类改动。

5. **脚本里做不到的事，指名说出来，不许静默。** 今天有两类会**半途而废**：
   - **需要人的调用**：悬置型判定命中时，内层调用会建一条 parked 记录、把 `{:parked ..}` 交给 eval 代码，
     而**运行不会中断**——人永远不被问，那条记录就此孤儿（已实测）。脚本里没有人可以问。
   - **`skill`**：技能的正文靠「某条 tool message 以 `[skill-loaded]` 开头」被发现
     （`harness.cap.skills/derived-injections` 把 `skill` 的 tool_call id 与那条消息对起来），脚本里的调用
     产生不了这一对——正文被取回又丢掉。
   - 两者都**直接拒**，点名理由/原因，并说清「作为顶层调用发出才行」。

6. **拒在缝上，不拒在入口上。** 手搓 `run!` 也是内层调用，**它同样不许静默 park**（实测那条路径一样会孤儿）。
   所以判定归执行缝；`skill` 这一条走本仓既有的**标记**写法（工具自己声明「只能在顶层用」，与
   `:fence-paths` / `:requires-approval` 同一族），缝照着执行。

7. **脚本里的每次调用都进审计流。** 三行 `tools/*` 今天只写给顶层调用：内层调用的相位事件没有去处
   （`run!` 拿到的是 nil on-phase）。把当前 run 的相位上报函数绑在一个动态 var 上（`*thread-id*` 的同族、
   同一个理由：内层代码要寻址自己所属的那次 run），内层调用默认用它。
   **id 由外层调用派生**（`<外层 toolCallId>/<n>`），读日志的人一眼分得出内层与顶层，也能机械地归到外层。
   注意 hook 那一半**今天就已经看得见内层调用**（实测），缺的只有审计线——这一条是把两边补齐。

8. **内层调用不出帧。** 不新增内核事件种类、不改 AG-UI 帧形状、不改既有 JSONL 行的 schema。
   UI 因此**不会多出卡片**：内层调用出现在 eval 那张卡片的正文里。这是对的——一个脚本的中间步骤
   不是七张卡片，那是把序列拆开给用户看。

9. **拒绝是信息，不是 run 的失败。** 内层被拒的调用返回 `{:error true :content "…"}` 给序列，
   序列可以据此改道继续，run 不炸——与「工具失败是给模型的信息，不是 run 的失败」同一条。

## 复议 2（2026-09-16，牛总）：说明走 hook，且是个开关

- ~~本特征要写进 prompt 的那一段属于**固定开头**那一半：「那个特征先落就写进新的固定开头，
  **不要塞进块**——块按会话现算，把一个与会话无关的句子放进去，它就会为一个与会话无关的理由而变。」~~
  **撤销。**
- **改后：不在 prompt 里写。** reasons（牛总）：**不在 prompt 中说明 eval 功能或者其他 tools 能力，
  因为本来在接口调用的时候 tools 就是自描述的；只需要通过 hook 注入 action fusion 的说明，
  这个是可配置的开关。**
- 落地形状（票 04）：
  - 说明是 `SystemPrompt` 点上的一条**内建行**，与 `<project>` / `<env>` 同一条表、同一条缝，排在它们之后；
  - **开关在 `harness.edn`**（`~/.clj-harness/harness.edn` 与 `<项目>/.harness/harness.edn` 两级装配，
    与 `:editing` / `:approval` 同一处），默认**开**；它同时也是一条普通的行，
    所以会话里 `session-disable!` 也关得掉（两条命令同一个效果，不是两份真相）；
  - 它**被 01–03 挡住**：`call!` 还不存在时告诉模型它存在，是这块最坏的形态。
- **两条推理并存，别把它们压成一条**：
  - **名册不必说**（这是牛总的理由，`<tools>` 因此退场）；
  - **技法不在 wire 上，所以得有地方说**——「怎么把工具串起来用」不是任何工具的描述覆盖得了的，
    而这块就是那个地方。也正因如此，它不该写进冻结的 `prompt.md`：技法会随机制演进，
    冻结文件里的每一句话都要过 `reset-prompt!` 才好改。

## 跨特性：与 `session-context` 的交界

`.scratch/session-context/`（2026-09-16 立，4 张票）把内核自己的行从三条改成两条：`<project>` 保留、
新增 `<env>`、`<tools>` 与 `<provider>` 退场。票 04 加的那一行**排在它们之后**，本特征**不改它的票**。
两边都不动对方的东西：那边改行集合，这边加第 N 行。

## 非目标

- **不做 ObservationPack**（本地归档 + `obs_xxx` 句柄 + 分页召回）。它同样不依赖模型，与融合正交：
  融合解决「多跑了一轮」，它解决「同一段大文本在每一轮里重复出现」。留给它自己的特征。
- 不做 Evidence-Preserving Reducer / Online Context Compact（依赖模型，见开头）。
- **不做新工具、不做新参数、不碰任何工具的 schema。**
- 不做多步序列的**语法**：没有 `steps: [...]` 这种东西，序列就是 Clojure——语言已经是这件事最好的语法。
- 不做超时（`bash` 的既有立场）、不做重试、不做命令内容的判定。
- 不改 UI：内层调用不出帧，也就没有新卡片。

## 验收主线

离线全量 `harness.test-runner` 全绿。两处是这一版的**承重断言**：

1. **零变化**：`specs` 与改动前逐字节相同——没有一个工具的定义被碰过。
2. **不静默**：内层调用命中悬置型判定时，人没被问、工具没跑、记录没留，而序列**知道**这件事。
