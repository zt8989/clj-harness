# 11 — 事件三域与「新行为该挂哪」

**What to build:** 事件是唯一的扩展点，所以**分域**是这套东西最要紧的一张表：**会话事件**（持久事实，
必须活过重载）、**agent 事件**（活体：观察或拦截在飞的活）、**能力事件**（`fs/*`、`tools/*` 这一类，
挂策略与适配器而不 import 循环）。本仓今天有内核 14 种事件、27 个 hook 点、一条帧流、工具的三个出口。
这一票把每个点归到**恰好一域**，给出「加一种新行为挂哪」那张表，顺带**定下 hook 引擎的归属**——
这是 spec 里列的三处待定之一，票 01 把它指到了这里。

**Blocked by:** 07 — `ctx.systemPrompt`；10 — 悬置、审批与恢复

**Status:** ready-for-agent

## 验收

- [ ] 每个事件点在三维里**恰好一个**归属；给不出归属的，指出它其实不是扩展点（该删或该合，不是硬塞）
- [ ] 「新行为挂哪」那张表：加工具 / 加 provider / 加策略 / 加只读的读法 / 加一出网后端 / 加一条人下发的命令——
      每一件事都有一行，指向**唯一**一个扩展点（照 dsh 那张同样用途的表）
- [ ] **hook 引擎的归属写下来了**：留脊柱还是成为挂能力事件的能力插件，选一个，并给出代价——
      本仓 `docs/architecture/layers.md` 里那段反面意见要接上，不能装作没写过
- [ ] 「需要活过重载的事实必须是会话事件」这条进了守卫或断言：新的模型可见输入走事件，不走别处
- [ ] 帧流与三域的关系说清了：哪些行是持久事实、哪些是只给屏幕的活帧（注入物与压缩那两张卡属于后者）
- [ ] 三域各自的**派发模式**写清（哪些是瀑布、哪些是顺序、哪些是即发即忘）——本仓今天没有这套词汇，
      它是「谁能不能拦」这件事的答案
