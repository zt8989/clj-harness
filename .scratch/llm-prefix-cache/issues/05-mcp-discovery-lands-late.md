# 05 — MCP 的名单迟到落地（排在最后）

**What to build:** 查清一个会话里 MCP 工具名单是否**在首次模型调用之后**才补齐，若是则决定：
是让首次调用等一个「发现已 settle」的屏障，还是至少把「这次调用拿的是第几代名单」记下来，
好让票 04 的报告能点名。

**Blocked by:** 04（先有报告，才有「改前 / 改后」可比）

**Status:** 已给出结论（要的那个决定是「不动」，无代码改动）。按 `docs/agents/triage-labels.md`
的约定，做完了的票应当从 `issues/` 移除而不是换标签——**这一步留给人**，理由见 `spec.md` 末尾。

## 为什么是这张票

1. **证据**：会话 `d62a2cd9`（2026-09-21 14:23）的工具表在**自己会话中途**从 95 个变成 96 个，
   多出来的那一个是 `mcp__zvec_grep__zvec_grep_search`。一个工具在会话中途出现，只可能是
   某个 MCP 服务器的名单在那时才有答案。
2. **代价是整段前缀**：工具表在消息**之前**，所以那一次补齐把**此前写下的所有缓存**作废——
   不是多一个工具那么便宜，是整场对话从 token 0 重算。
3. **它今天是「每调用时取」的形状**：`specs`（`kernel/tools.clj:411-417`）每次模型调用都调
   `effective-tools` → `session-tools`（`:338-347`）→ 折进来的 `:tools-for` 贡献（MCP 的那一份）。
   所以**当时知道多少就发多少**，这是有意的（一个服务器没起来不该让整个工具集陪葬），但它同时
   意味着**第一次调用可能发一张不完整的表**。
4. **本次要回答的问题**（不是这张票能凭空定的）：
   - 首次模型调用发生时，MCP 的名单**是否**已经 settle？`cap/mcp.clj` 的连接与列名单是
     在会话出生时同步等，还是后台落地？
   - 如果会迟到：等一个屏障的代价是什么（一次调用慢一点）与不等它的代价（一次冷前缀）
     哪个大？**要量，要拿票 04 的报告量**，不要凭直觉选。
   - 有没有第三种：不等，但把名单的**代**记在 `model/start` 那一行上，让报告能说
     「这次调用拿的是第 N 代」，从而把「我们发了一张中途变过的表」与「厂商没认回」分开。
5. **别顺手扩大范围**：playwright 名单跨天的变化（`browser_emulate_media`、`browser_webmcp_call/list`
   的出现与消失）是外部服务器版本差，**不在**这张票里。

## 答案：会 settle，而且是同步的——首次调用本来就在等

`tools-for` 在 `:1015` **同步**调 `server-connection`：连线、握手、`tools/list` 全在那一步等结果，
或等到那台服务器自己的 `:timeout`（默认 60s）。答不出来的一台记为 `:failed`、贡献零个工具，别的
服务器不受影响（`:1022-1027` 写明的取舍）。

**所以不存在「后台还在发现、首次调用拿到半张表」这种竞态。** 首次调用拿到的是**那时所有已声明
服务器答出来的东西**——它已经是完整的了；会变的只是「已声明」这个集合本身。

### 量到了什么（会话 `d62a2cd9`，2026-09-21）

| 时刻 | 事件 | 工具表 |
|---|---|---|
| 46.2s | `provider/init`（会话开始） | — |
| 48.7s | 第 1 次模型调用 | **95**（16 内建 + playwright 25 + agentmemory 54）：两台已声明的**都齐了** |
| 51.0–77.3s | 第 2–5 次调用 | 95（不变） |
| **78.1s** | **一个 `write`，TOOL_CALL_ARGS 里的路径是 `~/.clj-harness/mcp.edn`** | — |
| **79.1s** | 第 6 次调用（写入后 **0.9 秒**） | **96**（+ zvec_grep 的 1 个工具） |
| 84.7s | 第 6 次的 `usage` | `prompt=255857`，**`cached=14720`**（前一次是 `252544`） |
| 87.8s | 第 7 次 | `cached=255872`（恢复） |

**一次「改声明」的价格 = 一次冷前缀：约 24 万 token 由命中变成不命中。**

基准率（36 个有工具表记录的会话）：4 个中途变过工具数，其中**只有这一个**是 MCP 名单变化；
另 3 个是内建工具数随代码版本变（MCP 那部分恒为 26）。

### 为什么选「不动」

1. **屏障是空操作**——首次调用本来就在等每一台已声明的服务器。屏障唯一等不到的，是**还没被写出来**
   的那份声明，而它比首次调用晚 **29 秒**，且是**那个会话自己写的**。没有屏障能看见未来。
2. **「等齐再发」会把一条深思过的取舍翻过来**：一台服务器慢或坏了，不该让整个工具集陪葬
   （`cap/mcp.clj:984-987`、`:1022-1027`）。
3. **「记代」是第二份真相**：工具表已经能被逐字节指纹化，票 04 的报告就是靠这个把那次变化点名到
   「`read` 第 87→88 位」的。再维护一个计数器，只会多一个可能与字节不一致的说法。

### 为什么不做「等屏障 vs 不等」的 A/B

那个实验**测不到东西**：因果路径上根本没有「等待」这个变量——名单变化发生在首次调用之后 29 秒，
由会话自己的写触发；首调用无论等多久，那次变化都会发生。能测的是**那次事件的代价**，而它可以直接
量到（上表末三行）。
