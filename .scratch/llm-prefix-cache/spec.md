# spec: 前缀缓存的第一性 —— 工具表要逐字节稳定，稳定的一半与善变的一半分开住

**一句话**：厂商的前缀缓存按**发出去的字节**键控，而这个 harness 每一次请求都把**工具表**
（96 个工具、71,923 字节，约 16k token）摆在**消息之前**——于是工具表里**一个字节**的变化就作废
整段前缀：所有工具、system prompt、指令文件、技能目录、以及**整场对话**。而它今天确实在变：
`job_output` 的描述里钉着**一个 JVM 身份哈希**，每个进程都不一样。本特征先把这个哈希拿掉
（这是根因），再把工具表切成「稳定的一半住前面、善变的一半住后面」，最后给一条能一句话回答
「这次为什么没命中、第一个不同的字节在哪」的报告。

2026-09-22 立。起点是一条真实的低缓存率：`~/.clj-harness/logs/llm-debug.jsonl` 里那场会话
（`2f92662b-45e7-4db7-b12d-d89451a5ee1b`，5 次调用）的会话级命中率是 **78.8%**，而第一次调用是
**3072/22049 = 13.9%**。

## 问题

1. **钱花在第一枪，而第一枪打空。** 那 5 次调用的续轮命中近乎满分——22016/22049（99.85%）、
   26880/26957（99.7%）、27648/28052（98.6%）、28672/28936（99.1%）；差的 0/1/6/4 个块
   （64 token/块）是厂商侧的写入粒度，不是我们的漂移。会话级的 78.8% 全部由第 1 次调用拖下来。
2. **前缀在进程内是稳的，跨进程不是。** 逐字节验证：那 5 次的 `tools` 数组**完全相同**，
   每一次的 `messages` 数组都是上一次的**字面前缀延长**。也就是说「每次发出去的前缀不一样」
   在**同一个进程内不成立**——变的是**跨进程**（以及命名空间重载后）。
3. **根因是一个没被调用的函数。** `cap/tools.clj:969-970` 把 `jobs/job-output-default-timeout-ms`
   （`cap/jobs.clj:786-795` 的 **defn**）**没调用就拼进描述**。Clojure 函数 `str` 出来是
   `类名$名@身份哈希`，于是描述里带着 JVM 身份哈希。两场真实会话里它是：
   `harness.cap.jobs$job_output_default_timeout_ms@4d27716bms` 与 `…@20eee47cms`。
   兄弟变量 `answer-budget-bytes`（`cap/jobs.clj:555`）是普通 `def`，拼出来是 8000，是对的。
4. **这个变量还有第二个 bug，同一个根**：`cap/jobs.clj:845`
   `(deref (:ended job) (long (or timeout job-output-default-timeout-ms)) ::timeout)`——
   `wait: true` 且调用没给 `timeout` 时，`long` 拿到的是**函数对象**，本意的 120000 根本到不了。
5. **现有的测试把这个 bug 钉住了，而不是抓到它。** `test/harness/kernel/tools_test.clj:796`
   拿**同一个坏表达式**去比描述（`(str jobs/job-output-default-timeout-ms "ms")`），
   所以带着哈希也通过。
6. **表里的工具不止一族，而善变的那族夹在中间。** `specs`（`kernel/tools.clj:411-417`）是
   `(sort-by key …)`，于是 `mcp__*` 排在 `job_output` 与 `read` **之间**：一个外部服务器的名单
   增删，会把后面那批**内建**工具的位置一起挪走。而 MCP 名单确实善变——122 份会话记录里
   （35 份带 `model/start` 的 `:tools`）有 **11 种不同的表**，**6 个会话在自己会话中途换过表**
   （`d62a2cd9` 95→96 中途长出 `mcp__zvec_grep__zvec_grep_search`；`02ba8830` 名字与顺序全同而
   `job_output` 的描述变了——那就是上面这个哈希；其余几个是 job 工具族/编辑模式/playwright 名单）。
7. **没有一件工具能回答「为什么没命中」。** 这次的定位全程靠手搓脚本：读 jsonl、逐字节比
   `messages` 数组、跨 122 份记录比 `model/start` 的 `:tools`。这件事应该一条命令做完。
8. **判断依据的一半是可信的，另一半不是。** 请求侧是**原样字节**（`kernel/llm.clj:313` 序列化一次
   → `:322-324` 同一个串既落盘又上线；`infra/llm_debug.clj:151-153` 以 JSON 字符串落地，
   `tools_test`… 见 `test/harness/infra/llm_debug_test.clj:79-81`），所以**前缀分析是事实**。
   响应侧是**折叠后的重建**（`llm.clj:334` 解析 SSE → `:339-340` 落盘拼装结果），原始 SSE 一个
   字节都没留。

## 决策

1. **根因按「它本来是个值」来修。** `job-output-default-timeout-ms` 改成与 `answer-budget-bytes`
   同形的一个**值**，而不是在拼装处补一对括号。理由是那个 docstring 自己写的：「The tool's
   description interpolates it, so there is one number」——**一个数**，不是一次调用。
   改完 `tools.clj:970` 拼出 `120000ms`，`jobs.clj:845` 顺带修好（同一个根，不另开一处）。
2. **工具表切成两半，善变的一半住后面。** `specs` 不再全局 `sort-by`，而是：**稳定的一半**
   （`:source :builtin`，按名字排序）在前，**善变的一半**（其余，按名字排序）在后。
   这件事用**一个 `sorted-map-by`** 表达：比较器先比「稳不稳」，再比名字——序不是排出来的，
   是那个结构的**定义**。
   判据用已有的**来源标记**而不是名字前缀：`:source :builtin` 由 `cap/tools.clj:54` 的 `register!`
   盖，`:source :mcp` 由 `cap/mcp.clj:754` 盖。名字前缀是第二条真相源，改个命名规则就失效。
3. **这句话要说实话：MCP 挪到最后救不了对话。** 因为工具表在**消息之前**（由数据本身证明：一次
   `messages` 全新的调用命中了 3072 token，命中只可能来自 system + 工具那一头），所以 MCP 名单一变，
   **它后面的一切**（包括对话）照样冷。这个决策买到的是三样，别多算：**稳定的一半成为一段连续、
   逐字节不变的字节**；**第一处分歧永远落在 MCP 边界**，可被报告点名；**名单没变时一切照旧**。
   把这三样写进 `specs` 的 docstring，别让下一个人以为挪个位置就省下了对话。
4. **JSON 定义也要稳定，用 `sorted-map` 焊死。** 工具表落到线上是 JSON，键序是**字节的一部分**。
   今天 `tool-face`（`kernel/tools.clj:384-390`）返回一个 2 键 map、`specs` 再 `assoc :name`，
   于是键序是 `description, parameters, name`——那是**数组 map 的插入序**。这里有一个**无声的
   悬崖**：Clojure 的数组 map 到 8 个键为止保插入序，**第 9 个键一进来就整张翻成哈希序**，
   所有键都可以换位，而源码上没有任何一行说了这件事。哈希序本身是确定的（Clojure 的
   `hash` 不受进程影响），但它**不再是「键集相同 ⇒ 字节相同」的承诺**：它随键集变化而重排，
   随 Clojure 版本实现而变，而这里的代价是**一次没人察觉的冷前缀**。
   所以：**凡是我们自己为线上构造的 map，一律构造为 `sorted-map`**——序是键的纯函数，
   与插入序无关、与键数无关、与哈希实现无关。三处要落：
   - 信封两层（`{:type "function" :function {...}}`，`kernel/tools.clj:412-414`）；
   - 内建参数表与它的 `:properties`（`cap/tools.clj:60-64`）；
   - MCP 的 `:parameters`（服务器给的 `inputSchema`）：在**过桥那一刻**（`cap/mcp.clj:752`）
     做一次**深**规范化——对象递归成 `sorted-map`，**数组原样保序**（`required`/`enum`/`oneOf`
     的序是内容的一部分，不许排）。
   `:required` 两处已经是对的、不要改坏：内建 `(mapv name required)`（按声明序，
   `cap/tools.clj:62`），MCP `(mapv keyword (:required inputSchema))`（按服务器给的序，
   `cap/mcp.clj:753`）。**任何集合（set）喂进 `:required` 或 `:properties` 都是 bug**——
   集合序不是契约，它连「同一个进程里两次相同」都不保证。
5. **`sorted-map` 也顺手缩小了「加一个属性」的爆炸半径。** 哈希序下加一个键可能让**其余全部**
   重排；字典序下只有排在它后面的才挪。所以改一个工具的 schema 时，前面那段的缓存还活着。
   这不是主要理由（主要理由是那个悬崖与「纯函数」），但它是对的，别把它说成主要理由。
   **代价要说清楚**：键序从插入序翻成字典序，**发出去的字节变了一次**，于是**故意付一次冷前缀**。
   这是本特征里唯一一次主动的冷启动，写在这里免得下次有人以为是回归。
5. **一次装配不算稳，两次独立进程才算稳。** 守卫测试要能抓住**跨进程**的漂移：同进程内两次装配
   逐字节相同只是必要条件（身份哈希在同一个进程里就是同一个）。所以除了「重复装配相同」，
   还要一条**子 JVM**的用例：另起一个进程装配 `specs`，哈希与父进程相同。
   再加一条廉价的哨兵：任何工具面里不得出现 `@<6+ 位十六进制>` 这种身份哈希形状。
6. **报告是一件只读的事，独立于 harness 命名空间。** 一个脚本，吃一个 `llm-debug.jsonl`
   （以及可选的会话记录目录），打出：逐次 `prompt/cached/rate`；与上一次的**共享字节前缀长度**
   与**第一处分歧的偏移 + 上下文**；跨会话的**工具表哈希**与**第一个不同的工具/字段**。
   它**不 require harness**、不开 `harness.db`、不写 `~/.clj-harness`——它是读证据的，不是跑系统的。

## 非目标

- ~~**不改响应侧的落地形状。**~~ **已改为做掉，理由见下面「落地结果」第 5 条。** 原来记的形状是：
  `telemetry-fields`（`kernel/llm.clj:183-187`）只留 `:usage`/`:model`/`:finish-reason`，厂商对这次
  调用的**其他说法在落地前就被丢了**（包括它自己的 `prompt_cache_hit_tokens` 拼法）；`llm.clj:208`
  是**浅** `merge`，最后一个带 `"usage": null` 的 chunk 会**覆盖掉好的 usage**。当时的结论是「缓存率
  这个判断不受影响（整数过一遍 parse 不变），但『厂商为什么报 0』这类问题可能被折叠骗到且看不出来，
  要补的时候补一条 `:usage-raw`」。后来定的做法比它更彻底：**整段原始 SSE 原文都落下来**（响应侧的
  `:body`），而不是只挑承载 usage 的那一个 frame——因为「该挑哪几个 frame」本身就是要靠原文才能回答

- **不为编辑模式切换做缓存优化。** `session-configure` 换模式会换掉工具表（`cap/editing.clj:215`

   把这个代价写下来就够，不改行为。
- **不动 playwright 跨天的名单变化**（`browser_emulate_media`、`browser_webmcp_call/list`
   的出现与消失是外部 MCP 服务器版本差）。修不了，靠报告看得见。
- **不加 tokenizer。** 这个工程按**字符**量尺寸（`edge/context.clj:37-47` 的 `size-of`），
   本特征里所有 token 数字都来自**厂商自己的 `usage`**，一个字都不由我们估。
- **不追 MCP 迟到发现**（票 05）。它在本次证据里是真的（`d62a2cd9` 会话中途 95→96），
   但要读写连接的时序，排在最后做。

## 落地结果

**票 01（身份哈希）**：`job-output-default-timeout-ms` 值化。实测补充——它不是「每次都不一样」，
而是**没有契约的稳定**：35 个带工具表的会话里 19 个带着这个坑，哈希有 **10 个不同的值**
（`3d6e18b4` … `154bc3cf`）；HotSpot 默认 `hashCode` 在分配顺序相同时可重复，所以多数会话恰好一样，
而任何改动启动期分配顺序的东西都可能把它挪走。它确实在线上字节里（活体请求体逐字可见），也确实是
**4 个会话中途漂移**的原因之一。

**票 02（序与 JSON 形状）**：深规范化落在 **wire 门口**（`kernel/tools.clj` 的 `wire-json`），不是
过桥处——一处生效、能力层继续写可读的字面 map、`cap/mcp.clj:728` 那句「verbatim」**不必弱化**；
排序改成 `sorted-map-by` + 按 `:source` 排名；集合在门口**按名字拒绝**。代价是**故意改一次字节**。

**票 03（守卫）**：哨兵用例（`harness.*$`、`@[0-9a-f]{6,}`、`#<`）＋「每一层对象的键都有序」的
递归断言＋数组保序＋集合拒绝。**并且反着验过一次**：把那个常量改回「未被调用的函数」，哨兵当即在
`tools_test.clj:1002` 变红（实际值 `harness.cap.jobs$` / `@463d48b2`），等待那条用例同时抛
`ClassCastException`，恢复后全绿——**这一轮的哈希与既往前几次观测到的都不同**，所以「身份哈希不是
契约」这一点不是推理，是量到的。「逐字节相同」那条用例**守不了跨进程**，用例注释与票 03 都写明了。

**票 04（报告）**：`scripts/llm-prefix-report.mjs`，只读。它把三类漂移分开了——身份哈希（3 个会话）、
我们自己改描述文本（4 个）、MCP 工具把内建挤位（`d62a2cd9`：`read` 第 87→88 位）。写这个脚本时还
抓到我自己一个 bug：`JSON.stringify(v, Object.keys(v).sort())` 的 replacer **会在每一层生效**，
把每个工具过滤成 `{}`，于是 11 张表被说成 6 张。

**响应侧保真（原「非目标」第 1 条，后来做掉）**：`stream!` 用 `tee-lines` 把原始 SSE 帧文本落成
响应侧的 `:body`（与请求侧同名字段、同一条理由：折叠出的 `:telemetry` 是**解读**，解读失去来源就
无法核对）；`telemetry-fields` 里 `:usage`/`:model` 改用 `some?` 守卫，**`null` 不再能顶替真值**
（这个丢失最坏，因为它看起来像「这次调用什么都没报」）。报告脚本会把原文里的 `usage` 与折叠结果
对一次，不一致就点名；历史行没有 `:body`，它保持沉默。

**票 05（MCP 名单迟到）→ 结论：不动。** 完整证据与三条理由写在
[`docs/architecture/mcp.md`](../../docs/architecture/mcp.md) 的「名单什么时候定型」一节：
名单是**同步**要的（`cap/mcp.clj:1015`），首次调用本来就在等每一台**已声明**的服务器，**不存在
后台发现竞态**；唯一那次变化是会话自己写的配置（会话开始约 32 秒后写 `mcp.edn`，0.9 秒后的调用
就带上了新服务器），代价量到了——那一次命中的 token 从 `252544` 掉到 `14720`，下一次恢复到
`255872`。屏障看不见未来；「记代」是工具表指纹已经说完的事。

**关于那个 78.8% 的准确说法**：会话级的低命中**全部由第 1 次调用拖下来**（`3072/22049`），而第 1 次
只命中 3072 是因为某个字节把可命中的前缀**截断**在了 `job_output` 那里（活体 body 里它在 tools 数组
起点之后 10609 字节）。修完的正确验收要**连开两个会话**：第一个把新字节写进厂商缓存，第二个才命中。

## 追加：AI 返回的 tool call 的形状，一路到下一次请求

工具表的字节稳了，还差**消息那一半**：assistant 的 `tool_calls` 从厂商流里进来、经我们折叠与落地、
再作为下一次请求的 `messages` 发出去。同一条道理——**一个字节变了，代价不是一条消息，是整段前缀**。

**观测到的形状（五份真实请求体，`~/.clj-harness/logs/llm-debug.jsonl`）**：带调用的 assistant 消息
**10 次**全是 `role, content, reasoning_content, tool_calls` 这个键序；每个调用 `id, type, function`
**14 次**；每个 function `name, arguments` **14 次**；而 `arguments` **14 次全是字符串**——从流到请求，
**没有任何一步把它 parse 再序列化**（折叠是字符串拼接：`llm.clj:149-150`）。这是「形状稳定」最要紧的
一条：参数里的键序、空白、转义都是厂商自己写的，我们从头到尾只当它是**文本**。

**回来的是哪条路**：`replay/entries` 的 `ours?`（`:507-509`）只把 `:source` 属于
`conversation-sources`（client / injection / opening）的 `message` 行当作会话条目，因为「模型的返回与
工具的答复**已经由帧承载**」。**所以 tool call 的重建只走帧**（`TOOL_CALL_START` 按 `:parentMessageId`
挂到文本那条消息上 + `TOOL_CALL_ARGS` 拼接），模型那一行的 `message` 行在记录里、**不在会话里**。

**8 键悬崖在这条路上是真的，但踩不到消息**：实测（`clojure.data.json`）≤8 键的对象经「写→读→写」
