# 04 — composer 的数字由推的（状态条五格 + 上下文圈）

**What to build:** 状态条那五格（轮数 / 模型调用数 / 速度 / 用量 / **缓存命中**）与 model 左边那颗**上下文圈**
（占用比例与三个篮子）在服务端写下那一次调用的那一刻自己更新。客户端不再在「助手消息多一条」「run 结束」
各取一次，也没有 run 结束后隔 400ms 那一问、打开面板那一问——`components/composer-numbers.tsx` 那四个触发
与两次按需追一问整体退场，改成一个订阅。

这是 `events.mux` 的第三种帧的第二个读者（建议 `type: "stats"`），与票 02 同一个路由、同一套订阅集合。

**Blocked by:** 02 — 会话事实帧、按类型分发的路由、三处合一的订阅集合都是票 02 立的；这一票加的是**一种
新的事实**，不是一条新路。

**Status:** ready-for-agent

- [ ] 一场 run 跑完：状态条五格与圈是这一场的数，**网络上没有一条 `/stats`**（今天那条命令结束时必有一次）。
- [ ] 长调用进行中：两处**停在上一格**（那个数还不存在），恢复时不闪、不跳——「不编」这条一个字不改。
- [ ] **变了才推**：那一轮没有变化的时间段里，socket 上不发任何东西；一次长回答落几千行，
      客户端**一帧都不会因为那些行而收到**（客户端拿到的永远只是「几个值变了」这一件事）。
- [ ] 打开上下文面板**不再触发读**；圈与面板读的是同一帧的同一份（不可能出现两个瞬间的同一条日志）。
- [ ] 从没跑过的会话、日志不在的会话：两处都不画（404 是普通答案那条纪律不变）。
- [ ] 敲门铃的时机是**调用边界**（一次模型调用结束 / run 结束），不是**每一行落盘**：长会话上不许把记录
      读烂。要有一条测试钉住「一次 run 里折的次数与行数无关」。
- [ ] 没人订阅的会话：服务端不折、不建帧（与票 02 同一条「没人看就是零」）。
- [ ] 后端全量绿；`cd ui && npm test` 与 `npm run build` 全绿。

**落地时要记下来的**：断线重连拿到的是一份**当前**的数，不是增量——这条帧没有游标（与 `events.host` 同一条
理由）。以及「推的是一份已经折好的答案」：客户端仍然一个数都不自己算。
