# 剩下的读也走下行（pushed-reads）

**一句话**：这一页上「谁在跑 / 谁在等 / 花了多少」的每一处都由服务端**推**——客户端不再有钟、不再按 step
重取；而**后台作业的身份活过进程**（`j1` 不再随重启从 1 重来）。

## 背景

`events.mux`（窗口帧 + run 帧）与 `events.host`（家级 listing）落完之后，读侧还剩三处自己在问，另有**一处更根本的债**（第 4 条）：

1. **右栏任务视图**（`hooks/use-task-pane.ts`）：**全仓唯一的 `setInterval`**，1 秒一问、两条读
   （`GET /api/threads/<stem>/jobs` + `GET /api/subagents`）共用一个 tick。选轮询的理由记在
   `.scratch/right-pane-tasks/spec.md` **决策 7**：**「一条作业的结束没有能推到客户端的通道」**。
   这条前提在今天不成立了——通道有了，铃有了，缺的只是**话说出去**。
2. **composer 的数字**（`components/composer-numbers.tsx`）：挂载 / 换会话 / 助手消息多一条 / run 结束各取一次，
   外加 run 结束后隔 400ms 追一问、打开上下文面板再一问。读的是 `GET /api/threads/<stem>/stats`，
   状态条五格（含**缓存命中**）与 model 左边那颗**上下文圈**共用这一份。
3. **侧栏每一行的状态**：`:running` 已经在推（`run-started!` / `run-finished!` 敲 `events.host` 的铃），
   但「等你回应」（**parked**）**根本不在 listing 里**——`session-row` 只有 `:running` 一个进程内字段。
   于是一场在别的标签页/别的进程里 park 住的会话，在这一页的侧栏那一行**什么都不显示**。
4. **后台作业的身份只活在进程里**（顺着第 1 条查出来的，比「推不推」更根本）：id 是**进程内**计数器，
   所以新进程的第一条作业又叫 `j1`——同一场会话里两条不同的命令共用一个名字；命令与起点只活在内存
   登记表里，进程一走就没了（`job_list` 那句 `(no command kept -- a record holds what it said)` 与
   `[exit ?]` 就是这件事的两个影子）。记录文件本身活得比进程久，但「哪个文件是 `j1`、它跑的是什么」
   **没有一处持久的地方能回答**。这不是推送能修的：推一份会随重启消失的答案，只是让它消失得更快。

服务端侧其实已经备好了：会话有一条**写流**（落一行就推进登记过的实时 step），stats/context 早就改成
读会话而不是自己读盘。所以难的不是怎么算，是**什么时候敲铃**与**谁在听**。

## 决策

1. **推的载体沿用两条 socket，不新开第三条。** 右栏与 composer 都是**按会话**的事实 ⇒ `events.mux`；
   侧栏是**家级**事实 ⇒ `events.host`。ADR 0004 决策 1：下行按**类别**分。
2. **`events.mux` 的帧从两种变三种**：窗口帧（`window|append|page|tail|end`）、run 帧（AG-UI），
   以及**会话事实帧**。名字沿用窗口帧那套（小写字面，`type` 字段）；建议 `tasks` 与 `stats`。
   两件事跟着改：
   - 客户端现在按「**是不是窗口帧**」二分（是 ⇒ 窗口跟随者，否 ⇒ run 订阅者），第三类会掉进 run 订阅里
     被丢掉 ⇒ 路由要**按类型分发**；
   - 订阅集合现在从**两处**拼（`subscriptions` 窗口 + `runSubscriptions` run）⇒ 变**三处**，
     否则握手 URL 不会为它声明那场会话，帧推不到。
3. **客户端看到的语义是「变了才推」，这一条不在本次商量范围内。** 一帧没有新闻就不发——既有的窗口推送
   已经是这么做的（push 先比对再决定发不发，静置的会话上 socket 是安静的），本批原样沿用：客户端
   **不关心记录里一帧一帧的东西**，只关心它画的那几个值动不动。
   要解决的是**服务端怎么便宜地知道「变了」**：会话那道缝今天是 `{:kind :entries}` / `{:kind :gone}`，
   而「落了一行」与「一次模型调用结束了」不是一件事——数字只在**调用边界**才变。若把推送挂在写流的
   每一行上，就得**每一行折一次整份统计、再比出「没变」**：客户端一条都不多发（这是对的），服务端
   却把记录读烂（一次长回答里几千行 ⇒ 几千遍）。所以门铃要说得出「哪一类事实变了」——**这不是为了
   多发帧，恰恰是为了不发没新闻的帧，而且不为「发现没新闻」付整份重算的代价**。
4. **任务视图那两条读合成一帧。** 作业与子代理是**同一个问题**（这个会话现在有什么在跑）的两个答案，
   今天靠「一个 tick、两条读共用一个 `AbortController`」保证它们说的是同一刻；推之后由**一帧**保证。
5. **「跑了多久」是本地的钟，不是请求。** 今天那一行的秒数靠轮询带来的每秒重渲染在长；钟删掉之后要有一个
   **只喂渲染、不发请求**的本地 tick（`task-pane-jobs.tsx` 的 `now` 参数早就是这个形状了，所以这是接线不是新概念）。
6. **侧栏每行的状态进 listing，而且只对服务端**自己持有的**会话说实话。** parked 住在会话的内存里；
   对别的进程跑的会话，与今天的 `running` 一样**照旧说不知道**——为它去读日志尾巴是 listing 明令放弃的
   每行一次盘读（`session-row` 的注释写了这件事）。宁可不知道，不撒谎。
7. **没人看的订阅是零。** 订阅随栏（或随页面）挂上、随它断掉；服务端不为没人订阅的会话折数字、建帧。
   这与「关掉镜子就挂断跟随通道」是同一条纪律，也是 ADR 0004 决策 6（不许全量广播）在这一层的说法。
8. **两个兜底随推送退场**：`lib/sidebar-refetch.ts` 那套「最多 5 次、400ms 间隔」的重问是**主机推送之前**
   写的，推送上线之后它是重复劳动 ⇒ 删。`lib/delegations.ts` 那套有界的重试**这次不动**：它不是轮询，
   是「卡片画出来了、那一行还没写下来」那几百毫秒的等，与推送无关。
9. **作业的身份与状态都读库；记录只做两件事——内容，和异常之后那一次补档。** 一行 = id、命令、起点、
   记录路径、**状态**。这是本仓自己那条分层（会被改写的事实进库，append-only 的进 jsonl）：一个作业的
   状态就是「会被改写一次」的那种事实，而 `session_claims` 已经开了同层表的先例。
   - 读的人（那一栏、`job_output`、`job_list`、`job_kill`）**只看库**，正常情况下一个记录文件都不打开。
     这顺带买掉一个今天的代价：列表的每一行都要把那条作业的**整份记录 `slurp` 一遍**才知道它结束了没有
     （`status-of` → `record-lines` 就是 `slurp`），而那一栏**每秒列一次**。
   - 正常结束（跑完 / 人按 ■ / 模型停 / **干净关进程**）在写结局的那一句同时落库。
   - **记录的末行照旧写**（`[exit N]` / `[stopped]`）：给「用 `read` / `bash` 直接翻这份文件」的人看，
     一份自我完备的记录不该在最后一句上撒谎。但它**不再是读的权威**——权威是库。
   - **异常退出**（进程被杀、崩溃、断电）之后，库里的行还写着「在跑」而没有进程在跑它：**启动时补档一次**，
     对每一行还写着「在跑」的作业**读一次它那份记录的末行**——有结局就照抄进库，没有就记成
     「那次跑的东西没了，没留下末行」（今天 `[exit ?]` 那个词）。补完，库里不再有「在跑」的孤儿。
   - **代价正面接受：结局写两处**（记录末行 + 库），不一致时以库为准。记录仍会降级（那套既有的话照旧说），
     库写失败是本地库的失败，不是这一票新造的。
   - 重启之后**能读不能停**：记录还在，`job_output` 照旧读得出来；进程不在了 ⇒ 没有可停的东西。

10. **记录一律流式读，`slurp` 不许碰记录。** 会话与轨迹早就是一行一行读的（`replay/read-records` 走
    `io/reader` + `line-seq`，它自己的注释写着「以前是 slurp 整份再 split-lines」）；这一批把剩下的清完。
    2026-09-25 扫过一遍全局 `slurp`，碰记录的只剩两处、五个调用点：

    | 谁在读 | 读的是什么 | 今天的频率 | 归谁 |
    |---|---|---|---|
    | `cap.jobs/record-lines`（经 `listing` → `status-of`，**每行一次**） | 作业记录 | **热**：那一栏开着时每秒列一次 ⇒ 每秒把每条记录的整份读一遍，只为读最后一行 | 票 01 |
    | 同一个（经 `ending-of` → `records-for` → 模型 `job_list`） | 这个会话**产生过的每一条**作业记录 | 模型每次 `job_list` | 票 01 |
    | 同一个（`output` → 模型 `job_output`） | 作业记录，而它最后**只发一个窗口** | 模型每次读它 | 票 01 |
    | `edge.http/ts-range`（×**2**：目标文件 + 残留段） | **会话**记录 | 每次绑定（carry-back）一次 | 票 05（**删掉**——绑定不可变之后这条路不存在） |
    | `edge.http` 的 carry-back 正文搬运 | 同一个残留段 | 同上，而且读进来还要 `spit` 出去 | 票 05（同上） |
    **这次扫描之后，`slurp` 就不再碰任何记录**——最后两处不是改成流式，而是随不变量一起消失。

    **不属于记录、可以照旧整份读的**：`prompt.md`、配置文件与 EDN（`.env` / `harness.edn` / `config.edn` /
    hooks / MCP）、技能正文、**模型自己点名要读的文件**（`read` / `edit` / hashline 的目标）、HTTP 请求体与
    响应体、子进程的 stdout。这条清单要随票 06 落进 `docs/architecture/edge.md`。

11. **绑定只有一次：会话开口之后不可变。** 界面上本来就是这条（选目录那颗控件是 `{!started && …}`，会话一有消息就藏起来），
    这一批把它变成**服务端的不变量**：第二次绑到别的目录被拒，**已经有行的会话**（说过话的任务）也绑不上项目。
    代价明说：**一场说了话的任务就永远无家**——这正是界面已经给人的答案。买到的是一整条补路可以删：
    `move-log!` 没有东西可搬，「一场对话两个文件」这个状态不再可能，`carry-back!` / `ts-range` 随之退场。

### 状态住在哪儿，谁敲铃（说准，免得下一个人猜）

**推送由改状态的那一句敲铃，不由定时器、也不由「拼一帧来比对」。** 这是本仓已经立好的规矩
（`harness.edge.host` 的注释就是这么写的：IT IS RUNG FROM THE MUTATORS, NOT FROM A TIMER）。窗口那条
推送今天会比对，是因为它答的是「从你的游标往后有什么」——那个答案**可以是空的**；这批事实不是那个
形状：**状态在哪儿、谁改它，都是已知的**，所以没有要比的东西。

| 要看的东西 | 状态住哪儿 | 谁改它（= 敲铃处） |
|---|---|---|
| 左栏每行「在跑 / 等你回应」 | **进程内存**：run 集合 + 会话条目上的 `:state`。**不在 SQLite**——日志文件答不了「现在跑没跑」（一段没有终帧的日志，既可能正跑着，也可能是进程被杀了） | run 起来 / run 结束 / park 住的那一处（今天已经在敲 `events.host` 的铃） |
| 右栏的**后台作业** | **库**：身份（id / 命令 / 起点 / 记录路径）**与状态**都在库里；记录文件只是内容 + 一句自我完备的末行（结果写两处，以库为准） | `start!` / 结束的那一句 / 干净关进程；异常之后由启动时**一次**补档读记录的末行填上 |
| 右栏的**子代理** | **两半**：`sessions` 里有它的行（重启还在，「这个家委派过谁」由库答）+ 内存里「还在跑」。重启之后一律 false，照实说 | 委派那一行写下时 / 那次委派结束的那一处 |
| composer 的**数字** | **记录折出来的实时折**（每来一行推进一格），不额外存一份 | 一次模型调用结束的那一行（`model/end`）落下时 / run 结束 |

「等你回应」值得单独说一句：它**不在 SQLite**，也不该在——一次 park 就是一次 run 结束，所以它与
「在跑」由**同一条铃**带出来，缺的只是把这个字段读进 listing。
## 代价

- **订阅集合多一类**：`wantedThreads()` 要从三处拼，漏一处就是「帧推不到」这种不报错的坏。
- **服务端的折要挑时机**：数字这一帧的敲铃点必须钉在调用边界上，否则这条推送本身就是新的负载。
- **侧栏那一个字段有前提**：`parked` 只在服务端持有该会话时是真话。别的进程跑的那一场，侧栏照旧说不知道
  ——这与 `running` 今天的能力边界是同一条线，不是新欠的债。
- **推的帧没有游标**（与 `events.host` 一样）：断线重连拿到的是一份**当前**的两段/一份**当前**的数，
  不是增量。这是对的——它们问的都是「现在是什么样」，不是「我错过了哪些条目」。
- **结局写两处**（记录末行 + 库），以库为准：这是决策 9 明码标价的代价，不是漏掉的重复。
- **库多了一张有寿命的表**：作业行要跟着记录的回收一起走（库不是坟场），而且它**只对同一个家起过的作业**
  说了算——别家/更早的旧记录文件照旧只有 `job_list` 列得出来，那一行照旧没有命令（今天的诚实不变）。

## 非目标

- 不改窗口与游标那一套代数，不改 run 帧的形状，不改 `POST /api/*`（上行仍是 HTTP）。
- 不改「数字不编」：客户端仍然不自己数 token、不估算缓存命中；**没有数就是不画**。
- 不新增任何可见控件，不改右栏的开关与两态、不改镜像那条跟随通道。
- 不动 `lib/delegations.ts` 的有界重试（见决策 8）。
- 不给 `c*` 那类**前台溢出的记录**建行：它们是 `bash` 输出的落点，后面没有作业（没有进程可停、没有 id 可
  寻址）；`job_list` 照旧按文件名里的进程戳分行列出它们。
- **不改记录文件里那一行**（末行 `[exit N]` / `[stopped]` 照旧写）：一份自我完备的记录不欠这一句；改的只是
  **读**它的人不再以它为准。

## 验收主线

1. 栏开着看一整场 run：网络上**没有一条重复的 `/jobs` 或 `/api/subagents`**；作业起/停、子代理开跑/跑完，
   行自己变；运行中那一行的秒数照旧在长。
2. 一场 run 跑完：状态条五格与上下文圈是这一场的数，**没有一次 `/stats` 请求**；长调用进行中两处停在上一格。
3. 新会话发第一句：侧栏那一行**自己出现**、带标题，**没有 `/api/projects` 重问**。
4. 另一扇窗里那场会话 park 住 ⇒ 这一页侧栏那一行显示「等你回应」（服务端持有它时）。
5. 栏关掉、页面切走：**一条请求都没有**，服务端那边的订阅归零。
6. 重启一次 harness：那场会话的后台作业还在，`j1` 还是同一条命令，起点与「跑了多久」不是从零重来；
   新起的一条不会又叫 `j1`。

## 反转的旧决策（落地时要在那几处留下日期注）

- **`.scratch/right-pane-tasks/spec.md` 决策 7**（「轮询只在任务视图开着时跑」）：作废——不是「轮询挪了个地方」，
  是**没有轮询了**。那条决策的理由（作业的结束没有推的通道）已经不成立。
- **`docs/architecture/client.md`** 里两节：「状态条那五格……**它什么时候问**」（四个触发 + 两次按需追一问）
  与「任务视图两段，各读什么 / **一个 tick**」。改的是**怎么来的**，不是**画什么**。
- **`.scratch/right-pane-tasks/spec.md` 的非目标**（「不进库、不进 jsonl：作业与 runs 都是进程内的事实，刷新就空
  ——那是老实话，不是这个特性的债」）：**翻转**，理由在决策 9。子代理那半本来就在库里（`sessions` 的行），
  当时那句话把两半当成了一回事。
- **`cap.project/bind!` 的「rebinding to another directory is just binding again —— the last bind wins」**，
  连同 `(bind! id nil)` 那段「释放会话，**通常因为它马上要绑到别处**」：**翻转**，理由在决策 11。
  `(bind! id nil)` 本身（无家会话的释放）还在，只是它不再有「为了绑到别处而释放」这个用途。
