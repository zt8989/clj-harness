# 03 — 收口：文档、两套报数、落地记录

**What to build:** 把「一次状态读几个进程」写进该写的地方，留下改前 / 改后两套全量报数。这一票交的
是**话说得对**与**数是真的**。

**Blocked by:** 01 — `git/state` 一条命令答三个问题；02 — 夹具建一次、拷多次

**Status:** ready-for-agent

## 要落地的判断

1. **`docs/architecture.md` 的 `cap.git` 那一行（第 86 行）补一句进程数。** 那一行现在写的是
   「会话目录作为 git 工作树：读当前分支、列本地分支、切分支……」，把「读一次状态要几个进程」
   写进去是有用的 —— 因为这正是它的成本所在（一次状态读 4 → 2、一次切换 9 → 5），而那一行是
   读者判断「这个端点贵不贵」时唯一会看的地方。**别为它新开一节**：文档是入口不是手册。
2. **`state` / `switch!` 的 docstring 不再点名被换掉的命令**（票 01 已经改过一轮，这一票复查：
   句子里还有没有 `--porcelain`（不带 `=v2`）或 `--abbrev-ref` 这类已经不作数的说法）。
3. **两套全量报数是判据，不是装饰**：改前（`main` @ `19e9d9f`）与改后各一次，**比失败名单**，
   不只比绿不绿 —— 本仓纪律（`.scratch/tool-parity/spec.md` 记过这条的来历）。测试数与断言数的
   变化要能逐条解释（票 01 与票 02 各新增了哪些用例）。
4. **报数之外还要报进程数**：本特征的全部意义在进程数上，所以 `git-test` 的 spawn 计数
   （**100 → ？**）要作为一个数报出来，与时间一起。只报时间的话，别人的机器上就看不出这一票
   干了什么。
5. **`git-test` 的时间预期**：按本机 1.08s/spawn 计，100 → 约 42 次 ⇒ 107.7s → **约 45s**。
   这个数是**预期不是承诺**，实测出来差得多就说差多少（本仓的报数纪律：数字要说清是哪台机器、
   什么时候量的）。
6. **落地记录写进 `spec.md` 的「状态」一节**，票面按本仓约定**删除**（记录只活在 `git log` 与
   spec 里）。
7. **非目标那两条不许被顺手做掉**：profile 三个开关（另一条线，6652097）与让 git 走 cmd
   （`.scratch/bash-shell-choice`）。文档这一票只写本票做过的事。
