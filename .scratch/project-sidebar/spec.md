# spec: 项目侧边栏（会话按项目目录分组，元数据进 sqlite）

把页面从「一页聊天 + 顶部一条会话横排」改成**侧边栏 + 聊天**：侧边栏顶部钉住「新建任务」、底部钉住
「设置」、中间整块滚动，滚动区里按**项目目录**分组列会话。同时把「项目」从一个可有可无的内存绑定
升格为一等实体，会话日志按项目分目录落盘，界面元数据与 hashline 的锚点存储共用一个 sqlite。

参照的交互是 assistant-ui 官方 Claude demo 的侧边栏；抄组件走官方那条路（`shadcn add
@assistant-ui/thread-list`），项目分组与三段位布局是我们自己的。

## 背景与定位

今天的三件事与目标都对不上：

1. **会话没地方归。** `harness.project/bindings` 是一个内存 atom（thread-id → 目录），重启即失；绑定是
   可选动作，绝大多数会话没有绑定。assistant-ui 06 落地的会话面板因此是一条**平铺**的横排，一页聊天上面
   挂一条列表——它答的是「日志目录里有哪些文件」，不是「我在哪个项目里、这个项目下有哪些会话」。
2. **日志平铺在一个目录。** `~/.clj-harness/logs/*.jsonl`，文件名是 thread id，与项目没有关系。
3. **没有元数据层。** 归档、项目归属这类都是"关于会话的事实"，今天无处安放——jsonl 是 append-only
   的记录，不是可改状态。

界面侧的前置已经到位：assistant-ui 03–06 把页面接到了新运行时，`Thread` 的元素、工具卡、审批门、会话
面板都在。**本特征取代 assistant-ui 07**（项目目录面板），理由见决策 7。

## 决策

1. **项目是一等实体，界面不再产生未绑定会话。** 一个项目 = 一个绝对目录；一个会话属于恰好一个项目。
   点「新建任务」时已经选中某个项目就直接在该项目下开会话；一个项目都没有时说的是「先添加一个项目」，
   而不是开一个游离的会话。

   **但服务端容忍未绑定**：`POST /`（AG-UI 跑）对一个库里没有的 thread id 仍然接受，该会话的日志落在
   `projects/.unbound/`，侧边栏不列这一组。理由是这条边界上不引入"先建会话"的协议前置——否则既有 4 组
   e2e 用例与整套后端断言都要先学会建会话，而它们要验的都不是这件事。工具侧「未绑定 = 恒等」的回归保证
   同样一字不改。

   目录名是 `.unbound` 而不是初稿写的 `_unbound`：**留白由构造保住，不由约定保住**。workspace 名是项目
   绝对路径 `sanitize` 的结果，非 `[A-Za-z0-9._-]` 一律换成下划线，而绝对路径必然以 `/`（或 Windows 的
   盘符）开头——所以项目名永远不会以点开头。反过来写字面 `_unbound` 会和 `/unbound` 这个目录撞名，
   两份互不相干的日志混进同一个目录，正是这棵树要消掉的那种混乱。

2. **一个 sqlite，位置 `~/.clj-harness/harness.db`。** 它装两类东西：界面元数据（项目、会话归属、归档），
   以及 hashline 的锚点快照 / 撤销记录 / 会话归属。**推翻了 hashline spec 的两条**：`与参考实现的有意偏离`
   表第一行（"本仓不引入数据库"）与非目标里的"不做跨进程锁"。

   推翻的理由不是"数据库更好"，是那两条建立在**一个 home 只有一个使用者**的假设上，而 sqlite 在这里的
   真正收益不是并发查询，是**一次写入多个事实**。归档一个会话要同时改 `sessions` 的一行并让列表读到的
   归属一致；项目解绑要同时改项目行与会话行；hashline 的一笔编辑要在同一个临界区里推进锚点归属与撤销记录
   ——这些在"每份状态一个文件 + 原子写"下要么各写各的（可能只成功一半），要么手搓一个跨文件的两阶段提交。
   顺带拿到的是跨进程安全：将来 `replay` / `evals` 这类离线工具与服务器同时开着时，"两个写者"从
   *静默损坏* 变成 *要么串行要么报锁*。

   位置为什么是 home 根而不是 `hashline/` 下：它不再是某个特征的私有存储，是这个 home 的元数据层；
   让第二个使用者去别人的目录里写库，是把一个共享设施命名成了一个特征的附属物。

   **库与文件的边界：库装状态，文件装记录。** 会变的东西（项目、会话归属、归档、锚点、撤销）进库；
   只追加、不修改的东西（会话 jsonl、config.edn、providers.edn、harness.edn）留在文件里。这道线是
   "频繁变更"这个口径的准确形式——**判别标准不是"改得勤"，是"能不能被改写"**：归档标记一年改一次也是
   状态，它必须进库因为没有别的地方放；一条消息永远不会被改写，所以它永远不进库，改得多勤都一样。
   三个推论，每一条都要在票面与验收里看得见：

   - **库不是日志索引。** 会话 jsonl 里的任何内容都不进库——没有消息表、没有全文索引、没有"会话摘要"
     这类镜像。要看内容，读那个文件；库回答的是"这个会话是谁的、归档没有"。
   - **既有的 `~/.clj-harness/logs/*.jsonl` 不导入。** 库从空开始，老会话不会因为库建好了就出现在侧边栏
     里。这是"不导入"的字面后果，也是它该有的样子：一个会话没有项目归属、库里没有它的行，界面就没有
     理由显示它。**这不是数据丢失**——文件还在原地，只是不再被这份界面认领（下面决策 3 说不迁移，
     理由同一条）。
   - **harness 自己的配置仍是文件。** `config.edn` / `providers.edn` / `harness.edn` 继续每次调用现读、
     改配置不需要重启，`harness.home` 与 `harness.project` 的既有纪律一字不动；hashline 票 01 把
     `:editing` 放在 `harness.edn`（而不是 `config.edn`）这个选择同样有效。库里装的是**界面那侧的**状态：
     项目、会话归属、归档，以及界面自己的偏好——按"频繁变更的界面状态"这个口径，库是这类东西**可以**住
     的地方，但本特征只往它里面放下面几张票真的需要的那几样，不为了"顺便持久化"把每一个 UI 开关都塞进去

3. **日志按项目分目录：`~/.clj-harness/projects/<workspace>/<threadId>.jsonl`。**
   `<workspace>` 是**项目绝对路径的 `sanitize` 结果**（沿用 `harness.home/sanitize` 的同一套规则），
   不是末段文件夹名——末段会撞（两个不同父目录下的 `foo`），全路径不会，而且可以肉眼倒推回目录。
   **显示名才是末段**，那是界面的事。

   旧 `~/.clj-harness/logs/` 退役：不再被读取（`logs-dir` 从 home 里消失），**不迁移、不导入、不出现在
   任何列表里**——本仓没有需要保护的生产数据，多一条迁移路径就多一处要测的代码和一处会腐烂的分支。
   代价说清楚：**今天已经存在的会话，在新界面上一个都不会出现**，直到它们在某个项目下被重新开出来。
   文件一个字节不动，重建它们的能力也还在（`harness.replay` 不认识项目，它只吃目录与 thread id——
   把文件挪进 `projects/<workspace>/` 就能被那份界面看见，但这件事要人来做，工具不做）。

4. **移除项目 = 解绑，不删日志。** 项目从侧边栏消失，`projects/<workspace>/` 下的 jsonl 原样留着；
   重新添加同一目录，会话与它们的归档状态都回来。**删除（连同日志）本特征不做**：这一步不可逆，而它
   省下的磁盘在今天没有任何意义。

5. **归档是行的状态，不是删除。** 归档的会话从项目下移出，落进该项目底部默认折叠的「已归档」分组；
   取消归档放回去。jsonl 一个字节不动。

6. **「设置」这一版只读。** 显示生效的 provider / model / reasoning-effort 与**这个选择来自哪一级**、
   配置家目录的绝对路径（以及它是不是 `CLJ_HARNESS_HOME` 给的）、home 里有哪几份文件。
   **api-key 永不出值**——只有"有/没有"与它来自 `.env` 还是环境变量。写回配置是另一件事。

7. **本特征取代 assistant-ui 07。** 那份票要的是"聊天上方一条项目目录面板"，位置与视觉都对位今天；
   侧边栏里项目在**旁边**而不是上方，绑定发生在**建会话时**而不是会话跑起来之后。留着它会造成一张
   落地即被替换的票，所以 07 置为 `wontfix` 并在票面写明去向；它依赖的三条路由（`GET/POST /api/project`、
   `POST /api/project/pick`）**已经在 `harness.http` 里实现**，本特征直接复用，票里的行为契约
   （三种填法、取消不是错误、请求中禁用）搬进本特征 05。assistant-ui 08 的阻塞边随之去掉 07。

8. **分票顺序：01 → 02 → 03 → 04 → 扇出 05–08 → 09 收口。** 01 是唯一的横切（一个存储层，没有使用者），
   它按 to-tickets 的口径属于**预付**：先把它立起来，后面每一票都只是在它上面加一张表。02 让"项目"在
   服务端成为实体而不动界面，03 搬日志，04 才动界面——界面上线时它脚下已经踩实了。

## 非目标

- **不做会话搜索。** Claude demo 的侧边栏带一个搜索框，本仓的会话数还没到需要它的量级。
- **不做重命名 / 标题生成。** 侧边栏显示的是会话的开始时间与体积；用模型生成标题是另一个特征。
- **不做多窗口 / 多标签同步。** 侧边栏是快照：切换、归档、移除、当前会话变化时重取。
- **不迁移、不导入 `~/.clj-harness/logs/`**，也不在文档里承诺它还能被读。既有的会话文件不会因为库建好
  了就出现在侧边栏里——这是"库装状态、文件装记录"的直接后果，见决策 2。
- **库不是日志索引**：不做消息表、不做全文搜索、不把 jsonl 的内容镜像进库。
- **harness 自己的配置不搬进库**：`config.edn` / `providers.edn` / `harness.edn` 仍是文件、仍现读。
- **不做项目的删除**（连同日志），也不做把会话在项目之间移动。
- **不做既有日志的搬迁工具**：从 `logs/` 挪进 `projects/<workspace>/` 是人手动能做的事，本特征不提供
  自动化，因为那就等于把"不迁移"改成了"悄悄迁移"。
- 不改 AG-UI 帧、不改 CORS 放行名单、不改 5173 契约。
- 不做配置的写回（「设置」只读），不做 api-key 的任何形式的展示。
- 不为侧边栏引第二套样式体系：Tailwind + 抄来的组件，与 assistant-ui 那条纪律一致。

## 验收主线

1. 三关全绿：`clojure -M:test`（含被本特征改写的 hashline 票里那批断言在各自落地时仍绿）、
   `cd ui && npm run build`（`tsc --noEmit` 0 error + Vite 成功）、`cd ui && npm test`。
2. **侧边栏三段位**：新建任务与设置钉住，项目区是唯一的滚动容器；窗口拉高拉矮都不出现整页滚动。
3. **新建任务必须先选项目**：有项目时落在当前项目下；没有项目时说的是"先添加一个项目"并给出添加入口。
4. **绑定持久**：重启进程（清内存、只留磁盘）后，项目、会话归属、归档状态都还在。
5. **归档**：会话落进「已归档」分组且 jsonl 字节数与 mtime 不变。
6. **移除项目**：磁盘上 `projects/<workspace>/` 逐字节不变；重新添加同一目录，会话都回来。
7. **日志落位**：`~/.clj-harness/projects/<workspace>/<threadId>.jsonl`；`~/.clj-harness/logs/` 下的旧文件
   **既不出现在任何列表里，也没有进库**（用例直接对库查一遍，断言没有它们的行）。
8. **库装状态、文件装记录**：库里的表只有状态型的（项目、会话归属、归档、hashline 的三张）；没有一张表
   装消息、帧或日志行。
9. **配置仍是文件**：改 `config.edn` 的 model 或 `harness.edn` 的 `:editing`，不重启、不碰库，「设置」
   那一版显示的是**新值**。
10. **「设置」不泄密**：响应体里搜不到 api-key 的任何形式。
11. 真 Chromium 走一遍全主线，截图留档。

### 01 落地记录

`src/harness/db.clj`（新）、`test/harness/db_test.clj`（新）、`harness.home/db-file`、`deps.edn` 加
`org.xerial/sqlite-jdbc 3.53.4.0`、`test/harness/test_runner.clj` 的隔离复查。**全仓没有第二个使用者**
——没有路由、没有界面、不碰日志、不读任何配置文件。

- **库是 0 张表、`user_version` 0**。本票只立存储层与迁移链：一个没有使用者的库没有表可装，先编出来的
  schema 是猜，回头还得迁移掉。第一张表跟第一张读它的票一起来（02）。
- **身份在数据库头的字节里**：`application_id = 0x6861726E`（`harn`）。判断"这是不是本仓的库"完全靠读
  文件头 100 字节，**不打开它**——打开一个别人的 sqlite 会在他旁边留下 `-wal`/`-shm`，而"拒绝时原文件
  一个字节不动"正是本票的验收项。
- **身份先写，WAL 后开**。WAL 会在主库里持有更新的页，只读文件头可能读到旧版本（迁移会自愈），但**绝不
  能让身份被遮住**——那会让库认不出自己。所以 `application_id` 在默认回滚日志模式下写入，之后才切 WAL。
- **损坏的处置分两级，靠"能不能读出主人"划线**：头 100 字节之内读不出应用 id 的一律**点名拒绝**
  （`reason :unidentifiable`）——把主人不明的文件挪走，与把他的文件覆盖一样是毁它；能读出主人但不是我们
  的（`:foreign`）同样拒绝；确认是我们的才隔离重建（改名 `.corrupt-<ts>`），并把这件事**说出来**
  （stderr 一行 + `harness.db/recoveries`），不静默当成空库。
- **`migrate!` 逐级迁移**，每步与它的版本号同一个事务提交，失败即整体回退且连接关闭；比目标版本新的库
  点名拒绝（`reason :too-new`）。`schema-version` 是只读的那一半：不开连接、不建文件，没有库时答 `nil`，
  损坏时拒绝（与 08 的"改配置立刻可见"同一条线：有别的权威来源的东西，库都不存，也就都不写）。
- **`with-transaction` 是这一切存在的理由**：一笔事务里几个事实要么都成要么都不成。连接用
  `BEGIN IMMEDIATE` + 5 秒 busy timeout，`busy_timeout` 让争用的写**排队**而不是失败（实测 4 线程 ×
  25 轮读改写，计数恰好 100，零失败）。
- 验收：**247 tests / 1221 assertions 全绿**（改动前 232 / 1128，既有断言一条未改）；真 Chromium 无关
  （本票无界面）。`npm test` 的 UI 套件与改动前状态相同（11 条里 1 条 `approval` 失败，**改动前后逐字
  相同，不是本票引入的**）。

### 02 之后的两条纪律，后来者要接住

- **`harness.db` 的路径只从 `harness.home/db-file` 来**，没有第二份优先级拷贝。测试运行器就是在
  `isolate!` 搬走 root **之前**取一次这个 File 并一直拿着——之后再问一次会拿到临时 home 的库，拿临时库
  和它自己比会永远通过，而真实的 home 正被写着。
- **隔离复查比的是 `[bytes mtime]` 而不是 `exists?`**。开发者一旦有了库（正常工作状态就是这样），
  `exists?` 前后都为真、什么都发现不了；而字节数或 mtime 一动就能抓到。实测过两次：库不存在时被创建，
  与库存在时被写入，两次都以非零退出码报 `ISOLATION FAILURE`。

### 02 落地记录

`harness.db` 的迁移链加了第 1 级（`projects` / `sessions` 两张表），`harness.project` 的状态从内存 atom
换成库里的行。**对外契约逐字未变**：成功返回绝对路径、`dir` 为 nil 解绑、目录不存在/不是目录各自是原来
那句点名错误；未绑定仍然是 nil、仍然不是错误、工具侧的恒等行为一字不改。既有的 project / tools /
approval / http / hooks 断言**一条未改**（project_test 只动了 ns docstring 与 import）。

- **两张表，两个问题。** 目录的**身份**在 `projects.canonical_path`——符号链接、`..`、不同写法塌成同一个
  形态，所以一个目录绝不会变成两个项目；会话的**拼写**在 `sessions.path`——`bind!` 返回它、`binding-for`
  答复它、shell 在其中运行，而这三件事都是关于**这个会话**的绑定，不该因为别的会话用另一种写法绑了同一个
  目录而变化。身份共享、拼写不共享，一个列各管一头，两句话就都是真的。
- **未绑定是一个状态，不是两个。** `project_id` 与 `path` 一起为 NULL 或一起不为：CHECK 拒绝半绑定的行，
  `BEFORE DELETE` 触发器在一个语句里把两列清掉。**触发器必须是 BEFORE DELETE**——外键的
  `ON DELETE SET NULL` 只清 `project_id`，那正好是 CHECK 要拒的半绑定状态，级联会失败、删除跟着失败；
  先清干净两列，级联就无事可做。
- **`bind!` 的一元形式保留但点名拒绝**（`:reason :no-session-slot`）：它原先往"无会话槽"里写绑定，而
  `sessions.id` 是 NOT NULL，那样一行这个 schema 装不下。删掉签名会把调用方的错误变成别处的 arity 报错，
  留着它在这里说清缺哪个参数为什么。
- **绑定真的跨进程活下来了**，而且这条是用**真进程**验的：测试 spawn 一个全新 JVM，只给它
  `CLJ_HARNESS_HOME`，让它自己去问 `binding-for`。目录通过**环境变量**传递、绝不拼进 argv 字符串——
  deps.edn 明写本机默认字符集是 GBK，任何字节跨进程边界都要显式 UTF-8。
- **一条测试改了对象**：`a-binding-outlives-the-process-that-made-it` 的第二段从"改 `projects.path` 再看"
  改成从**外部连接**改 `sessions.path`。理由是它要证的从来是"没有内存副本"，而现在的 `binding-for`
  只读会话自己那一行——原先那条断言在新形状下会通过得毫无意义。
- **`bind-params!` 对未知类型点名失败**，不再 `(str v)` 兜底：关键字会存成 `":editing"`、Double 会存成
  `"1.5"`，两行读回来都像模像样。schema 没有的列就不该有值。
- **列清单进了元断言**（`sessions-hold-no-conversation-content`）：表级的元断言挡得住新增一张表，挡不住
  给 `sessions` 加一个 `title` 列——而标题就是会话内容，是这份存储不能持有的第二个真相。列清单与表清单
  一样是**精确列举**，加列的人得写下为什么它是状态而不是记录。

验收：**262 tests / 1328 assertions 全绿**；跑完真实的 `~/.clj-harness` 里没有 `harness.db*`。

### 03 落地记录

日志真的搬进了 `projects/<workspace>/`。`harness.home` 多了 `projects-dir`（只管树根）、`log-file` /
`log-path` 改成 `[dir thread-id]`（目录是调用方的），**`logs-dir` 消失**；`harness.replay` 的
`read-lines` / `rebuild` / `history` / `resume!` 吃 `File`，`threads` 走整棵树；`harness.http` 的
`log-dir-for` 是 home 与 project 唯一的交点；`dev/harness/evals.clj` 的 `evals` 吃 `File`。

- **两条路径、两个命名空间、一个方向。** 树根与"id→文件名"的规则住在 `harness.home`；"这个会话属于哪个
  项目"要问库，所以那个交点住在 `harness.http`（`log-dir-for`）并要求 home，**绝不反过来**。写盘的
  `log!` 问它一次，读侧的列表与查找**不问**——它们走文件系统：一个被手工挪过的日志仍然是日志。
- **一度写过一个 `harness.logs`，然后删掉了。** 它把路径规则和项目查询放在一起，看起来内聚，实则让
  home 的知识有了第二个家，而且它自己不拥有任何状态——一个中间人。最终形态把路径规则留在 home、把查询
  留在 http，两者在 http 的 `log-dir-for` 里相遇。
- **workspace 用项目的 CANONICAL 路径命名**（`project/identity-for`），不是这次绑定用的拼写：同一个项目
  无论被怎么拼写绑定，所有会话落在同一个目录里。`binding-for`（答复本次拼写）与 `identity-for`（共享
  身份）因此是两个函数，各有一个非要它不可的调用方。
- **未绑定的 workspace 是 `.unbound`，留白由构造保住**（见决策 1 的修订）。
- **`move-log!`：重绑把日志一起搬走。** 一个会话是一份文件——重建、列表、eval 读取器全都从**单个文件**
  重建一段对话，所以绑定移动而文件留下会把一段会话劈成两半，三个读取器同时读不了。于是绑定成功后搬文件，
  **审计行最后写**：这样它落在刚搬进的那个 workspace，整条时间线在一份文件里。
- **搬不动就点名拒绝，而且拒绝时不写审计行。** 目标已有同名文件时（会话回到一个它待过的项目、库被隔离
  重建过、树被手工编辑或从备份恢复、进程在绑定提交与 rename 之间被杀）追加会读成顺序错乱的同一段对话、
  覆盖会毁掉一次 run 的记录，所以问人。拒绝的判据是**问整棵树**（`replay/logs-for`）而不是只看目标，
  因为上面那些来路都会在别处留一个副本。**审计行放在搬之后写**正是为此：先写就会追加进那份刚被判为
  歧义的文件，毁掉拒绝本身要保护的东西。**绑定不回滚**——回滚了库与树的说法仍然不一致，而人接下来要做
  的事在两种情况下一样：决定哪份文件才是这段对话。
- **`replay/logs-for` 与 `locate` 分开。** 前者答一个向量（可能为空、可能多个），搬文件的人要用它自己
  说拒绝的话；后者把"一个都没找到"也变成异常，因为重建不能凭空造一段空对话。两个调用方对"多个"的处理
  不同，所以都不能替对方猜——原先合成一个函数时，搬文件的人拿到的是重建口吻的错误消息。
- **`rebuild` 对定位失败答 404**（不是 400）：什么都没重建，也没有哪份日志有问题，只是这个 stem 什么都
  不指向。截断/损坏仍然是 400。
- **旧 `logs/` 退役三件事都锁在用例里**：列表里没有它（`threads` 走 `projects/`）、库里没有它的行
  （没有任何路径会从磁盘反推归属）、启动不扫描它。文件一个字节不动，`harness.replay` 也仍然能重建它们
  ——把文件手工挪进 `projects/<workspace>/` 就能被看见，工具不替人做这个决定。
- **e2e 的 `seedHome` 只写 config.edn。** 原先预建 `logs/`；现在库与 projects 树都由"谁先写谁建"，
  在这里预建任何一个都是替一个有主人的布局做第二份猜测。UI 套件里那条 `approval` 用例顺带修好：它脚本
  里的 eval 代码还写着 `harness.memory/...`，而那个命名空间早已改名成 `harness.tools`——**这条失败在
  改动前就存在**（干净 HEAD 上逐个跑同样是红的），本次一并修掉。

验收：**264 tests / 1359 assertions 全绿**（既有断言一条未删，只随签名与路径更新）；`cd ui && npm test`
**11 条全绿**（含上面那条修复的 `approval`）。

### 04 落地记录

界面换装配。`ui/src/components/sidebar.tsx`（新）三段位，`session-panel.tsx` 删除，`app.tsx` 的列从
竖排改横排；`lib/projects.ts`（`GET /api/projects` 的类型与取数）、`lib/format.ts`（体积与时间）、
`lib/run-state.ts`（两句拒绝 + 探针）各自独立出来；抄了一份 `@assistant-ui/thread-list` 并**就地重写**。

- **列表的数据来自新端点 `GET /api/projects`，不是运行时的 thread 形状。** 侧边栏要按项目分组、每行
  要显示日志的体积与 mtime，而运行时的 thread 形状里没有项目、也没有磁盘事实——把它硬掰成那个形状是
  尾巴摇狗。所以面板自己取那个端点，适配器只留切换动词（`adapters.threadList` 的 `onSwitchToThread` /
  `onSwitchToNewThread`），threadId 的归属不变（仍是 React state，仍在 await 之前写回）。
- **端点是"库 + 文件系统"的合成，而这是它存在的理由。** 库答"有哪些项目与会话、谁属于谁、谁被归档"，
  文件答"每份日志多大、什么时候改的"。两个问题各自只有一边答得了（一个目录的 jsonl 说不出归属，库也
  不该镜像文件大小），所以字段来源在端点上写清：`projectId`/`path`/`archived` 来自库，
  `bytes`/`lastActivity` 现读文件。
- **两个字段可以是 `null`，而且这是有意义的。** 刚建出来还没跑过的会话就是没有磁盘事实。**不显示成
  0 字节**：0 字节是一份坏掉的日志，不是"还没有日志"。排序上"没有日志"算最新（它是刚刚才被创建的状态，
  每个会话都从这里开始），所以新建的会话会出现在项目顶部而不是被压在老会话下面。
- **`ensure-complete!` 的判据收窄了，因为侧边栏一点就会踩到。** 原先"日志里有记录且末帧不终结"就拒绝；
  而绑定会往日志里写一行 `project/bound`，于是一个刚建好、一次都没跑过的会话**打不开**——重建会用一个
  根本不存在的"截断 run"名义拒掉它。现在的判据是**输入开一段 run、终结帧收一段 run**：审计行多的日志
  是合法的空对话（`{:messages []}`）。这同时修好了另一个旧 bug：第一轮跑完、第二个 input 落盘、然后
  进程被杀——末行是 RUN_FINISHED 但那段 run 没结束，旧判据会放它过去。
- **抄来的 `thread-list.aui.tsx` 是这份清单里唯一被改过的一份，改动逐处有 `LOCAL:` 标注。**
  上游那份是给另一种产品形态的扁平、按日期分组的线程列表；本仓要的是按项目分组、行上带体积与 mtime。
  删掉的是重命名/删除菜单项（本仓没有这两个动词，一个点了会抛的菜单项比没有更糟）与
  `ThreadListItemPrimitive.Trigger`——它的 action 是 `() => aui.threadListItem.switchTo()`，**Promise 被
  丢掉**（见上游的 useThreadListItemTrigger 与 createActionButton），所以被拒的切换只会变成一条无主的
  未处理拒绝；而本票要求"原因显示在所点的行上"，那需要我们自己持有那个 Promise，于是行的点击走组件
  收到的回调，守卫与错误都归侧边栏。
- **三段位的高度契约写在类名上也在注释里**：视口是 `h-dvh` 的行，侧边栏 `shrink-0`、聊天区
  `min-h-0 flex-1`（`Thread` 的根是 `h-full`，`min-h-0` 才让它真的能收缩而不是把整页撑出滚动条）。
  实测：10 个项目、视口压到 1400×420 时 `document.scrollHeight === clientHeight`，项目区
  `scrollTop` 可动，头部 `getBoundingClientRect().top` 滚动前后都是 0。

### 05 落地记录

新建任务从"随便开一个"变成"必须有地方放"。服务端加了一条路由与一个动词，客户端补上添加项目那半边的
界面；`app.tsx` 里那个 `onSwitchToNewThread` 随之**删掉**。

- **`POST /api/projects`（复数）与 `POST /api/project`（单数）是两个不同的动词。** 单数是既有那条：
  把一个**会话**绑到一个目录（`{threadId, dir}`，写 `sessions`）。复数是本票新加的：让一个**目录**成为
  本 home 的项目（`{dir}`，写 `projects`）。两条路由只差一个 `s` 而语义完全不同，所以 `http.clj` 的
  docstring 把这件事写成了路由表的一部分——`projects-get` 与 `add-project-post` 各自点名解释自己那半边，
  免得后来者按 REST 的直觉把复数那条当成"批量绑定"。
- **`add-project!` 是 find-or-create，不是 insert。** 一个已经在列表里的目录再加一次，返回的是**同一个**
  项目行与它的规范路径，不产生第二行。这条与 02 的 `upsert-project!` 是同一条纪律：项目的身份是规范
  路径，所以"再加一次"与"加一个有点像的写法"（`/tmp/x` 对 `/tmp/x/`）落在同一行。真 Chromium 里验过：
  先加 `/tmp/h05proj-a`，再输 `/tmp/h05proj-a/`，列表仍是一行。
- **目录校验在写之前，且是点名失败。** `checked-directory` 把"不存在"与"不是目录"分成 `:missing` /
  `:not-a-directory` 两条人话，由 `add-project!` 抛出、由路由翻成 400。**表单失败时保持打开**，把服务端
  那句原话放在输入框下面，路径还在框里可以改——清空或关掉表单会让一次可修的输入变成要重敲一遍。
- **「选择文件夹…」只填字段，提交永远显式。** 复用了既有的 `POST /api/project/pick`（服务端弹原生目录
  对话框），选中的路径只写进输入框；真正的建项目仍然走用户点「Add」。**取消不是错误**：服务端答
  `{:dir nil}`，界面把它说成"Selection cancelled — nothing was added."，不是红色告警。**"选完就自动提交"
  被明确否掉**——OS 对话框离一次手滑只有一个回车，而库里没有撤销。
- **新建任务是三步，且顺序是有原因的：铸 id → 绑定 → 切过去。** id 由客户端铸（服务端从来没有铸过 id），
  绑定需要这个 id，所以第三步只能走 `switchToThread`：这时它已经是一行有归属的会话，"切到它"就是字面
  意思。适配器的 `onSwitchToNewThread` 因此**没有留下任何事可做，删掉了**（它在 assistant-ui 上游本就是
  可选的）。运行时自己铸一个 id 会让 id 落到本组件够不着的地方，而绑定恰恰要那个 id。
  绑定失败时**不 adopt** 那个 id：会话没生出来，切过去只会让页面停在一条没有家的线程上。
- **一个刚建、一次都没跑过的会话要能打开，这是本票逼出来的服务端修复。** 绑定会往日志里写审计行，所以
  新会话**有文件**；而 `ensure-complete!` 旧判据把这个只有审计行的文件当成了"跑到一半断掉的日志"，于是
  「新建任务」切过去的第一次重建就是 400。判据改成**输入开一段 run、终结帧收一段 run、末尾必须闭合**；
  审计行构成的空对话是合法的（`{:messages []}`）。顺带修好另一个旧 bug（第一轮跑完、第二个 input 落盘、
  进程被杀——旧判据会放它过去）。见 04 落地记录里同一条的详细说明。
- **"哪个项目"是派生出来的，只有一个动作能钉住它。** 新任务落在**当前会话所在的项目**（"再来一个同类
  任务"是人最常说的意思），没有当前会话时落在列表第一个。**点项目行会把它钉住**（同一个手势既选择也展开，
  因为在这里这两件事是同一个意图）。钉住的路径如果不在列表里了（项目被移除）就**自动丢掉这个钉子**——
  否则新任务会安静地投向一个已经不存在的项目。
- **`onAdded` 顺带清掉新建任务那句拒绝。** 加了项目之后，"先添加一个项目"这句就在它自己下面一行被事实
  推翻了；不清掉的话界面在同一屏里自相矛盾。
- **服务端拒绝在 400 里带 `:threadId` 与 `:dir`**（回顾 03 的移动拒绝）：客户端不需要猜它落在哪一边。

验收：**269 tests / 1414 assertions 全绿**（改动前 268 / 1399；既有断言一条未改，只随 05 新增的用例上调）；
`cd ui && npm run build`（`tsc --noEmit` 0 error + Vite 通过）、`npm test` 11 条全绿。真 Chromium 六张截图在
`evidence/`：无项目时的空态、无项目时点新建任务（拒绝 + 添加入口就地展开）、手输坏路径被点名拒绝且表单
不关、新建任务落在选中项目下并成为当前会话、选择文件夹只填字段（未提交、列表未变）、取消选择说的是
"已取消"而不是错误、选中的路径提交后建出项目、同一目录换个写法再加仍是一行。**「选择文件夹…」这一路
是打桩验的**：真对话框会阻塞在一个等人点击的窗口上，自动化过不去（`osascript choose folder` 实测挂住），
所以浏览器里那次点击是把 `fetch` 换成返回固定目录/返回 null 两次，覆盖"填进去"与"取消"两侧；服务端那侧
的对话框本身由 `http_test` 用 `*directory-chooser*` 桩覆盖（含"只填不绑、绑定仍只有一条路由"）。

### 一条与本题无关的既有 flake（记下来，不在本票修）

- **`harness.project` 从内存 atom 换成库里的行**，凡是用 `binding-for` 的地方都换了数据来源。回归保证
  靠既有断言：未绑定仍然是 `nil`、仍然不是错误、工具侧的恒等行为一字不改。
- **侧边栏的列表是快照**。一轮 run 落盘之后列表不会自己变，要等切换/刷新；订阅日志目录不是这张面板的
  事。这一点在界面上要能被看见（有个刷新动作），而不是让人以为列表坏了。
- **既有的会话在侧边栏里不会自动出现。** 不导入、不迁移的直接后果：今天 `~/.clj-harness/logs/` 下的会话
  在新界面上一律不可见，直到人手动把文件挪进 `projects/<workspace>/`（工具不做这件事）。选这条是因为
  自动迁移要猜"这个会话属于哪个项目"，而日志里没有可靠答案——猜错的结果是把一个会话悄悄挂到别的项目
  下，比看不见更难发现。
