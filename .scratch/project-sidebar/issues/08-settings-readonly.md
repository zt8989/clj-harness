# 08 — 设置：一版只读的生效配置

**What to build:** 侧边栏底部钉住的「设置」打开一版**只读**的生效配置：这个进程现在用的是哪个 provider
与 model、reasoning-effort 是多少、**这个选择来自哪一级**（默认 / config.edn / 会话覆盖 / 请求），配置
家目录的绝对路径（以及它是不是 `CLJ_HARNESS_HOME` 给的），home 里现在有哪几份文件。
**api-key 永不出值**——只有"有/没有"与它来自 `.env` 还是环境变量。

写回配置是另一件事，本票不做：它是给"我现在到底在跟谁说话"一个诚实的答案，不是配置编辑器。

**这些值全部来自文件、现读**，不来自库：`config.edn` / `providers.edn` / `harness.edn` 的既有纪律
（每次现读、改配置不重启）在界面上也必须成立——打开设置看到的必须是**此刻**的配置，不是启动时的快照。
这一点有验收，因为它是"配置不进库"在界面上唯一看得见的地方。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 一个只读端点交出上面那几件事实；**`harness.memory` 已有的查询面（`current-provider-config` /
      `selection` 那类"从不带 key"的读取）直接复用**——不为界面新造一条会泄密的读取路径
- [ ] 响应的实现走"带 key 的解析"之后**取差集**（全字段减掉 key 相关字段），因此"新增一个字段忘了判断"
      这一种错法在结构上不可能发生；不是逐字段地判断"这个能显示吗"
- [ ] 有一条测试：把 `.env` 与 `HARNESS_API_KEY` 都设成一个可辨认的哨兵值，然后对**整个响应体做字符串
      搜索**，断言哨兵不出现——不是断言某个字段为空
- [ ] 界面显示：provider、model、reasoning-effort、选择来自哪一级、配置家目录路径
- [ ] 家目录路径要标明它是**默认值**还是 `CLJ_HARNESS_HOME` 给的（这两种情况下的问题排查方式完全不同）
- [ ] api-key 只显示"有 / 没有"与来源（`.env` / 环境变量），任何情况下都不显示值，也不显示长度或前缀
- [ ] **改配置立刻可见**：进程起着，改 `config.edn` 的 model（或 `harness.edn` 的 `:editing`），重开设置
      看到的是新值——不重启、不碰库。这条断言问的就是"配置到底从哪读"（与 01 的"打开数据库不读配置文件"
      是同一件事的两端）
- [ ] 打开设置不影响正在进行的 run，也不改变当前会话
- [ ] 端点失败时，面板说的是服务端的原因，不是空白面板
- [ ] 真 Chromium：打开设置、核对上面每一项、并确认响应体里搜不到 key，截图留档
